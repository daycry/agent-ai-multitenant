# Plan 06.18 — Tools: UI clara, sin duplicados y cableado real del runtime

## Resumen

El subsistema de tools estaba **roto de extremo a extremo entre tres
capas que no compartían una fuente única de nombres**: el **catálogo**
(`read_file`/`write_file`/`http_get`…), los **chat-modes**
(`file_read`/`http_request`…) y el **runtime ejecutable** (`file_read`…).
El boot real del agente sólo montaba `echo`+`noop`+`shell_exec`
condicional; toda la infra de cableado del Plan 06.16 existía y estaba
testeada en aislado pero estaba **muerta en producción**. Consecuencia:
**el operador asignaba `read_file`/`run_pytest`/`http_get` desde una UI
cuidada y el motor sólo ejecutaba `echo`/`noop`/`shell_exec`**; cualquier
otra tool caía en `unknown tool` silencioso.

Este plan endurece el subsistema **de raíz y en orden**: primero la
**verdad backend** (fuente única de nombres + cableado real + dedup),
luego la **verdad visible** (endpoint de set efectivo + catálogo
navegable + runtime-templates), y encima la **UI clara**. Expone el
contrato `effective-tools` que el Plan 06.17 consumirá en el Hub de
Capacidad. Prioridad explícita del operador: la categorización/asignación
de tools debe ser **UI-amigable e intuitiva**.

> **Construido bajo override humano del operador.** El frontmatter del
> plan lo cierra el humano tras los tests humanos + merge del PR; esta
> entrada documenta lo implementado.

## Fase A — Verdad backend

- ✅ **`task_06_18_03`** — **Fuente única de nombres** en
  `packages/shared-domain/src/shared_domain/tool_names.py`
  (`CANONICAL_TOOL_NAMES`) importada por seeds, chat-modes, `approval` y
  los `register_*` del runtime. Capa de **alias retrocompatible**
  (`file_read↔read_file`, `http_request↔http_get+http_post`,
  `notify_user↔send_notification`, `semantic_search↔rag_search`).
  `combine_tool_allowlists` resuelve por canónico (`to_canonical_set`);
  `DEFAULT_TOOL_CATEGORIES` de `approval` migrado a nombres canónicos
  (cierra el bypass latente de aprobación).
  - **Tests**: `tests/integration/test_tool_namespace_unification.py`.
- ✅ **`task_06_18_04`** — **Deduplicación**: migración reversible con
  `UNIQUE (tenant_id, name) WHERE deleted_at IS NULL` en `tools`; enum
  `ToolCategory` + `CHECK` sobre `category`/`security_level`/
  `implementation_type`; `create_tool`/`update_tool` → **409** ante
  colisión (built-in u otra del tenant) y normalización de `name` a
  slug-case.
  - **Tests**: `tests/integration/test_tool_uniqueness_and_taxonomy.py`
    (`-m cross_tenant`).
- ✅ **`task_06_18_05`** — **Cableado real del runtime**. En
  `agent_runtime.__main__.run_task` se construye `WiringContext` y se
  registran **todas** las familias bajo nombre canónico
  (`register_builtin_families`: file / red / orquestación / notificación /
  conocimiento / memoria) + los `run_*` (`register_tool_specs` desde los
  `tool_specs` que ahora **serializa el orquestador**, no sólo nombres) +
  `default_runtime_template` para los `run_*`. Feature-flag por familia
  (`AGENT_TOOL_FAMILY_*`, default backward-compat de 06.15). Punto
  **único** de intersección agente∩modo.
  - **Tests**: `tests/integration/test_runtime_register_all.py` +
    `docker/agent-runtimes/agent-runtime/tests/test_runtime_boot_tools.py`.
- ✅ **`task_06_18_06`** — **Disponibilidad honesta**. Flag derivado
  **`is_runtime_wired`** en `ToolResponse`
  (`RUNTIME_WIRED_TOOL_NAMES`); `PUT /agents/{id}/tools` avisa/`422` ante
  nombre no ejecutable; **familia `git` retirada del seed** (sin ejecutor)
  → el catálogo pasa de 18 a **15 tools** built-in; reconciliación
  `semantic_search`↔`rag_search` en la fuente única.
  - **Tests**: `tests/integration/test_tool_runtime_availability.py`.
