# Plan 06.15 — Asignación de tools por agente (básicas/avanzadas)

## Resumen

Hasta ahora **no existía pantalla para asignar tools a un agente**: el
catálogo (`/tools` CRUD), la junction `agent_tools(agent_id, tool_id,
config_override)` y el panel read-only `agent-tools-diagnostic` ya
estaban, pero `agent_tools` sólo se rellenaba por seeds/SQL, no había
endpoint de asignación, ni sección en el editor de agente, ni distinción
**básicas vs avanzadas** en la UI; y el runtime **no filtraba** el
toolset por `agent_tools` (la restricción real sólo vivía a nivel
chat-mode). Este plan cierra el hueco: **endpoints de asignación por
agente + enforcement backward-compatible en runtime + sección "Tools del
agente" en el editor**, con la taxonomía básicas/avanzadas **derivada**
de `is_builtin`/`implementation_type` (sin cambio de esquema, ver
**ADR 0044**). Reutiliza el patrón del agent↔KB del Plan 06.9
(endpoints + `AgentKbsSection`) y la ruta de `ToolRegistry` del runtime.

> **Construido bajo override humano del operador.** El frontmatter del
> plan lo cierra el orquestador; esta entrada documenta lo implementado.

## Cambios por tarea

### Fase A — Backend: asignación por agente

- ✅ **`task_06_15_01`** — **Endpoints `GET/PUT /agents/{id}/tools`**.
  Router en `agents.py`: `GET` (`tenant_user`) lista las tools asignadas
  vía `agent_tools` con la _read shape_ del panel `agent-tools-
diagnostic` + `is_builtin` (taxonomía) + `config_override`; `PUT`
  (`tenant_admin`) reemplaza **declarativamente** el conjunto entero en
  una transacción (delete + insert). Validación de scope: built-in
  asignable a cualquier agente; custom sólo del tenant (cross-tenant
  oculto por RLS → **422**); MCP sólo si el proyecto del agente declara
  ese MCP server (match por prefijo de server-name de
  `implementation_ref` → **422** si no). Un agente `global_builtin`
  rechaza la escritura con **403** (forkear primero). Tenant-scoped por
  RLS vía la tabla `agents`. Schemas `AgentToolAssignment` /
  `SetAgentToolsRequest` (sin `tool_id` duplicados) / `AgentToolResponse`
  en `schemas/agents.py`.

### Fase B — Enforcement en runtime

- ✅ **`task_06_15_02`** — **El toolset del agente respeta
  `agent_tools`**. Módulo `api_server/agent_tools_enforcement.py` (puro,
  sin HTTP): `resolve_agent_tool_names(session, agent_id)` devuelve el
  `frozenset[str]` de `Tool.name` asignados o **`None`** cuando no hay
  filas (sentinel "sin restricción" = comportamiento actual);
  `combine_tool_allowlists(agent_set, mode_set)` **intersecta** el set
  por-agente con el `allowed_tools` del chat-mode (cada `None` = "esa
  capa no restringe"; ambos `None` → `None`). Cableado en el orquestador
  (`dispatch.py`): se resuelve, se intersecta y **sólo si el resultado
  no es `None`** se emite `allowed_tools` en el task spec
  (`ExecutionRequest.allowed_tools → _agent_spec → AGENT_TASK_SPEC →
ToolRegistry.set_allowed_tools`). El `ToolRegistry` del runtime ya
  rechazaba en `call()` cualquier tool fuera del allowlist. **Backward-
  compatible**: sin filas ⇒ no se emite la clave ⇒ comportamiento previo.

## Migraciones

**Ninguna.** El plan se monta sobre columnas y la junction
`agent_tools` que **ya existían**. La taxonomía básica/avanzada es
**derivada** (no hay columna `tier`); el enforcement usa el sentinel
`None` para preservar el comportamiento de los agentes sin filas. Head
único antes y después del plan: **`0071_model_prices_provider_id`**.

## Endpoints nuevos

| Endpoint             | Método | Rol mínimo     | Notas                                                              |
| -------------------- | ------ | -------------- | ------------------------------------------------------------------ |
| `/agents/{id}/tools` | GET    | `tenant_user`  | lista las tools asignadas (incluye `is_builtin` para la taxonomía) |
| `/agents/{id}/tools` | PUT    | `tenant_admin` | reemplazo declarativo del set; validación de scope                 |

> Scope (ADR 0044): built-in → cualquier agente; custom → sólo del
> tenant (cross-tenant 422); MCP → sólo si el proyecto declara el server
> (422 si no); `global_builtin` → 403. Lista vacía ⇒ limpia y restaura
> el comportamiento por defecto.

## Taxonomía básica/avanzada (derivada — sin esquema)

```
básica   = is_builtin == true
avanzada = is_builtin == false
           OR implementation_type ∈ {mcp_tool, http_endpoint,
                                      python_function, docker_command}
```

`security_level` (`safe`/`sandboxed`/`privileged`) es un eje
**ortogonal**. Ver ADR 0044 para la justificación de no persistir el
tier.

## Enforcement (backward-compatible — NON-NEGOTIABLE)

- **Sin filas `agent_tools`** ⇒ `resolve_agent_tool_names` devuelve
  `None` ⇒ no se emite `allowed_tools` ⇒ **comportamiento actual** (sin
  restricción por agente). No se le quita ninguna tool a un agente
  existente.
- **Con filas** ⇒ el agente queda restringido a exactamente esas tools;
  el `ToolRegistry` rechaza cualquier otra en `call()`.
- **Intersección** con el `allowed_tools` del chat-mode cuando aplique
  (cada capa es un límite independiente; el efectivo es el cruce). Set
  vacío = bloquea todo (como el modo discusión).
- El frontend **no es la barrera**: la restricción real vive en el
  runtime; la UI sólo configura.
