# Plan 06.5 — Orchestrator wiring

## Resumen

Plan 06 entregó los módulos individuales del ciclo testing → revisión →
git (worker-test, dep-cache, worktrees + bare repos, pool elástico,
plan-git workflow, review-runtime, task lifecycle, plan progress) con
sus tests verdes y un `plan_runner.py` síncrono que los integra.

Plan 06.5 cablea esos módulos en la **infraestructura productiva**:
persistencia en BD, endpoints REST/WS auténticos, Celery tasks reales
que invocan a los módulos, beat scheduler para mantenimiento, e
integración del agente reviewer con el `TestReport` canónico. El
`plan_runner.py` síncrono se mantiene en paralelo (ADR 0027) — sirve
para demos, smoke tests y troubleshooting offline.

### Endpoints REST/WS nuevos (Fase B)

- `GET /api/v1/tasks/{task_id}/history` — `lc.history(task_id)`
  serializado desde `task_audit_events`. Auth + RLS.
- `POST /api/tasks/{task_id}/human-action` — invoca
  `lc.apply_human_action`. Acciones tipadas (`HumanAction`):
  `approve_manual → done`, `reassign_with_guidance → backlog + retry++`,
  `block_with_reason → blocked`, `cancel → cancelled`. Sólo acepta tasks
  en `awaiting_human_approval` o `blocked`. Persiste audit event.
- `POST /api/plans/{plan_id}/free-task` — crea task con
  `inputs.is_free_task=true` (`parent_checkbox_id=null`).
- `GET /api/plans/{plan_id}/escalated-tasks` — lista tasks en
  `awaiting_human_approval` con los últimos 20 audit events por task.
- **`apps/api-server/src/api_server/routers/review.py`** (nuevo) —
  endpoints firmados HMAC, no JWT (Plan 06.5 §B):
  - `GET /review/{session_id}` — shell HTML del SPA, verifica `sig`/`exp`
    y hace `touch_activity`.
  - `POST /review/{session_id}/rerun` — marca `rerun_requested=true`.
  - `WS /ws/review/{session_id}/logs` — suscribe Redis pub/sub al canal
    `review:logs:{session_id}`; verifica firma **antes** de `accept()` —
    cierra con code 4403 si inválida. Usa
    `get_admin_sessionmaker()` (BYPASSRLS) porque el handle del review
    es per-tenant pero la auth es la firma, no la sesión.
- **`api_server.config.review_url_signing_secret`** —
  `SecretStr`, env `API_SERVER_REVIEW_URL_SIGNING_SECRET`. Tenant-level
  (no per-session), para que `review_sessions` no tenga que guardar un
  secreto por fila.

### Celery tasks y beat (Fase C + D)

- **`workers.run_test_runtime`** (cola `test`) — agrupa
  `acceptance_criteria` en `RuntimePlan`s, ejecuta
  `TestRuntimeRunner.launch` por plan, emite audit
  `test_run_started` al encolar + `test_run_completed` por plan
  (`exit_codes`, `container_id`, `network_name`, `timed_out`,
  `logs_tail` truncado a 4 kB). Fallback a `status="docker_unavailable"`
  cuando el daemon no responde — el orchestrator path sigue testable
  sin infraestructura.
- **`workers.compose_review_runtime`** (cola `review`) — persiste
  `review_sessions` row primero (estado recuperable), luego intenta el
  spawn vía `docker.from_env()` con la misma envolvente endurecida que
  `agent-runtime` (cap-drop ALL, no-new-privileges, read-only root, uid
  no-root, mem/pids capados, tripwire de socket Docker). Worktree
  bind-montado en `/workspace`. Si Docker falla, devuelve
  `container_ids=[]` + nota "pending spawn" — la fila DB sigue siendo
  útil para la admin-panel.
- **`apps/workers/src/workers/maintenance.py`** (nuevo) — 4 tasks
  scheduled:
  - `workers.idle_sweep_pools` — heartbeat (el sweep real va por
    in-process ticker, deferred a Fase F).
  - `workers.expire_review_runtimes` — DB sweep:
    `list_running_overdue → expired`,
    `list_running_idle(24h) → suspended`.
  - `workers.purge_dep_cache` —
    `DepCacheManager(<data_root>/dep-cache).purge_expired()`.
  - `workers.prune_worktrees` — walk
    `<data_root>/projects/*/repos/*.git/`, instancia `WorktreeManager`
    por `(tenant, project, repo)`.
- **`apps/workers/src/workers/beat_schedule.py`** (nuevo) — 4
  schedules:
  - `idle_sweep_pools` cada 30 s → cola `default`.
  - `expire_review_runtimes` cada 5 min → cola `review`.
  - `purge_dep_cache` diario 03:00 UTC → cola `test`.
  - `prune_worktrees` diario 03:30 UTC → cola `default`.

## Decisiones técnicas notables

### Persistencia primero, spawn después

`compose_review_runtime` persiste la fila DB **antes** de intentar el
spawn de Docker. El spawn es recuperable (un follow-up tick puede
reintentar, el daemon puede no estar disponible en CI); la fila DB no
lo es. Si la persistencia falla, el job de Celery falla (y el broker
reintenta). Si el spawn falla, la sesión queda en `running` con
`container_ids=[]` y la admin-panel la muestra como "pending spawn"
con un botón de reintento.

### Firma HMAC verificada antes de `WebSocket.accept()`

El router de review (`/ws/review/{session_id}/logs`) verifica la firma
**antes** de aceptar el handshake — close code 4403 si inválida. Esto
es importante: aceptar primero y luego cerrar deja al cliente con un
handshake exitoso que puede leer como "URL válida" antes del close.
Verificando antes, un atacante con URL caducada/falsa ni siquiera
establece la conexión.

### Auth bifurcada — JWT vs HMAC

Los endpoints `/api/...` siguen JWT + tenant-id middleware. Los
endpoints `/review/{session_id}/...` (y el WS correspondiente) son
**sólo HMAC** — el reviewer humano abre la URL desde un email/Slack y
no tiene una sesión JWT del tenant. La firma incluye `session_id|exp`
y se valida con `hmac.compare_digest`. La caducidad (`exp`) es la del
review session.

### `plan_runner.py` sigue vivo (ADR 0027)

El `plan_runner.py` sync de Plan 06 no se borra ni se reemplaza — los
dos paths conviven. La razón: el sync es invaluable para demos
(no requiere Celery + Redis + Postgres corriendo), smoke tests
(determinístico, sin dependencia de tasks asíncronos), y
troubleshooting de los módulos en aislamiento. El path async es el
productivo. Ambos importan los mismos módulos
(`api_server.task_lifecycle`, `workers.test_runtime`, etc.) — el
cambio es sólo el orchestrator que los pega.
