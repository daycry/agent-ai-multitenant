# Plan 06.7 — Detector de memorias similares + Tenant-settings genéricos

## Resumen

Dos cosas relacionadas:

1. **Detector de memorias similares (Nivel 1)** — endpoint pgvector
   que devuelve top-K candidatos por coseno, con UI accionable
   (Fusionar / Descartar) en `/admin/memories`. Sin LLM en el path:
   el % es coseno directo, la decisión es del humano.
2. **Sistema de tenant-settings genéricos categorizados** — tabla
   `tenant_settings(tenant_id, category, key, value)` + endpoints
   genéricos + página `/admin/settings` con cards por categoría
   (cada una con su icono lucide-react). Necesario porque el
   threshold + limit del detector deben ser configurables, y el sistema
   anterior (una columna por feature en `organizations`) no escala.

`hourly_rate` se queda donde está — no migramos lo que funciona. La
página `/admin/settings/hourly-rate` existente sigue activa; el nuevo
`/admin/settings` la enlaza desde la card de la categoría "Costes".

## Cambios visibles

### Tabla nueva y schema

- **Migration Alembic** `20260527_0023_tenant_settings.py` —
  `tenant_settings(tenant_id, category, key, value JSONB, updated_at,
updated_by_user_id, PK(tenant_id, category, key))`. RLS por
  `tenant_id` activo.
- **Model SQLAlchemy** `TenantSetting` en `db/models.py`.

### Registry code-side y endpoints

- **Registry** [`api_server/settings_registry.py`](../../apps/api-server/src/api_server/settings_registry.py) —
  `KNOWN_SETTINGS: dict[category, CategoryDef]` con cada
  `(category, key)` mapeado a `{type, default, description_es,
validator, icon, label}`. El registry es la fuente de verdad: el
  PUT rechaza keys no listadas, los tests pinean cada `default`, la
  UI lo lee para generar formularios automáticos.
- **Helper** `get_setting(session, tenant_id, category, key)` que
  abstrae lectura + default.
- **Endpoints nuevos** en
  [`routers/tenant_settings.py`](../../apps/api-server/src/api_server/routers/tenant_settings.py):
  - `GET /tenant-settings/_registry` → todo el registry serializado.
  - `GET /tenant-settings/{category}` → todas las keys de esa
    categoría dentro del tenant (sólo los valores set, no los defaults).
  - `GET /tenant-settings/{category}/{key}` → valor único; 404 si no
    está → caller usa el default code-side.
  - `PUT /tenant-settings/{category}/{key}` body `{ value }` →
    upsert con validación contra el registry. Sólo `tenant_admin`.

### Detector de memorias

- `GET /memories/{id}/similar` — lee `memories.similarity.threshold`
  y `memories.similarity.limit` del tenant-settings (defaults `0.85` y
  `5` del registry), corre pgvector cosine query restringida al
  `scope + tenant` del row origen, devuelve `[{memory, similarity}]`.
- `POST /memories/{id}/merge-into` body `{ target_id }` — funde
  content + tags en target, soft-deletes el origen, anota
  `metadata.merged_from` en target.

### UI

- **Nueva** `/admin/settings/page.tsx` — index categorizado con cards
  por categoría conocida (consume `GET /tenant-settings/_registry`).
  Cada card tiene su icono lucide-react resuelto desde un string del
  registry (mapping `string → component` en frontend).
- **Nueva** `/admin/settings/memories/page.tsx` — formulario con
  slider para `similarity.threshold` (0.5-0.99) + input numérico para
  `similarity.limit` (1-20). Persiste vía PUT al endpoint genérico.
- `/admin/memories/page.tsx` — botón "Ver similares" por row + modal
  con candidatos + botones Fusionar / Descartar.
- **Sidebar** — el item "Settings" pasa a apuntar a `/admin/settings`
  (no a `/admin/settings/hourly-rate`); las dos páginas siguen
  cohabitando.

### Categorías iniciales

```
memories  → "Brain"  (lucide-react)
costs     → "Coins"  (link a la página dedicada de hourly-rate)
```

## Decisiones técnicas notables

### Registry de settings conocidos en código, no en BD

El registry vive en `api_server.settings_registry` y es immutable en
runtime. El PUT rechaza keys no listadas. Ventajas:

- Type safety en backend (`get_setting` devuelve el tipo correcto vía
  el `type` del registry).
- UI generable automáticamente desde el `_registry` endpoint —
  ningún formulario está hardcodeado.
- No hay key/value libre que termine siendo basura.
- Migrar a una key nueva = añadir al registry + un test. Sin Alembic.

### `value JSONB`, no `string`

Permite floats, ints, strings, dicts. El validator del registry
chequea el tipo concreto antes del upsert.

### Defaults code-side, no DB-side

Si el row no existe en `tenant_settings`, `get_setting` devuelve el
default del registry. El tenant no necesita haber tocado el setting
para que el sistema funcione — el detector arranca con
threshold=0.85 y limit=5 directamente.

### Iconos como strings (no objetos importados)

El registry vive en backend y se serializa por JSON; declarar el
componente lucide-react en Python no tiene sentido. La UI tiene un
mapping `string → component` con los iconos disponibles
(`Brain`, `Coins`, `Cpu`, …).

### PUT requiere `tenant_admin`

Mismo patrón que `/tenant-settings/hourly-rate`. Lo enforcea el
helper `_require_tenant_admin` que mira la membership del JWT user
contra el tenant. Cambiar settings es operación de admin.

### Fusión asimétrica de memorias

Cuando el humano elige "Fusionar A en B":

- `B.content = B.content + "\n\n---\n" + A.content`.
- `B.tags = unión(A.tags, B.tags)`.
- `A.deleted_at = now()`.

La memoria target (B) sobrevive con su embedding original; la origen
(A) queda soft-deleted. El re-embed de B la próxima vez que se
actualice corresponde al Memorizer (no parte del path síncrono).

## Tests

- **Test humano `human_06_7_01`** — tenant-settings categorizados con
  iconos funcionan. PASSED.
- **Test humano `human_06_7_02`** — detector end-to-end con datos
  seedeados (memorias A/B con cos 0.896, C aleatorio, D sin embedding).
  PASSED.
- **Fix descubierto** durante los tests humanos: el endpoint usaba
  `str(numpy_array)` que produce formato incompatible con pgvector
  (`'[0.1 0.2 0.3]'` con espacios en vez de comas). Corregido a
  `","join(f"{x:.6f}" ...)` — misma receta que ya usaban
  `memorizer/recall.py` y `rag/search.py`.
