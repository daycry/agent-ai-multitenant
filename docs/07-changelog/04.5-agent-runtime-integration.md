# Changelog — Plan 04.5 · Integración agent-runtime ↔ memoria/RAG

Plan corto e intercalado entre Plan 04 (Memoria + RAG + KBs) y
Plan 05 (Multi-agente y coordinación avanzada). Su único propósito:
**cablear**. Plan 04 construyó la pila completa en el api-server;
Plan 04.5 la conecta al sandbox donde el agente realmente corre.

## Resultado

Al cierre del plan, la plataforma puede:

1. **Memorizar ejecuciones sin intervención humana.** Cuando una
   `Execution` cierra como `done`, el worker dispara
   `workers.memorize_execution` (Celery, fire-and-forget). El
   Memorizer aplica `should_memorize`, destila con Ollama y
   persiste `MemoryEntry` con el `scope` y owner pointer correctos
   (team_id desde el proyecto, project_id desde la task, global sin
   owner; el caso `private` se skipea con log para agentes IA).

2. **Tools de memoria reales en el agente.** `memory_recall` y
   `memory_store` ya no devuelven 501. Llaman a
   `/internal/agent/memory-recall` y `/internal/agent/memory-store`
   vía httpx, con el bearer `AGENTIC_INTERNAL_TOKEN` minteado por
   el worker. Owner pointers (team_id / project_id) se resuelven
   en el servidor desde el `Agent` row — el sandbox no puede
   widening de scope.

3. **RAG en el agente.** `rag_search` es un tool nuevo (no había
   placeholder). El sandbox llama a `/internal/agent/rag-search`
   y reusa el motor `api_server.rag.tool.rag_search` (BM25,
   vector y reranker). El `project_id` se pin del agente: cero
   forma de escapar al KB de otro proyecto.

4. **Tools Docling en el agente.** `document_convert` deja de ser
   501 y devuelve los chunks estructurados de un Document
   existente (lectura rápida sobre `chunks`). `promote_to_kb` es
   un tool nuevo que duplica un Document + sus chunks en otra KB
   del mismo proyecto. Ambos comprueban grants en
   `kb_projects` para lectura **y** escritura.

5. **Auth dedicado para el sandbox.** `/internal/agent/*` vive
   bajo un único `get_agent_principal` que valida un JWT con
   `kind: "agent"`. Tokens humanos sin ese claim se rechazan
   con 401; tokens de agente borrado entre mint y uso → 403.

## Decisiones clave (ADR 0024)

Las cinco tools del sandbox hablan con el api-server por
`/internal/agent/*` (HTTP+JSON). Alternativas descartadas: opción B
(pre-inyectar contexto en `AGENT_TASK_SPEC`) y opción C (sink para
writes + HTTP para reads). HTTP puro gana por **read-after-write
dentro de la misma run** y **menos piezas móviles**. Ver
`docs/05-architecture-decisions/0024-internal-agent-http-api.md`.

## Tests humanos (2/2)

Las dos pruebas humanas que Plan 04 dejó pendientes a la espera
del wire-up del agent-runtime ya son ejecutables end-to-end:

1. **`human_04_5_01`** — _Memory replay._ Arrancar una ejecución
   `done` con un agente `memory_scope=team_shared`, comprobar en
   `/admin/memories` que aparece la(s) entrada(s) destilada(s).
   Lanzar una segunda ejecución que pida algo afín; los pasos
   `recall` del nuevo agente deben referenciar la memoria
   almacenada.

2. **`human_04_5_02`** — _RAG con citas._ Subir un PDF a una KB de
   un proyecto (UI Plan 04 task_04_19). Esperar a que se indexe.
   Pedirle al agente algo cuya respuesta esté en ese PDF; el
   `steps_log` debe incluir un `tool_call` a `rag_search` con
   hits cuyo `document_id` apunte al PDF subido.
