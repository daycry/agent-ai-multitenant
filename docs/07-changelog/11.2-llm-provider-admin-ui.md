# Plan 11.2 — UI de administración de proveedores LLM (System Admin)

## Resumen

Hasta ahora los proveedores LLM (ADR 0021: Claude Agent SDK, GitHub
Copilot, Azure AI Foundry vía APIM, Ollama) **sólo se configuraban en el
instalador** (Fase 15, paso 5) y sus credenciales vivían en Vault
(`secret/platform/llm-providers`); no había pantalla para verlos, crearlos,
editarlos, rotar credenciales o probar la conexión post-instalación. Este
plan materializa la decisión del **ADR 0028**: proveedores **platform-global,
gestionados sólo por `system_admin`**, con sus secretos en Vault. Aporta la
tabla `llm_providers`, el backend CRUD `system_admin`, el Device Flow de
Copilot, el cableado del factory de runtime (precedencia DB > env) y la
página `/admin/llm-providers`, reutilizando lo que ya existía (catálogo
`model_prices` / `/admin/model-prices`, el cliente Vault del backend, el
gate RBAC `require_system_admin`, y la máquina de Copilot de
`shared_llm.providers.copilot`).

> **Construido bajo override humano del operador.** El frontmatter del plan
> lo cierra el orquestador; esta entrada documenta lo implementado.

## Cambios por tarea

### Fase A — Modelo de datos + backend de proveedores

- ✅ **`task_11_2_01`** — **Tabla `llm_providers` + ORM + migración**.
  Tabla **platform-global** (sin `tenant_id`, **sin RLS**): `id`, `kind`
  (`TEXT` + CHECK `ck_llm_providers_kind` ∈ {`claude_sdk`,`copilot`,
  `azure_foundry`,`ollama`}), `display_name`, `base_url` (nullable),
  `secret_vault_path` (nullable — puntero Vault, nunca el secreto),
  `config` JSONB (no-secretos), `is_active` (default true), timestamps.
  Índice parcial `ix_llm_providers_kind_active`. ORM
  (`db/llm_providers.py`) + enum `LLMProviderKind` + repositorio
  (`get_llm_provider` / `list_llm_providers` / `list_active_llm_providers_by_kind`).
  Acceso sólo vía el engine BYPASSRLS de los endpoints `system_admin`;
  la migración no concede la tabla a `app_user`. Migración **0070**.
- ✅ **`task_11_2_02`** — **Backend CRUD `system_admin` + Vault +
  test-connection**. Router `/admin/llm-providers`
  (`GET` list / `POST` / `GET {id}` / `PUT {id}` / `DELETE {id}` /
  `POST {id}/test`), todo `require_system_admin` sobre `get_admin_session`.
  La credencial llega como `pydantic.SecretStr`, se escribe en Vault en
  `platform/llm/<provider_id>` y se persiste **sólo** `secret_vault_path`;
  **nunca** se devuelve (la respuesta expone campos no-secretos + un
  booleano derivado `has_credential`). Campos de credencial por `kind`
  espejando el instalador: `claude_sdk`/`copilot` → `oauth_token`;
  `azure_foundry` → `api_key` + `base_url`; `ollama` → `base_url` +
  `bearer_token` opcional. Store Vault inyectable (`llm_providers/vault.py`:
  `HvacLLMProviderVaultStore` prod + `InMemoryLLMProviderVaultStore` test).
  `/test` (`llm_providers/liveness.py`) hace una llamada mínima por `kind`
  leyendo el secreto de Vault y devuelve un estado clasificado
  (`ok`/`auth_error`/`connection_error`/`config_error`/`upstream_error`)
  sin filtrar el secreto. Sin Vault cableado → `503`; fallo de escritura →
  rollback + `502`.

### Fase B — Device Flow Copilot + cableado runtime

- ✅ **`task_11_2_03`** — **Device Flow de GitHub Copilot**. Router
  `/admin/llm/copilot/device-flow` (`system_admin`): `POST /start` arranca
  el flujo para un provider `copilot` existente y devuelve `user_code` +
  `verification_uri` (+ `device_code`/`interval`/`expires_in`); `POST /poll`
  hace **un** intento de poll (`pending`/`slow_down`/`expired`/`denied`/
  `authorized`) y, al autorizar, acuña el token OAuth, lo escribe en Vault
  (`oauth_token` en `platform/llm/<provider_id>`), fija `secret_vault_path`
  y **nunca** lo devuelve. Reutiliza `shared_llm.providers.copilot`
  (no reimplementa el protocolo). Cliente httpx inyectable (red mockeada en
  tests).
- ✅ **`task_11_2_04`** — **Cableado del factory de proveedor (DB+Vault,
  fallback env)**. `llm_providers/factory_resolver.py`:
  `resolve_provider_config(kind)` lee la fila ACTIVA más reciente del `kind`
  junto con su credencial de Vault y devuelve
  `ResolvedProviderConfig(base_url, secret)`, que el factory de runtime
  superpone sobre el spec de env/instalador. **Precedencia DB row > env**:
  sin fila activa devuelve `None` y se mantiene el fallback actual sin
  romper call sites. Tipo local estructuralmente compatible con el
  `ResolvedProviderConfig` del runtime (sin acoplar la api-server a la
  cadena de import del runtime). Un blip de Vault degrada a "sin
  credencial" (deja la de env) en vez de fallar el run.

## Endpoints nuevos

| Endpoint                               | Método | Rol mínimo     | Notas                                                       |
| -------------------------------------- | ------ | -------------- | ----------------------------------------------------------- |
| `/admin/llm-providers`                 | GET    | `system_admin` | lista (newest-first)                                        |
| `/admin/llm-providers`                 | POST   | `system_admin` | crea; credencial `SecretStr` → Vault, write-only            |
| `/admin/llm-providers/{id}`            | GET    | `system_admin` | sin secreto                                                 |
| `/admin/llm-providers/{id}`            | PUT    | `system_admin` | edita / rota credencial                                     |
| `/admin/llm-providers/{id}`            | DELETE | `system_admin` | borra row + secreto de Vault                                |
| `/admin/llm-providers/{id}/test`       | POST   | `system_admin` | liveness clasificado (lee Vault, no echo del secreto)       |
| `/admin/llm/copilot/device-flow/start` | POST   | `system_admin` | `user_code` + `verification_uri`                            |

## Manejo de credenciales (NON-NEGOTIABLE — sólo Vault)

- Credencial recibida como `SecretStr` → escrita en Vault (mount KV v2
  `secret`) en `platform/llm/<provider_id>`. La BD persiste **sólo**
  `secret_vault_path`; **nunca** una columna con el valor, **nunca** logueado,
  **nunca** devuelto. La respuesta expone `has_credential` (derivado del
  puntero) en su lugar.
- Reutiliza el cliente Vault del backend (mismo seam inyectable que el resto
  de la plataforma); el instalador escribe los mismos campos por `kind`
  (`vault_bootstrap.py`).
- Tests assertan que el secreto **aterriza en Vault** y está **ausente** de
  la respuesta de la API y de la fila de BD.
