# ADR 0098 — Política de push/PR y re-sync del ciclo de plan

## Contexto

El principio rector 5 de `CLAUDE.md` («Plan = unidad de cambio… al completar el plan se abre un PR automático») lo materializan ADR 0072 (auto-PR por proveedor) y ADR 0085 (worktree en la ejecución, ambos `accepted`). La auditoría de plataforma 2026-07-03 (`docs/roadmap/auditoria-plataforma-2026-07-03.md`, causa raíz **A** identidad git + **G** cierre incompleto) verificó adversarialmente contra HEAD `3d22337` que **la mecánica del ciclo git funciona sobre el bare local pero no contra un remoto real**. El plan `docs/roadmap/cadena-pr-plan.md` implementa la mecánica; **remite explícitamente a este ADR las tres decisiones de política** (su sección «Queda fuera → ADR candidato 0098»). Las tres, con evidencia:

**(P3) En modo `incremental` — que es el default — la rama nunca llega al remoto.** El default de `branch_push_mode` es `incremental` (`apps/workers/src/workers/plan_git.py:186`; `apps/workers/src/workers/plan_pr.py:37-39`), pero el paso de commit por tarea solo empuja worktree→bare local: `_git()` instancia `PlanGitWorkflow(...).push_review_to_bare(...)` y **no llama nunca** a `push_branch_to_remote` (`apps/workers/src/workers/execution.py:1002-1006`). Y `open_plan_pr` solo fuerza el push al remoto si el modo es `final_only` (`apps/workers/src/workers/plan_git.py:338-339`). Resultado: con el default la rama del plan vive solo en el bare y **jamás sube al `origin`** — ni por tarea ni al cierre. Contradice la decisión 5 de ADR 0085 («`push_branch_to_remote` según el modo»). `push_branch_to_remote` existe y está bien (`plan_git.py:292-314`, con `auth_env` ADR 0072), pero no tiene quien lo invoque en `incremental`.

**(P4) El «merge directo a la rama base» es una opción de UI sin efecto.** El único código que materializa el merge directo es `apply_push_policy`, que hace `git update-ref refs/heads/{default} → refs/heads/{plan_branch}` **sobre el bare** (`apps/workers/src/workers/plan_git.py:378,397-409`). Tiene **dos** carencias: (a) **no tiene caller de producción** — solo lo ejercitan tests; `open_plan_pr` no lo llama (`plan_pr.py:107` invoca `wf.open_plan_pr`, no `apply_push_policy`); (b) aun cableado, solo movería el `default` del **bare local**, no el del remoto — el propio código admite que «el push del nuevo tip del default es un asunto aparte» (`plan_git.py:391`). La UI ofrece «Merge directo a la rama base» (`apps/admin-panel/components/projects/git-config-section.tsx:254`, valor `direct_to_default_allowed`), se persiste en `worker_config.git_policies`, pero se comporta **idéntica** a «Abrir PR»: un botón que promete algo que no ocurre.

**(P5) No hay re-sync automático del remoto; el docstring promete infra inexistente.** `fetch_remote` (`apps/workers/src/workers/git_repos.py:272-288`) solo se ejecuta al (re)guardar la config git: `set_project_git` → `enqueue_clone_project_repo` (`apps/api-server/src/api_server/routers/projects.py:365`) → la task de clone hace un `fetch_remote` (`apps/workers/src/workers/repo_clone.py:105`). Su docstring afirma que se llama «periódicamente (scheduled celery beat task)» y «desde el webhook receiver cuando un push aterriza en el remoto» (`git_repos.py:275-278`) — **ambos mecanismos no existen**: `BEAT_SCHEDULE`/`build_beat_schedule` no tienen ninguna entrada git (`apps/workers/src/workers/beat_schedule.py:46-135,230-333`) y no hay `enqueue_fetch_remote` en el cliente Celery (`apps/api-server/src/api_server/celery_client.py`, solo `enqueue_clone_project_repo:129` y `enqueue_open_plan_pr:178`). Consecuencia: si un humano mergea el PR o pushea un hotfix a `main` en el remoto, el bare local queda **stale** y el siguiente plan ramifica sobre una base vieja.

**Dato relevante que reduce el coste de una de las opciones:** ya existe un framework completo de **webhooks entrantes con verificación de firma HMAC para GitHub y GitLab**: `verify_incoming_signature` (`apps/api-server/src/api_server/webhooks/signatures.py:148`), la tabla de esquemas por origen con `GITHUB`/`GITLAB` en cabecera `X-Hub-Signature-256` (`signatures.py:47-60,77-84`), y el endpoint público `POST /webhooks/incoming/{origin}/{config_id}` con cap de cuerpo, rate-limit, RLS e idempotencia por `delivery_id` (`apps/api-server/src/api_server/routers/incoming_webhooks.py:1-38`). Su catálogo de acciones está **cerrado** a `create_task`/`comment`/`escalate` (`apps/api-server/src/api_server/webhooks/actions.py:9-20`) — orientado a crear tareas, no a operaciones de infraestructura git.

**Severidad efectiva: P1 latente.** La BD tiene 0 planes `completed`, así que la cadena aún no se ha disparado; pero el único proyecto con git real («Api CI» → GitHub, auth PAT) tocaría P3/P4 en cuanto su plan pase a `completed`. Hay que fijar la política antes del primer cierre real.

## Decisión propuesta (pendiente de aprobación)

Tres decisiones, una por eje:

**1) Timing y default del push al remoto → `incremental` sigue siendo el default, pero cableado de verdad y como paso best-effort no bloqueante.** Se mantiene el default heredado de ADR 0072 (tabla de políticas) y ADR 0085 dec.5 (no se contradice ningún ADR `accepted`). `cadena-pr-plan` **T3** conecta `_commit_and_push_worktree` → `push_branch_to_remote` según `branch_push_mode` (incremental = push por tarea aceptada; `final_only` = difiere al cierre, que ya funciona). **Contrato nuevo que fija este ADR:** el push al remoto es una **réplica best-effort** — la fuente durable es el bare local; un fallo transitorio de red/auth en el push incremental **se loguea con contexto pero NO marca la tarea `commit_failed`** ni la bloquea (a diferencia del commit worktree→bare, que sí es fatal, `execution.py:1016-1021`). `final_only` queda documentado como la elección para proyectos que no deben exponer WIP pre-validación al remoto (los commits `wip(escalated)`, `execution.py:980, llegan al remoto en modo incremental) — encaja con la plantilla «Cliente Externo» del principio 11.

**2) «Merge directo a la rama base» → se RETIRA de la UI; el merge directo real queda gated a un diseño futuro.** `cadena-pr-plan` **T5** quita la opción `direct_to_default_allowed` del select (`git-config-section.tsx:254`), dejando la superficie de usuario en `forbidden` | `branch_only_pr_required`. Se **conserva el valor en el enum del dominio** (`PushPolicy`, `plan_git.py:64`) para no romper la deserialización de filas ya persistidas, que pasan a comportarse como `branch_only_pr_required` — que es **exactamente lo que ya hacen hoy** por P4 (cambio de comportamiento observable = cero). `apply_push_policy` se retira o queda cubierto por un test que documente que no tiene caller de producción. El **merge directo real** (o bien fast-forward del bare + `push origin default:default`, o bien auto-merge del PR vía API del proveedor) se re-introduce cuando exista un diseño que respete el gate de validación humana / acciones sensibles (principio 11) y decida el caso no-fast-forward; no se implementa en `cadena-pr-plan`.

**3) Re-sync del remoto → botón manual «Sincronizar» AHORA + beat periódico configurable como automático por defecto; webhook receiver de push DIFERIDO (gated).**

- **Ahora (`cadena-pr-plan` T6):** endpoint `POST /projects/{id}/git/sync` → encola `fetch_remote` (nuevo `enqueue_fetch_remote` + task, espejo de `clone_project_repo`) y **corregir el docstring mentiroso** de `fetch_remote` (`git_repos.py:275-278`). Cubre el caso «acabo de mergear el PR, resincroniza el bare».
- **Este ADR aprueba añadir un beat periódico** como mecanismo automático por defecto: una entrada en `build_beat_schedule` (`workers.sweep_project_git_remotes` o equivalente) que recorre los proyectos con `git_config.remote_url` y hace `fetch --prune` best-effort, con **cadencia configurable** (`WORKERS_GIT_FETCH_CRON`, default conservador p.ej. cada 6 h) y **kill-switch** platform setting (`git_fetch_enabled`, default OFF hasta que el operador lo active), siguiendo el patrón ya establecido de `price_sync`/`backup`/`fx_fetch` (`beat_schedule.py:230-312`), pinned a la queue `default`. Es el mejor coste/beneficio para este despliegue: automático, sin superficie pública nueva, sin setup por-proyecto en cada repo, y **outbound** (no exige que el remoto alcance la plataforma).
- **Webhook receiver de push → GATED, no se implementa aquí.** Aunque la infra de firma GitHub/GitLab ya existe y lo abarataría, encajar un evento `push` en el modelo `action_mappings` (cerrado a crear/comentar/escalar tareas, `actions.py:9-20`) es un feature nuevo con su propia decisión de producto (¿nueva `WebhookActionKind.git_sync`? ¿endpoint dedicado? ¿cómo se mapea el repo del payload al proyecto/bare?). Además, en el modelo **Docker Compose single-machine** (`CLAUDE.md`) la plataforma puede no ser **alcanzable desde el remoto** (NAT/firewall de una máquina interna), lo que hace del webhook un mecanismo estructuralmente menos fiable que el poll outbound del beat. Se difiere; la infra de firma queda lista para el día que se decida.

## Opciones evaluadas

### Eje 1 — Timing/default del push al remoto

| Opción                                                                   | Pros                                                                                                                                                                                | Contras                                                                                                                                                                                   |
| ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`incremental` default, cableado best-effort (recomendada)**            | No contradice ADR 0072/0085; rama visible en el remoto desde la 1ª tarea (transparencia, CI incremental del remoto, colaboración); best-effort no bloquea la tarea si el push falla | N pushes autenticados por plan (más superficie de fallo transitorio); expone commits WIP/`wip(escalated)` al remoto antes de la validación humana                                         |
| **`final_only` como nuevo default**                                      | Un solo push al cierre, tras validación; no filtra WIP; menos carga de red                                                                                                          | Contradice el default de dos ADR `accepted`; la rama no existe en el remoto hasta el cierre (sin CI incremental); si el plan nunca cierra, el trabajo nunca sube                          |
| **Push síncrono y fatal (bloquear la tarea si falla el push al remoto)** | Garantiza que el remoto refleja siempre el bare                                                                                                                                     | Acopla el avance del plan a la disponibilidad del remoto; un fallo de red bloquearía tareas cuyo trabajo ya está durable en el bare — frágil, viola el rol del bare como fuente de verdad |

### Eje 2 — «Merge directo a la rama base»

| Opción                                                         | Pros                                                                                                                                                              | Contras                                                                                                                                                                                                          |
| -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Retirar de la UI, gated a diseño futuro (recomendada)**      | Elimina un botón que no hace nada (P4); cero cambio de comportamiento observable (ya se comporta como pr_required); mantiene el enum para compatibilidad de filas | El merge directo real queda pendiente para quien lo necesite (mitigable: `branch_only_pr_required` + merge manual del PR cubre el caso hoy)                                                                      |
| **Cablear fast-forward local + push del default al remoto**    | Cierra el ciclo sin intervención                                                                                                                                  | Auto-merge a `main` **sin PR ni revisión** contradice el principio 5 y el gate de validación humana (principio 11); falla si el default divergió (no fast-forward); solo aplica un subconjunto estrecho de casos |
| **Reinterpretar como auto-merge del PR vía API del proveedor** | Respeta las protecciones de rama del remoto; deja traza en el PR; más seguro que el update-ref crudo                                                              | Depende de permisos del PAT y de que no haya required-reviews; es un feature nuevo (no lo que `apply_push_policy` hace); merece su propio diseño                                                                 |

### Eje 3 — Re-sync del remoto

| Opción                                                                | Pros                                                                                                                                           | Contras                                                                                                                                                                                                                                            |
| --------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Botón manual «Sincronizar» (mínimo, ahora)**                        | Cero superficie pública; trivial; cubre «acabo de mergear, resincroniza»                                                                       | Manual; el bare puede quedar stale entre sincronizaciones                                                                                                                                                                                          |
| **Beat periódico configurable (automático por defecto, recomendada)** | Automático; sin setup por-proyecto; **outbound** (robusto en single-machine); patrón probado (price_sync/backup/fx) con kill-switch + cadencia | Poll: la mayoría de fetches son no-ops; coste crece con nº de proyectos (acotado con cadencia conservadora); latencia hasta 1 tick                                                                                                                 |
| **Webhook receiver de push con firma (gated)**                        | Push (fresco al instante, cero waste); reutiliza la infra HMAC GitHub/GitLab ya construida; multi-tenant/RLS/rate-limit resueltos              | Exige que el remoto **alcance** la plataforma (dudoso en single-machine tras NAT); setup manual del webhook por-repo; requiere un nuevo tipo de acción fuera del catálogo cerrado `create_task/comment/escalate`; es un feature de producto propio |

## Consecuencias

Si se acepta, **`cadena-pr-plan` lo implementa** así (este ADR fija la política; el plan, la mecánica):

- **T3 (push incremental)**: cablea `push_branch_to_remote` según `branch_push_mode`; el push al remoto pasa a ser **best-effort no bloqueante** (nuevo contrato de este ADR) — se distingue del commit worktree→bare, que sigue siendo fatal.
- **T5 (merge directo)**: se retira `direct_to_default_allowed` de `git-config-section.tsx`; `apply_push_policy` se elimina o se marca como no-usado con test; filas persistidas con ese valor se tratan como `branch_only_pr_required` (**sin migración de datos**, sin cambio observable).
- **T6 (re-sync)**: `POST /projects/{id}/git/sync` + `enqueue_fetch_remote` + docstring de `fetch_remote` corregido.
- **Nuevo respecto al plan (lo aprueba este ADR):** entrada de **beat periódico** de fetch en `build_beat_schedule` con `WORKERS_GIT_FETCH_CRON` (default cada 6 h) + platform setting `git_fetch_enabled` (default OFF), best-effort, pinned a `default`, solo proyectos con `remote_url`. Multi-tenancy: el sweep itera proyectos en un sessionmaker admin y hace un `git fetch` sobre el bare de cada uno (operación de filesystem, sin datos cross-tenant); el secreto se resuelve por-proyecto desde Vault como en `clone_project_repo`.
- **Gated (no se implementan aquí):** merge directo real (eje 2) y webhook receiver de push (eje 3), ambos con su decisión de producto pendiente. El **visor de diffs y el flujo de conflictos** (P7) es el ADR hermano **0099**.

**Riesgos y mitigaciones:** (a) el push incremental filtra WIP al remoto → mitigado por `final_only` documentado para «Cliente Externo»; (b) N pushes/fetches autenticados → best-effort + cadencia conservadora + `--prune` incremental (barato); (c) retirar la opción de UI podría sorprender a quien la haya seleccionado → mensaje de release notes + comportamiento idéntico al actual (no rompe nada).

## Criterio de aceptación

1. **Push (eje 1):** e2e de `cadena-pr-plan` T9 con remoto fake → con `incremental`, tras aceptar una tarea la rama **existe en `origin`**; con `final_only` **no**, hasta el cierre. Un fallo simulado del push al remoto **no** marca la tarea `commit_failed` (best-effort verificado por test).
2. **Merge directo (eje 2):** la opción `direct_to_default_allowed` **no aparece** en la UI; test de que `apply_push_policy` no es código muerto (tiene caller o se ha retirado); una fila persistida con ese valor se comporta como `branch_only_pr_required`.
3. **Re-sync (eje 3):** `POST /projects/{id}/git/sync` encola el fetch y actualiza el bare; el docstring de `fetch_remote` ya no menciona beat/webhook inexistentes; si se activa el beat, existe la entrada en `build_beat_schedule` con su cron configurable + kill-switch y un test de cadencia (patrón `price_sync`); el webhook receiver de push queda **documentado como gated** (no implementado).
4. El ADR es coherente con los principios de `CLAUDE.md` (multi-tenancy en el sweep, el worker —no el sandbox— hace git, single-machine, catálogo de providers ADR 0021 intacto) y no contradice ningún ADR `accepted` (0072, 0085).
