# Plan 06.15 — tests humanos

Esta guía cubre los **2 tests humanos** del Plan 06.15 (asignación de
tools por agente — básicas/avanzadas, UI + enforcement). Validan lo que
los e2e Playwright escritos pero no ejecutados no cubren: que un
**Tenant Admin asigna un subconjunto de tools a un agente desde la UI**,
que el **runtime respeta esa asignación** (una tool no asignada se
rechaza, quitar todas restaura el comportamiento por defecto) y que el
**aislamiento de scope** se cumple (no se asigna una custom tool de otro
tenant; las MCP dependen del proyecto).

> (`task_06_15_01`..`task_06_15_05`) están en verde (endpoints

> enforcement backward-compatible en `agent-runtime`, sección "Tools del
> agente" en el editor con pestañas Básicas/Avanzadas, enlace al
> diagnóstico, ADR + guía + changelog). El e2e
> `agent-tools-assign.spec.ts` está escrito pero NO ejecutado — estos 2
> tests humanos son el último paso antes de pasar a `completed`.

## TL;DR

No hay `setup_demo_06_15.py` ni launcher dedicado para este plan. Los
tests reutilizan los agentes/proyectos que ya tengas seedeados (p. ej.
los de `setup_demo_06_8.py` / `setup_demo_06_9.py`). El setup es manual:

```powershell
.\scripts\dev\up.ps1                                     # api-server :8001 + admin-panel :3000 + postgres + redis
.\.venv\Scripts\python.exe -m api_server.seeds           # built-in tools (incl. file/git/run_*) + agentes built-in
.\.venv\Scripts\python.exe scripts\setup_demo_06_9.py    # (opcional) 1 agente template + 2 proyectos para tener sujetos
```

La pantalla nueva (sección dentro del editor de agente) y la vista de
diagnóstico (read-only) donde se contrasta lo asignado:

```
http://localhost:3000/admin/agents/<agent_id>                              # sección "Tools del agente": pestañas Básicas / Avanzadas
http://localhost:3000/admin/projects/<project_id>/agent-tools-diagnostic   # diagnóstico read-only del toolset resuelto
```

La asignación se persiste en la junction `agent_tools` vía
`PUT /agents/{id}/tools` (escritura `tenant_admin`, lectura
`tenant_user`). El frontend NO es la fuente de verdad: la restricción
real se aplica en el `ToolRegistry` del runtime.

## `human_06_15_01` — Asignar tools a un agente desde la UI y verificar enforcement

**Qué prueba**: como `tenant_admin` se abre la sección "Tools del
agente", se asigna un subconjunto (p. ej. solo `file` + `git`) y se
guarda; el diagnóstico refleja exactamente esas tools; al ejecutar una
tarea con ese agente solo puede usar las asignadas (una no asignada es
rechazada); quitar todas las asignaciones devuelve al agente al
comportamiento por defecto; y como `tenant_user` la sección es
read-only.

**Precondiciones**:

- Login como `tenant_admin`.
- Un agente **project-scoped** del tenant (no `global_builtin`) con un
  proyecto donde ejecutar una tarea.
- Saber qué tools tiene disponibles (Básicas builtin + cualquier custom/
  MCP del proyecto).

**Pasos**:

1. Como `tenant_admin`, ve a `/admin/agents/<agent_id>` y baja a la
   sección **"Tools del agente"**. Verás dos pestañas:
   - **Básicas** (builtin: file / git / runtime / network — `is_builtin=true`).
   - **Avanzadas** (custom del tenant + MCP + ejecutores http/python/docker).
   - Cada tool muestra un badge de `security_level`
     (safe/sandboxed/privileged) y otro de `implementation_type`.
2. **Asigna un subconjunto**: marca solo `file` + `git` (en Básicas),
   deja el resto sin marcar, y **Guarda** (`PUT /agents/{id}/tools`).
3. Abre el **diagnóstico** del proyecto del agente:
   `/admin/projects/<project_id>/agent-tools-diagnostic`. El toolset
   resuelto del agente debe listar **exactamente** `file` + `git` (y
   nada más).
4. **Ejecuta una tarea** con ese agente. En la traza/logs del
   agent-runtime el agente solo puede invocar `file`/`git`; si intenta
   una tool **no asignada** (p. ej. una de red), `ToolRegistry.call` la
   **rechaza** (no aparece en su toolset resuelto).
5. Vuelve a la sección "Tools del agente" y **quita TODAS** las
   asignaciones (deja 0 marcadas) y Guarda. El agente vuelve al
   **comportamiento por defecto** (sin restricción por agente — no se
   rompe, sigue ejecutando como antes del plan). El diagnóstico ya no
   muestra una lista filtrada por `agent_tools`.
6. Cierra sesión y entra como **`tenant_user`**: en
   `/admin/agents/<agent_id>` la sección "Tools del agente" se muestra
   en **solo-lectura** (sin checkboxes editables / sin botón Guardar).

**Resultado esperado**: la asignación se guarda y el diagnóstico la
refleja; el runtime solo permite las tools asignadas y rechaza las
demás; quitar todas restaura el comportamiento por defecto; el
`tenant_user` solo ve, no edita.

**Checklist**:

- [ ] Como `tenant_admin`, en `/admin/agents/[id]` abrir "Tools del
      agente" → ver pestañas Básicas / Avanzadas (con badges
      `security_level` + `implementation_type`).
- [ ] Asignar un subconjunto (p. ej. solo `file` + `git`) y guardar
      funciona.
- [ ] El diagnóstico (`agent-tools-diagnostic`) refleja exactamente esas
      tools.
- [ ] Ejecutar una tarea con ese agente → solo puede usar las tools
      asignadas (una no asignada es rechazada).
- [ ] Quitar todas las asignaciones → el agente vuelve al comportamiento
      por defecto (no se rompe).
- [ ] Como `tenant_user` (no admin) → la sección es de solo-lectura.

**Pitfalls conocidos**:

- **Enforcement backward-compatible**: sin filas en `agent_tools` el
  agente NO está restringido por agente (comportamiento previo al plan).
  Por eso el step 5 (quitar todo) NO debe romper el agente — si lo
  hace, es un bug del fallback.
- Los agentes `global_builtin` son **read-only** en esta sección por
  diseño (no se les asigna tools desde el tenant). Usa un agente
  project-scoped o un fork.
- Si el diagnóstico no refleja el cambio, F5 — el cache de TanStack
  puede mostrar el toolset anterior un instante tras guardar.
- La restricción real vive en el `ToolRegistry` del runtime; ver los
  botones en la UI no garantiza el enforcement: el step 4 (ejecutar una
  tarea) es el que lo valida de verdad.

## `human_06_15_02` — Aislamiento de scope

**Qué prueba**: no se puede asignar a un agente una custom tool de
**otro tenant**; las **builtin** aparecen para cualquier agente; las
**MCP** solo aparecen si el proyecto del agente tiene ese MCP server.

**Precondiciones**:

- Login como `tenant_admin`.
- Una **custom tool** existente en otro tenant (para verificar que NO
  es asignable desde este).
- Un proyecto **con** un MCP server y otro **sin** él (o el mismo MCP
  server añadido/quitado) para contrastar la pestaña Avanzadas.

**Pasos**:

1. Como `tenant_admin`, abre "Tools del agente" de un agente del tenant.
   En la pestaña **Básicas** verifica que las tools **builtin**
   (`is_builtin=true`, PLATFORM_TENANT_ID) aparecen **siempre**, sea
   cual sea el agente.
2. En la pestaña **Avanzadas**, comprueba que **solo** aparecen las
   custom tools **de tu propio tenant** y las **MCP del proyecto** del
   agente. Una custom tool que vive en **otro tenant** **no** aparece en
   la lista (y un `PUT /agents/{id}/tools` que la incluya es rechazado
   por validación de scope).
3. Añade un **MCP server** al proyecto del agente y recarga la sección:
   sus tools MCP aparecen ahora en **Avanzadas**. Quita el MCP server
   del proyecto → esas tools MCP **dejan de aparecer** como asignables.
4. (Opcional, vía curl) intenta forzar la asignación de una custom tool
   de otro tenant:
   ```bash
   curl -sS -X PUT "http://localhost:8001/agents/<agent_id>/tools" \
     -H "Authorization: Bearer $TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"tool_ids":["<custom_tool_id_de_otro_tenant>"]}'
   # → 4xx: la tool no es asignable (fuera de scope del tenant/proyecto)
   ```

**Resultado esperado**: builtin siempre disponibles; custom solo del
propio tenant; MCP solo si el proyecto tiene el server; un intento
cross-tenant es rechazado.

**Checklist**:

- [ ] No se puede asignar a un agente una custom tool de otro tenant
      (no aparece en Avanzadas; el `PUT` que la incluya es rechazado).
- [ ] Las builtin aparecen para cualquier agente (pestaña Básicas).
- [ ] Las MCP solo aparecen si el proyecto del agente tiene ese MCP
      server (añadir/quitar el MCP server lo refleja).

**Pitfalls conocidos**:

- El scope se valida en el backend (`PUT /agents/{id}/tools`), no solo
  en la UI: aunque la lista del frontend ya filtra, el step 4 confirma
  que el rechazo es del servidor, no cosmético.
- Las tools MCP dependen de los **MCP servers del proyecto**, no del
  tenant entero: un agente template sin proyecto puede no mostrar
  ninguna tool MCP — eso es esperado, no un fallo.
- Si una custom tool de tu propio tenant no aparece, comprueba que está
  en el catálogo `/tools` del tenant correcto (el picker del system_admin
  puede tenerte en otro tenant).

## Troubleshooting

| Síntoma                                        | Causa probable                                               | Fix                                                           |
| ---------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------- |
| La sección "Tools del agente" no aparece       | El agente es `global_builtin` (read-only) o no cargó         | Usa un agente project-scoped / fork; F5 si el detail no cargó |
| Guardar da 403                                 | El usuario es `tenant_user` (la escritura es `tenant_admin`) | Login como `tenant_admin`                                     |
| El diagnóstico no refleja la asignación        | Cache de TanStack con el toolset anterior                    | F5; el diagnóstico re-resuelve el toolset desde `agent_tools` |
| El agente sigue usando una tool no asignada    | El agente no tenía filas `agent_tools` (backward-compat)     | Asigna al menos una tool para activar el filtrado por agente  |
| Una custom tool propia no aparece en Avanzadas | Estás en otro tenant (picker del system_admin)               | Cambia al tenant dueño de la tool; verifica `/tools`          |
| Una tool MCP no aparece                        | El proyecto del agente no tiene ese MCP server               | Añade el MCP server al proyecto; recarga la sección           |

Errores transversales viven en `docs/03-guides/gotchas/`.
