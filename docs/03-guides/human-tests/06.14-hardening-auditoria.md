# Plan 06.14 — tests humanos (hardening de seguridad)

Guía de pruebas humanas para el plan 06.14. Se va **ampliando a medida que
se implementan tareas**; hoy cubre los 3 críticos P0 (`task_06_14_01/02/03`),
la robustez de Celery (`task_06_14_04`), la atomicidad del dispatch +
dead-letter del consumer del orchestrator (`task_06_14_05`), el manejo de
errores de streaming LLM (`task_06_14_06`), el enforcement de `allowed_tools`
en tiempo de tool-call (`task_06_14_07`), el aislamiento por owner-pointer al
fusionar/listar memorias (`task_06_14_08`), la revocación del token de agente
cuando se borra (soft-delete) su proyecto (`task_06_14_09`) y el
request-context en logs + handler global de excepciones + saneo del
`IntegrityError` de KB (`task_06_14_10`), el hardening de los contenedores
auxiliares del test-runtime + DinD proxy + pin de la imagen MinIO
(`task_06_14_11`) y la validación de args MCP contra su `input_schema` + el cap
de tamaño del output del tool (`task_06_14_12`), la paginación
(`limit`/`offset`) en los endpoints de listado (`task_06_14_13`) y el Error
Boundary del admin-panel + el acotado de CORS (`allow_methods`/`allow_headers`

## `human_06_14_01` — WebSocket rechaza suscripción cross-tenant

**Qué prueba**: un miembro del tenant A no puede tailear streams del tenant B
(ejecuciones, kanban, conversaciones, ingesta de documentos), y un logout
corta los sockets vivos.

**Cómo ejecutarlo**:

1. Login como `tenant_admin` de **A**. En DevTools copia el JWT (de
   `localStorage`, clave del token).
2. En el tenant **B**, crea/abre una ejecución y copia su `execution_id` de la
   URL (`/admin/executions/<id>`).
3. Con el token de **A**, abre el WS de la ejecución de **B**:
   ```
   websocat "ws://localhost:8000/ws/executions/<execution_id_de_B>?token=<JWT_de_A>"
   ```
   **Verifica**: el socket se **cierra de inmediato con código 1008** (no
   recibes ningún evento).
4. Repite con `/ws/kanban/<project_id_de_B>`, `/ws/conversation/<id_de_B>` y
   `/ws/documents/<id_de_B>` → todos cierran `1008`.
5. **Caso feliz**: con el token de **A** sobre un recurso **de A** → el socket
   queda abierto y recibe el backlog + el tail en vivo.
6. **Revocación**: con un WS de A abierto y funcionando, haz **logout** en la
   UI (revoca la sesión en Redis). **Verifica**: al siguiente intento de
   reconexión el socket se cierra `1008` (la sesión revocada ya no vale).

✅ Pasa si todos los cross-tenant cierran 1008 y el propio tenant streamea.

## `human_06_14_02` — Arranque seguro: secretos dev rechazados en prod

**Qué prueba**: api-server / workers / orchestrator **no arrancan** en
`staging`/`prod` si conservan un secreto por defecto de desarrollo.

**Cómo ejecutarlo** (PowerShell):

1. Intenta arrancar la api-server simulando prod con el secreto dev:
   ```powershell
   $env:API_SERVER_ENVIRONMENT = "prod"   # deja JWT/MinIO/DB en sus defaults
   .\.venv\Scripts\python.exe -c "from api_server.config import get_settings; get_settings()"
   ```
   **Verifica**: lanza `ValidationError` enumerando los settings con default dev
   (`API_SERVER_JWT_SECRET`, `API_SERVER_MINIO_*`, `*_DATABASE_URL`).
2. Da valores reales y confirma que arranca:
   ```powershell
   $env:API_SERVER_JWT_SECRET = "una-clave-larga-y-aleatoria-de-verdad-xxxxx"
   $env:API_SERVER_MINIO_ACCESS_KEY = "prod-key"; $env:API_SERVER_MINIO_SECRET_KEY = "prod-secret-xxxx"
   $env:API_SERVER_DATABASE_URL = "postgresql+asyncpg://app:realpass@db/agentic"
   $env:API_SERVER_ADMIN_DATABASE_URL = "postgresql+asyncpg://mig:realpass@db/agentic"
   .\.venv\Scripts\python.exe -c "from api_server.config import get_settings; get_settings(); print('OK')"
   ```
   **Verifica**: imprime `OK`.
3. Repite el paso 1 con `WORKERS_ENVIRONMENT=prod` y `ORCHESTRATOR_ENVIRONMENT=prod`

4. **En dev** (`API_SERVER_ENVIRONMENT=dev` o sin setear) los defaults se
   aceptan sin error (no rompe el flujo local).

✅ Pasa si prod/staging falla con defaults dev y arranca con secretos reales,
y dev sigue cómodo.

## `human_06_14_03` — El worker rechaza ejecuciones cross-tenant

**Qué prueba**: un mensaje Celery que empareja un tenant con la tarea de otro
tenant no ejecuta nada y queda registrado en la cola de fallidos.

**Cómo ejecutarlo**:

1. Identifica una `task_id` real del tenant **A** (de su kanban).
2. Encola `workers.run_execution` con `tenant_id` del tenant **B** y la
   `task_id` de **A** (vía un script con el broker de dev, o forzando un
   payload manipulado).
3. **Verifica** en los logs del worker: `workers.cross_tenant_execution_rejected`
   y la tarea Celery marcada como fallida (sin lanzar contenedor).
4. **Verifica**: la stream Redis `dlq:executions` tiene una entrada con
   `task=workers.run_execution`, el `task_id` y el error `CrossTenantExecutionError`:
   ```powershell
   redis-cli -n 0 XRANGE dlq:executions - +
   ```
5. **Verifica**: NO se creó ninguna fila `executions` atribuida al tenant B.

✅ Pasa si el run se rechaza, no se crea execution, y aparece en `dlq:executions`.

## `human_06_14_04` — Robustez de ejecuciones (idempotencia + límites)

**Qué prueba**: un reintento tras caída del worker no duplica ejecuciones
vivas, y el límite de tiempo de `run_execution` es configurable por el operador.

**Cómo ejecutarlo**:

1. **Idempotencia**: lanza una ejecución larga y **mata el worker** a mitad
   (`taskkill /F` del proceso) — `task_acks_late` re-entrega el job. Al
   re-ejecutar, **verifica** en la tabla `executions` que la tarea tiene **una
   sola fila `running`**; la del intento caído quedó `failed` con
   `abort_code='superseded'` (log `workers.superseded_stale_executions`).
2. **Límite configurable**: como System Admin, fija el límite de tiempo por
   plataforma (sin reiniciar workers):
   ```sql
   INSERT INTO platform_settings (key, value) VALUES
     ('execution_soft_time_limit_s', '120'), ('execution_hard_time_limit_s', '180')
   ON CONFLICT (key) DO UPDATE SET value = EXCLUDED.value;
   ```
   Dispara una ejecución que tarde > 120 s. **Verifica**: el run recibe
   `SoftTimeLimitExceeded` (o se mata en 180 s) — el nuevo límite aplica a la
   siguiente ejecución despachada sin reiniciar nada.
3. (Cuando exista el formulario de platform-settings en la UI, este paso 2 se
   hará desde **Admin → Settings** en lugar del SQL — ver nota en el plan.)

✅ Pasa si no hay ejecuciones `running` duplicadas y el límite operador-fijado
se respeta en caliente.

## `human_06_14_05` — Atomicidad del dispatch + dead-letter del consumer

**Qué prueba**: si el broker se cae al encolar, la task no queda
`in_progress` huérfana (vuelve a `ready` y se re-despacha); y un evento cuyo
handler falla se conserva en `dlq:orchestrator_events` en lugar de perderse al
hacer ACK.

**Cómo ejecutarlo**:

1. **Revert-on-failure del dispatch**: con el stack arriba, identifica una
   task en estado `ready` de un proyecto con agente disponible (su kanban).
2. **Tira el broker Celery** (mismo Redis del broker, DB 1 por defecto): por
   ejemplo `docker stop agentic-platform-redis-1` justo antes de que el
   orchestrator despache esa task (o pausa la cola), de modo que el
   `send_task` falle.
3. Dispara la transición de la task a `ready` (re-encólala / cambia su estado
   para emitir el evento). **Verifica** en los logs del orchestrator
   `orchestrator.dispatch_enqueue_failed` con el `task_id`.
4. **Verifica** en la BD que la task **NO** quedó `in_progress` huérfana:
   ```sql
   SELECT status, assigned_agent_id, started_at FROM tasks WHERE id = '<task_id>';
   ```
   Debe estar `status='ready'`, `assigned_agent_id IS NULL`, `started_at IS NULL`.
5. **Re-despacho**: vuelve a levantar el broker (`docker start ...redis-1`) y
   re-dispara el evento `ready`. **Verifica**: ahora sí pasa a `in_progress`
   con su agente y se encola `workers.run_execution` (la task no se perdió).
6. **Dead-letter del consumer**: provoca un fallo del handler de dispatch (p.
   ej. con un proyecto sin ningún agente elegible que haga fallar la
   asignación, o forzando un error transitorio de BD). **Verifica** que el
   evento aparece en la stream de fallidos:
   ```powershell
   redis-cli -n 15 XRANGE dlq:orchestrator_events - +   # DB 15 en tests; 0 en dev
   ```
   La entrada lleva `entry_id`, `type`, `task_id`, `tenant_id`, `error` y
   `failed_at_unix`. El grupo de consumo **no queda atascado** (el evento se
   ACK-ea tras dead-letterarse: `XPENDING events:tasks orchestrator` → 0
   pendientes).

✅ Pasa si: (a) el fallo de broker deja la task en `ready` (no `in_progress`)
y se re-despacha al recuperar el broker; (b) un handler que falla deja el
evento en `dlq:orchestrator_events` con su contexto y sin atascar el grupo.

## `human_06_14_06` — Streaming LLM: errores tipados + 401/403 + retry Copilot

**Qué prueba**: un corte de red **a mitad** de un stream LLM ya no escapa como
error crudo de `httpx`, sino como `ProviderError` de la capa; un `401` y un
`403` se clasifican distinto (`AuthError` vs `ProviderError`); y
`CopilotProvider.stream()` reintenta una vez ante un `401` re-acuñando el JWT
(igual que `complete()`). Es lógica de la capa `shared-llm` sin red real: se
valida con transports mock desde el REPL.

**Cómo ejecutarlo** (PowerShell, desde la raíz del repo):

1. **Corte de red a mitad de stream → `ProviderError`**:

   ```powershell
   .\.venv\Scripts\python.exe -c @'
   import asyncio, httpx
   from shared_llm.providers import OllamaProvider
   from shared_llm.exceptions import ProviderError
   from shared_llm.types import Message

   class Raising(httpx.AsyncByteStream):
       async def __aiter__(self):
           yield b'data: {\"choices\":[{\"delta\":{\"content\":\"hola\"}}]}\n\n'
           raise httpx.ReadError(\"conexion caida\")
       async def aclose(self): ...

   def handler(req):
       return httpx.Response(200, headers={\"Content-Type\":\"text/event-stream\"}, stream=Raising())

   async def main():
       p = OllamaProvider.local(http_client=httpx.AsyncClient(transport=httpx.MockTransport(handler)))
       got = []
       try:
           async for c in p.stream([Message(role=\"user\", content=\"hi\")]):
               if c.delta: got.append(c.delta)
       except ProviderError as e:
           print(\"OK ProviderError:\", e); print(\"deltas previos:\", got); return
       print(\"FALLO: no se elevo ProviderError\")
   asyncio.run(main())
   '@
   ```

   **Verifica**: imprime `OK ProviderError: ... stream interrupted ...` y
   `deltas previos: ['hola']` (lo recibido antes del corte se entregó; el error
   posterior llega tipado, no como `httpx.ReadError`).

2. **401 vs 403** (clasificación): repite el script cambiando el `handler` por
   `return httpx.Response(401, text="bad key")` → debe elevar **`AuthError`**;
   y por `return httpx.Response(403, text="forbidden")` → debe elevar
   **`ProviderError`** con `status_code == 403` y **no** ser `AuthError`.

3. **Retry 401 de Copilot en `stream()`**: arranca el agent-runtime / un agente
   configurado con el proveedor **GitHub Copilot** y lanza una conversación en
   streaming dejando expirar el JWT (o reutilizando un JWT viejo). **Verifica**
   en los logs que ante el primer `401` la respuesta **no** falla: se re-acuña
   el JWT (segunda llamada a `/copilot_internal/v2/token`) y el stream continúa.
   Un `401` persistente (token de GitHub inválido) sí termina en `AuthError`
   tras **un único** reintento (no entra en bucle).

✅ Pasa si: (a) el corte a mitad de stream llega como `ProviderError`; (b) 401
da `AuthError` y 403 da `ProviderError`; (c) el stream de Copilot sobrevive a un
401 transitorio re-acuñando el JWT una sola vez.

> **Nota llm-providers-1**: se investigó la firma `def stream(...) -> AsyncIterator`
> del `Protocol` en `base.py`. Es el tipado **correcto** de un método
> async-generator (no debe ser `async def`, que forzaría `await` antes de
> iterar y rompería todos los call sites). `mypy --strict` pasa sin cambios, así
> que se deja como está; no es un hallazgo accionable.

## `human_06_14_07` — `allowed_tools` se aplica en tiempo de tool-call

**Qué prueba**: la lista `allowed_tools` de un modo de chat deja de ser un
comentario engañoso ("se aplica en la capa pre_tool") y pasa a ser un
**allowlist real**: el `ToolRegistry` del agent-runtime rechaza cualquier
herramienta fuera del conjunto **antes** de ejecutarla. La lista viaja del
worker al runtime en el `AGENT_TASK_SPEC` (clave `allowed_tools`). El motor de
guardrails por capas completo sigue siendo Plan 11 (fuera de alcance).

**Cómo ejecutarlo** (PowerShell, desde la raíz del repo; no requiere stack):

1. **Herramienta fuera del allowlist → bloqueada**: ejecuta el runtime con un
   spec que permite solo `noop` pero el modelo intenta `echo`:

   ```powershell
   $env:AGENT_TASK_SPEC = @'
   {"task":{"id":"t1","title":"probar allowlist","description":""},
    "allowed_tools":["noop"],
    "model":{"kind":"scripted","decisions":[
       {"kind":"act","tool":"echo","tool_args":{"text":"go"}},
       {"kind":"finish","output":"done"}]}}
   '@
   .\.venv\Scripts\python.exe -m agent_runtime
   ```

   **Verifica**: entre las líneas JSON emitidas, el paso `act` sale con
   `"status":"error"` y `result.error == "tool 'echo' not allowed in this mode"`
   (la función de `echo` **no** llegó a ejecutarse).

2. **Herramienta dentro del allowlist → corre**: repite cambiando el `tool` del
   primer decision de `"echo"` a `"noop"`. **Verifica**: el paso `act` sale
   `"status":"ok"` y la ejecución termina `done`.

3. **Lista vacía (modo `discussion`) bloquea todo**: pon `"allowed_tools":[]` y
   deja `echo` en el decision. **Verifica**: `act` vuelve a salir `error` con el
   mismo mensaje (lista vacía = ninguna herramienta permitida, NO "sin
   restricción").

4. **Sin la clave `allowed_tools` → sin restricción**: borra la clave del spec.
   **Verifica**: `echo` corre normal (compatibilidad hacia atrás: ausencia de
   allowlist = todo permitido).

5. **Cross-tenant (opcional, con BD dev)**: si el tenant A define un modo custom
   `team-mode` que permite `echo` y el tenant B define `team-mode` permitiendo
   solo `noop`, una ejecución del tenant B debe usar el allowlist de **B**:
   `echo` queda denegado aunque A lo permita (cubierto por el test automático
   `cross_tenant`).

✅ Pasa si: una herramienta fuera del allowlist se rechaza con el mensaje
`tool '<x>' not allowed in this mode` sin ejecutarse; una dentro corre; lista
vacía bloquea todo; ausencia de la clave no restringe; y el allowlist de un
tenant no se filtra a otro.

> **Nota guardrails-1**: el arreglo en alcance es el allowlist ligero en
> tiempo de tool-call (`ToolRegistry.set_allowed_tools` + check en `call()`) más
> la corrección de los comentarios engañosos en `chat/modes.py` y
> `db/custom_chat_mode.py`. El motor declarativo por capas (pre_llm / post_llm /
> pre_tool / post_tool) es Plan 11.

## `human_06_14_08` — Fusión/listado de memorias no cruza owners

**Qué prueba**: el `POST /memories/{src}/merge-into` ya no fusiona dos memorias
del **mismo scope pero distinto owner** (proyecto A1 vs A2, team A1 vs A2,
usuario U vs V), porque eso filtraría el contenido de un owner dentro de otro
dentro del mismo tenant (RLS solo aísla por `tenant_id`). Mismo arreglo en
`GET /memories/{id}/similar`: ya no devuelve candidatos de otro owner.

**Cómo ejecutarlo** (UI o API, con stack dev arriba; un solo tenant basta para
los pasos 1-4; el paso 5 es cross-tenant):

1. Como miembro del tenant **A**, crea dos memorias `project_shared` del **mismo
   proyecto** P1 (en la UI de Memorias o vía `POST /memories` con
   `scope=project_shared`, `project_id=<P1>`). Funde la primera en la segunda
   (`merge-into`). **Verifica**: responde **200** y el contenido de la fuente
   queda concatenado en el destino (separador `\n\n---\n`); la fuente queda
   soft-deleted.
2. Crea ahora una memoria `project_shared` del proyecto **P2** (distinto).
   Intenta fundir la memoria de P1 en la de P2 (y al revés). **Verifica**: en
   ambos sentidos responde **422** con `detail` mencionando `project_id`, y el
   destino **no** cambia (no se filtró contenido del otro proyecto).
3. Repite con dos memorias `team_shared` de equipos distintos (→ **422**,
   `team_id`) y con dos `private` de usuarios distintos (→ **422**, `user_id`).
4. **Mismo owner sigue funcionando**: dos memorias `global` del tenant (sin
   owner pointer) **sí** se funden (**200**). Y `GET /memories/<id_P1>/similar`
   con `threshold=0` devuelve la otra memoria de **P1** pero **nunca** la de
   **P2**, aunque compartan embedding (mira que el `id` de P2 no aparezca en la
   lista de candidatos).
5. **Cross-tenant**: con el token de un miembro del tenant **B**, intenta
   `merge-into` usando un `id` de memoria del tenant **A** como fuente o
   destino, y `GET /memories/<id_de_A>/similar`. **Verifica**: ambos devuelven
   **404** (RLS oculta la fila; B nunca puede leer ni fundir memoria de A).

✅ Pasa si: fusionar/similar dentro del mismo owner funciona, distinto owner del
mismo scope da **422** sin tocar el destino, `global` se funde, y un tenant
ajeno recibe **404** sin ver la memoria.

> **Nota rag-memory-ingestion-2**: el mapeo scope→columna de owner vive en la
> constante `_SCOPE_OWNER_ATTR` de `routers/memories.py` (no es un tunable
> operativo; es el invariante del modelo de datos, espejo del CHECK
> `ck_memory_entries_scope_pointer`).

## `human_06_14_09` — Borrar un proyecto revoca el token de sus agentes

**Qué prueba**: el token de agente (`/internal/agent/*`, TTL 24 h) ya no sigue
sirviendo después de hacer **soft-delete** del proyecto al que pertenece el
agente. Antes solo se comprobaba que el `Agent` siguiera vivo; ahora, si el
agente está ligado a un proyecto (`scope=project_local`), se exige además que
ese `Project` exista y tenga `deleted_at IS NULL`. Los agentes globales (sin
`project_id`) no se ven afectados.

**Cómo ejecutarlo** (PowerShell, con stack dev arriba; `psql`/`asyncpg` para la
BD y `curl` para el endpoint smoke `/internal/agent/_health`):

1. Identifica un agente `project_local` vivo y su proyecto:
   ```sql
   SELECT a.id AS agent_id, a.tenant_id, a.project_id
   FROM agents a JOIN projects p ON p.id = a.project_id
   WHERE a.scope = 'project_local' AND a.deleted_at IS NULL AND p.deleted_at IS NULL
   LIMIT 1;
   ```
2. Acuña un token de agente para ese `agent_id`/`tenant_id` (REPL):
   ```powershell
   .\.venv\Scripts\python.exe -c @'
   from uuid import UUID
   from api_server.auth.internal_agent import mint_agent_token
   print(mint_agent_token(agent_id=UUID(\"<AGENT_ID>\"), tenant_id=UUID(\"<TENANT_ID>\")))
   '@
   ```
3. **Caso feliz**: llama al smoke endpoint con ese token →
   ```powershell
   curl -H "Authorization: Bearer <TOKEN>" http://localhost:8000/internal/agent/_health
   ```
   **Verifica**: responde **200** con `{"status":"ok","agent_id":...}`.
4. Haz **soft-delete** del proyecto (sin tocar el agente):
   ```sql
   UPDATE projects SET deleted_at = now() WHERE id = '<PROJECT_ID>';
   ```
5. Repite el `curl` del paso 3 con el **mismo token** (sigue firmado y sin
   expirar). **Verifica**: ahora responde **403** con `"agent not found or
revoked"` — el borrado del proyecto revoca el token al instante.
6. **Reversible**: restaura el proyecto y vuelve a llamar:
   ```sql
   UPDATE projects SET deleted_at = NULL WHERE id = '<PROJECT_ID>';
   ```
   **Verifica**: vuelve a **200** (el mismo token funciona de nuevo).
7. **Agente global no afectado** (opcional): repite con un agente
   `global_tenant_template` (`project_id IS NULL`). **Verifica**: sigue **200**
   pase lo que pase con los proyectos del tenant (no hay proyecto que validar).
8. **Cross-tenant** (cubierto por el test automático `cross_tenant`): borrar el
   proyecto del tenant **A** revoca solo a los agentes de **A**; el token de un
   agente del tenant **B** (otro proyecto, otro tenant) sigue dando **200**.

✅ Pasa si: con proyecto vivo el token da 200; tras soft-delete del proyecto el
mismo token da 403; al restaurar vuelve a 200; un agente global no se ve
afectado; y borrar el proyecto de A no toca a B.

> **Nota auth-rbac-casbin-5**: el chequeo vive en `_agent_exists`
> (`auth/internal_agent.py`) como un `LEFT JOIN` a `projects` por
> `(id, tenant_id)`; no hay tunable operativo, es un invariante de seguridad
> (proyecto borrado ⇒ token revocado).

## `human_06_14_10` — Request-id en logs, 500 genérico y 409 limpio de KB

**Qué prueba**: (a) cada petición lleva un `X-Request-ID` de correlación que se
propaga si viene de fuera o se acuña si no, y que aparece en cada línea de log;
(b) un error no controlado devuelve un **500 genérico** sin filtrar la
excepción ni el stack al cliente (pero sí se loguea entero en el servidor con su
`request_id`); (c) crear una KB con nombre duplicado en el tenant devuelve un
**409 limpio** sin filtrar `exc.orig` de SQLAlchemy.

**Cómo ejecutarlo** (PowerShell, con stack dev arriba; `curl` y los logs del
contenedor `api-server`):

1. **Request-id acuñado + en logs**: llama a un endpoint cualquiera sin enviar
   la cabecera:
   ```powershell
   curl -i http://localhost:8000/healthz
   ```
   **Verifica**: la respuesta trae una cabecera `X-Request-ID: <uuid>`. En los
   logs del api-server (`docker logs ... api-server`) la línea de esa petición
   lleva el mismo `request_id` (JSON estructurado).
2. **Request-id propagado**: repite enviando tu propio id:
   ```powershell
   curl -i -H "X-Request-ID: trace-humano-001" http://localhost:8000/healthz
   ```
