Esta guía cubre los **4 tests humanos** del Plan 06.9 (Agent-scoped
Knowledge Bases). Los cuatro son navegación UI guiada — no se pueden
automatizar porque exigen verificar que un cambio en un lugar se
refleja correctamente en otro (e.g. grant en agente → visible en
todos los proyectos donde corre).

> **Estado del plan**: `pending_human_validation`. Las 13 tareas y los
> 20 tests automáticos están en verde. Estos 4 humanos son el último
> paso antes de pasar a `completed`.

```powershell
.\scripts\dev\up.ps1                                     # primera vez
.\.venv\Scripts\python.exe -m api_server.seeds           # built-in agents/KBs
```

## `human_06_9_01` — KB de rol grant a agente template

**Qué prueba**: granting una KB al agente template hace que sea
visible en **todos los proyectos** donde el agente ejecuta, sin
necesidad de grantearla individualmente a cada proyecto. Y al revocar
del agente, desaparece de todos a la vez.

**Cómo ejecutarlo**:

1. Login con `admin-06-8@example.com`.
2. Sidebar → "Agentes" → buscar **`backend-dev-tenant`** → entrar al detail.
3. En el detail, debajo de la card principal, sección **"Knowledge Bases"**.
4. Click "**Grant KB**" → dialog con el `<KbCombobox>`.
5. Buscar "API REST" → seleccionar "API REST design principles" → "Asignar".
6. La KB aparece en el listado.
7. Sidebar → "Proyectos" → entrar al "Plan 06.9 demo — Proyecto Python".
   - Tab/Sección **"Knowledge Bases"** del proyecto: la KB del agente
     **NO** aparece aquí (es del agente, no del proyecto).
   - Pero en runtime el agente la verá — esto es la separación rol vs stack.
8. Repetir con "Plan 06.9 demo — Proyecto PHP" — mismo comportamiento.
9. Volver al detail del agente → click el icono de papelera junto a la
   KB → confirma revoke → la KB desaparece del agente.
10. Re-abrir el dialog "Grant KB" — la KB ya no aparece como granteada
    (se puede grantear de nuevo).

**Verificación cross-proyecto (vía curl, opcional)**:

```bash
# Token del admin (login con /auth/login).
# Listar las KBs del agente:
curl -sS "http://localhost:8001/agents/<agent_id>/knowledge-bases" \
  -H "Authorization: Bearer $TOKEN"
# → array con la KB tras el grant; vacío tras el revoke.
```

**Checklist**:

- [ ] El dialog "Grant KB" abre con el combobox + typeahead funciona.
- [ ] Tras grant, la KB aparece en el listado del agente.
- [ ] La KB NO aparece en la sección "KBs del proyecto" en NINGUNO de
      los dos proyectos (porque NO es un grant de proyecto).
- [ ] curl `GET /agents/{id}/knowledge-bases` con el token del
      admin devuelve la KB granteada.
- [ ] Revoke desde el agente vacía el listado.
- [ ] Re-grantear funciona (es idempotente — re-grant no crea
      duplicados).

**Pitfalls conocidos**:

- Si el `<KbCombobox>` muestra 0 resultados al teclear "API", verifica
  que la KB existe en este tenant (`GET /knowledge-bases` debe
  listarla). El seed la crea bajo `tenant-a`.
- La "vista runtime" del agente (que el agente ve la KB en el
  proyecto) **no es visible en la UI** — el chunk-level retrieval
  sólo se ejecuta cuando hay tareas reales corriendo. Verifica vía
  endpoint `POST /internal/agent/rag-search` desde un container o
  inspeccionando los logs del agent-runtime.

## `human_06_9_02` — Plantilla pre-grantea KBs de stack

**Qué prueba**: al crear un proyecto desde una plantilla built-in con
`default_kb_grants` no vacío, el backend aplica los grants automáticamente
sobre el nuevo proyecto.

> **Nota**: la wizard del Plan 03 (`/admin/projects/new`) tiene que
> llamar a `apply_template_kb_grants` después de crear el proyecto.
> Si la wizard aún no está cableada para esto (es follow-up del Plan
> 03), puedes ejecutar el flow vía SQL/curl: ver "Verificación manual"
> abajo.

**Cómo ejecutarlo (UI, asumiendo wizard cableada)**:

1. Sidebar → "Proyectos" → botón "Crear proyecto" → wizard
   `/admin/projects/new`.
2. Selecciona "**Plantilla: API REST**".
3. Completa los campos básicos (nombre, descripción) → Crear.
4. En el nuevo proyecto → sección "Knowledge Bases".
5. Deben aparecer **3 KBs** ya granteadas:
   - `python-fastapi-conventions`
   - `api-rest-guidelines`
   - `postgresql-best-practices`
6. Repite con "Plantilla: Webapp Full-Stack" → deben aparecer **4 KBs**
   (las anteriores + `react-nextjs-conventions`).
7. Crea un proyecto **"desde cero"** (sin seleccionar plantilla) → la
   sección KBs queda vacía.

**Verificación manual (si la wizard aún no aplica los grants)**:

```bash
# 1) Crea un proyecto fresco vía POST /projects.
PROJECT_ID=$(curl -sS -X POST http://localhost:8001/projects \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name":"test-api-rest-template","status":"active"}' \
  | jq -r '.id')

# 2) Aplica los grants del template a mano (Python REPL):
python -c "
import asyncio
from uuid import UUID
from sqlalchemy.ext.asyncio import create_async_engine, async_sessionmaker
from api_server.seeds.builtin_project_templates import _project_template_id
from api_server.seeds.template_adoption import apply_template_kb_grants

async def main():
    engine = create_async_engine('postgresql+asyncpg://migrations_user:changeme-migrations-dev-only@localhost:15432/agentic_platform')
    sm = async_sessionmaker(engine, expire_on_commit=False)
    async with sm() as session, session.begin():
        granted = await apply_template_kb_grants(
            session,
            template_id=_project_template_id('api-rest'),
            new_project_id=UUID('$PROJECT_ID'),
            tenant_id=UUID('019e4a6a-d6bc-7b30-aef2-41fc4d48e59f'),
        )
        print(f'grants: {[str(g) for g in granted]}')
    await engine.dispose()

asyncio.run(main())
"

# 3) Verifica:
curl -sS "http://localhost:8001/projects/$PROJECT_ID/knowledge-bases" \
  -H "Authorization: Bearer $TOKEN" | jq '. | length'
# → 3
```

**Checklist**:

- [ ] "Plantilla: API REST" deja 3 KBs granteadas al proyecto nuevo.
- [ ] "Plantilla: Webapp Full-Stack" deja 4 KBs.
- [ ] "Plantilla: Data Pipeline" deja 1 KB (`postgresql-best-practices`).
- [ ] "Plantilla: DevOps Bootstrap" deja **0** KBs (agnóstica de stack).
- [ ] Re-adoptar la misma plantilla a un proyecto que ya tenía los
      grants NO crea duplicados (composite PK).
- [ ] Un slug del template que NO existe en el catálogo (e.g. si re-
      seedeas borrando una KB) se ignora silenciosamente.

**Pitfalls conocidos**:

- Si los `default_kb_grants` están vacíos en la BD aunque la plantilla
  los declare, verifica que ejecutaste `python -m api_server.seeds`
  TRAS aplicar la migración 0027 (la migración añade la columna; el
  seed la rellena).
- La wizard del admin-panel (Plan 03 task_01_21) cablear este flow es
  follow-up. Hasta entonces el seed sólo deja el template con sus
  grants declarados; aplicar los grants al adoptar es manual o vía
  el helper.

## `human_06_9_03` — Panel "Asignaciones" desde la KB

**Qué prueba**: desde el detalle de una KB se pueden ver y revocar
todos sus grants (proyectos + agentes) sin saltar entre pantallas.

**Cómo ejecutarlo**:

1. Previo: tener al menos un proyecto + un agente con grants a la KB
   "API REST design principles". Si vienes del test 01, ya tienes el
   agente; usa también la verificación manual del test 02 o haz un
   grant manual al proyecto Python desde `/admin/projects/{id}`.
2. Sidebar → "Knowledge Bases" → buscar "API REST design principles".
3. Click el botón "**Asignaciones**" en la fila.
4. Dialog se abre con dos secciones:
   - **Proyectos**: lista los proyectos con grant.
   - **Agentes**: lista los agentes con grant (con su rol + scope).
5. Click el icono de papelera en uno de los proyectos → revoke.
6. La fila desaparece. Cierra el dialog, vuelve a abrirlo → no aparece.
7. Repite con un agente — mismo comportamiento.

**Checklist**:

- [ ] "Asignaciones" abre un dialog con las dos secciones.
- [ ] Las dos secciones muestran las filas correctas (proyectos con grant,
      agentes con grant).
- [ ] Cada agente muestra su `role` + `scope` (badges).
- [ ] Revoke de un proyecto desaparece la fila + revoca el grant
      (verificable: el proyecto ya no ve la KB en runtime).
- [ ] Revoke de un agente ídem.
- [ ] Si no hay grants → mensaje "Esta KB no está granteada a ningún
      proyecto ni agente todavía".

**Pitfalls conocidos**:

- El revoke desde el dialog requiere `tenant_admin`. Si lo intenta un
  `tenant_user`, el botón aparece pero la API responde 403. La UI no
  oculta el botón en este dialog específicamente — pendiente añadirle
  el `<RoleGuard>` si lo quieres más estricto.

## `human_06_9_04` — Built-in agent rechaza grant del tenant

**Qué prueba**: los agentes built-in (`scope=global_builtin`) NO
pueden recibir grants desde el tenant — ni desde la UI (el botón está
escondido) ni desde el API (403 con mensaje claro). Forkear el built-in
permite grantear sobre la copia.

**Cómo ejecutarlo**:

1. Sidebar → "Agentes" → buscar `project_manager` (scope `global_builtin`).
2. Entrar al detail. La sección "Knowledge Bases" se muestra **pero
   sin botón "Grant KB"** (read-only).
3. Si la KB siembra ya tuvo grants previos via seeds, los ves; si no,
   listado vacío con el mensaje informativo.
4. Verifica el backend desde curl:
   ```bash
   curl -sS -X POST "http://localhost:8001/agents/$BUILTIN_PM_ID/knowledge-bases" \
     -H "Authorization: Bearer $TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"kb_id":"<kb_uuid>"}'
   # → 403 {"detail":"cannot grant/revoke KBs on a global_builtin agent;
   #          fork it first and grant on the fork"}
   ```
5. **Forkear** el built-in:
   - En el detail del agente → botón "Hacer copia" (si está disponible
     en tu UI).
   - O via `POST /agents/{id}/fork`.
   - Resultado: una copia con `scope=global_tenant_template` y
     `forked_from_agent_id` apuntando al built-in.
6. Entra al detail del fork → tab KBs → **SÍ** ves el botón "Grant KB"
   y funciona normal.

**Checklist**:

- [ ] Detail de `project_manager` (built-in) **NO** muestra "Grant KB".
- [ ] `curl POST /agents/{builtin_id}/knowledge-bases` → **403** con
      mensaje "global_builtin".
- [ ] El fork creado tiene `scope=global_tenant_template` y
      `forked_from_agent_id` apuntando al built-in.
- [ ] El fork SÍ permite grant via UI + API.

**Pitfalls conocidos**:

- Si el built-in `project_manager` no existe en tu BD, corre primero
  `python -m api_server.seeds`.
- La operación "fork" puede no estar 100 % cableada al admin-panel
  todavía (depende del estado del Plan 01.15). Si no hay botón en
  la UI, ejecuta el fork vía curl: `POST /agents/{builtin_id}/fork`
  con `{"name":"PM-fork-tenant"}`.

## Troubleshooting

| Síntoma                                                                  | Causa probable                                       | Fix                                                                                 |
| ------------------------------------------------------------------------ | ---------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `setup_demo_06_9.py` falla con "column default_kb_grants does not exist" | Migración 0027 sin aplicar.                          | `cd apps/api-server && alembic upgrade head`                                        |
| `<KbCombobox>` no encuentra la KB                                        | El usuario no es member del tenant donde vive la KB. | Usa `admin-06-8@example.com` que el seed configura como `tenant_admin` de tenant-a. |

| Revoke en el panel "Asignaciones" no actualiza la lista                  | TanStack Query no invalidó el cache.                 | F5 — el cache se cae con la sesión.                                                 |

`docs/03-guides/gotchas/`.
