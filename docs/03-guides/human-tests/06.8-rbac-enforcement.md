# Plan 06.8 — tests humanos

Esta guía cubre los **4 tests humanos** del Plan 06.8 (RBAC
enforcement). Cada uno consiste en loguearse como un usuario con un
rol distinto (`tenant_user`, `tenant_admin`, `system_admin`) y
verificar que los botones / sidebar items / `403` esperados están donde
deben.

> **Estado del plan**: `pending_human_validation`. Las 11 tareas y los
> 39 tests automáticos están en verde (6 helpers + 28 RBAC parametrizados
>
> - 5 de `/me`). Estos 4 tests humanos son el último paso antes de
>   pasar a `completed`.

## TL;DR

```powershell
.\scripts\dev\up.ps1                                     # primera vez
.\.venv\Scripts\python.exe scripts\setup_demo_06_8.py    # 3 usuarios + proyecto demo
.\scripts\dev\run-human-tests-06.8.ps1                   # imprime credenciales + URLs
```

El launcher es un **printer informativo** — no hay nada que automatizar
aquí porque los 4 tests requieren ojos humanos en la UI (botones
escondidos, badges visibles, sidebar reducido). El launcher:

1. Verifica que `api-server :8001` y `admin-panel :3000` responden.
2. Lee `scripts/.demo_state_06_8.json` (creado por el setup) y
   re-imprime las **credenciales de los 3 usuarios** + URLs útiles.
3. Lista qué hacer con cada cuenta — coincide con los checklists
   de abajo.

| Requisito                                   | Por qué                                                     |

## Qué siembra `setup_demo_06_8.py`

Bajo el tenant `tenant-a` (override con `DEMO_TENANT`):

| Usuario                     | Rol            | Password             |
| --------------------------- | -------------- | -------------------- |
| `user-06-8@example.com`     | `tenant_user`  | `demo-06-8-user`     |
| `admin-06-8@example.com`    | `tenant_admin` | `demo-06-8-admin`    |
| `sysadmin-06-8@example.com` | `system_admin` | `demo-06-8-sysadmin` |

Más un proyecto `"Plan 06.8 demo"` para que los tres tengan algo
visible en `/admin/projects`.

State persistido en `scripts/.demo_state_06_8.json` — el launcher lo
lee para volver a imprimir las credenciales sin tocar la BD.

## `human_06_8_01` — tenant_user no puede mutar recursos

**Qué prueba**: el rol `tenant_user` ve los recursos pero la UI no
muestra botones de mutación; el backend rechaza con 403 cualquier
intento por curl.

**Cómo ejecutarlo**:

1. Logout del admin-panel.
2. Login con `user-06-8@example.com` / `demo-06-8-user`.
3. Recorre la UI:
   - Sidebar: **NO** debe mostrar "Settings" ni "Validación humana".
   - Header: el badge junto al menú de usuario dice **`user`** en gris.
   - `/admin/projects`: ves la card de "Plan 06.8 demo" pero
     **NO** hay botón "Crear proyecto".
   - Entra en el proyecto: **NO** hay botones "Editar" / "Borrar".
   - Tab "MCP servers": ves el listado pero **NO** hay botón "Añadir".
   - Sidebar "Knowledge Bases": ves los KBs pero **NO** botón "Crear
     KB" ni botones Edit/Delete/Grant por fila.
4. Verifica el rechazo desde fuera de la UI:
   ```bash
   # Obtén el JWT del tenant_user (paste manual o lee la cookie).
   curl -s -X POST http://localhost:8001/projects \
     -H "Authorization: Bearer $TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"name":"hack","status":"active"}'
   # → {"detail":"tenant_admin role required"}  (HTTP 403)
   ```

**Checklist**:

- [ ] Login OK como `tenant_user`.
- [ ] Badge en el header dice "user" (gris).
- [ ] Sidebar SIN "Settings" ni "Validación humana".
- [ ] `/admin/projects`: SIN botón "Crear proyecto".
- [ ] Detail de proyecto: SIN botones Editar / Borrar.
- [ ] Tab MCP servers: SIN botón "Añadir".
- [ ] `/admin/knowledge-bases`: SIN botones "Crear KB" / Edit /
      Delete / Grant.
- [ ] `curl POST /projects` con su token → **403 tenant_admin role
      required**.

**Pitfalls conocidos**:

- Si ves los botones admin, comprueba que el `useCurrentUser` hook se
  ha invalidado tras el cambio de tenant. F5 fuerza el refresh.
- El proyecto seedeado debe estar en `tenant-a`. Si tu admin-panel
  apunta a otro tenant (picker del superadmin), no verás el
  recurso — eso es un falso negativo, no falla del RBAC.

## `human_06_8_02` — tenant_admin puede todo dentro del tenant

**Qué prueba**: el rol `tenant_admin` ve todos los botones de
configuración del tenant **pero** NO puede cambiar de tenant (el
picker está oculto).

**Cómo ejecutarlo**:

1. Logout. Login con `admin-06-8@example.com` / `demo-06-8-admin`.
2. UI:
   - Badge: **`admin`** en azul.
   - Sidebar: muestra "Settings" y "Validación humana".
   - Tenant-picker del header: **NO** aparece (solo system_admin lo ve).
3. Operaciones (deben funcionar end-to-end):
   - Crear proyecto vacío desde `/admin/projects` (botón visible).
   - Crear KB desde `/admin/knowledge-bases`.
   - Añadir MCP server al proyecto (botón visible, dialog se abre).
   - `/admin/settings/memories` → cambia el threshold a 0.85,
     guarda. F5 → persiste.
   - `/admin/settings/hourly-rate` → cambia el rate, guarda.
4. `GET /me` desde el navegador o curl debe devolver
   `is_system_admin: false` y `memberships: [{role: tenant_admin}]`.

**Checklist**:

- [ ] Badge "admin" (azul) visible.
- [ ] Sidebar con "Settings" y "Validación humana".
- [ ] Tenant-picker NO visible.
- [ ] Crear proyecto funciona desde la UI.
- [ ] Crear / editar / borrar KB funciona.
- [ ] Añadir MCP server abre el dialog.
- [ ] Cambiar tenant-setting (memoria threshold) persiste tras F5.
- [ ] `GET /me` → `is_system_admin: false`, role en
      memberships es `tenant_admin`.

**Pitfalls conocidos**:

- Si crear proyecto da 422, suele ser por el enum de status — el
  valor por defecto debe ser `active`, no `draft` (corrigió Plan 06.6).
- El cambio de threshold solo persiste si la migración
  `tenant_settings` está aplicada (lo hace `up.ps1`).

## `human_06_8_03` — system_admin pasa todo + cross-tenant

**Qué prueba**: el flag global `is_system_admin=true` pasa todos los
gates, el tenant-picker aparece y cambiar de tenant refresca la UI.

**Cómo ejecutarlo**:

1. Logout. Login con `sysadmin-06-8@example.com` /
   `demo-06-8-sysadmin`.
2. UI:
   - Badge: **`system_admin`** en ámbar.
   - Sidebar: muestra todo (Settings, Validación humana, etc.).
   - **Tenant-picker** del header: visible. Lista los tenants
     existentes (al menos `tenant-a` + cualquiera que tengas).
3. Cambia el tenant activo:
   - Pick otro tenant del picker.
   - Las listas (proyectos, agentes, etc.) refrescan con los datos
     del nuevo tenant.
   - Vuelve a `tenant-a` — los datos vuelven.
4. Mutaciones cross-tenant:
   - Crea un proyecto en `tenant-a`. OK.
   - Cambia a otro tenant, crea otro proyecto. OK.
5. `GET /me`:
   ```bash
   curl -s http://localhost:8001/me -H "Authorization: Bearer $TOKEN"
   # → {"is_system_admin": true, "memberships": [], ...}
   ```

**Checklist**:

- [ ] Badge "system_admin" (ámbar) visible.
- [ ] Tenant-picker muestra todos los tenants.
- [ ] Cambiar de tenant refresca la UI con datos del nuevo.
- [ ] Mutaciones funcionan en cualquier tenant.
- [ ] `GET /me` → `is_system_admin: true`.
- [ ] `/me` con `X-Tenant-Id: <otro>` honra el header (cambia el
      `active_tenant_id` del response).

**Pitfalls conocidos**:

- El picker fetchea `/admin/tenants` que solo responde a system_admin.
  Si está vacío, es que la BD solo tiene un tenant — crea otro vía
  `/admin/tenants` con curl o desde la UI.
- El sticky cache de TanStack puede mostrar datos del tenant
  anterior un instante tras cambiar — el `tenant-context.tsx`
  invalida con `queryClient.invalidateQueries()`, pero algunos
  componentes con `staleTime: Infinity` se refrescan solo con F5.

## `human_06_8_04` — tasks se crean por cualquier member

**Qué prueba**: las operaciones del **día a día** (crear tasks,
mover en kanban, comentar planes) NO requieren admin — el matriz
las clasifica como `tenant_member`.

**Cómo ejecutarlo**:

1. Logout. Login con `user-06-8@example.com` / `demo-06-8-user`
   (tenant_user, NO admin).
2. Entra a `/admin/projects/{id}/tasks` del proyecto demo.
3. Botón "Crear tarea" debe estar **visible** (es day-to-day).
4. Crea una tarea con un título cualquiera → debe aparecer en el
   kanban inmediatamente.
5. Drag-and-drop la tarea de "backlog" a "in_progress" → cambia de
   columna, la API responde 200, F5 confirma la persistencia.
6. Abre un plan del proyecto, añade un comentario en markdown,
   guarda → comentario visible al recargar.

**Checklist**:

- [ ] `tenant_user` ve `/admin/projects/{id}/tasks` con las tareas.
- [ ] Botón "Crear tarea" **SÍ** aparece (operación del día a día).
- [ ] Crear tarea funciona end-to-end (POST `/projects/{id}/tasks`
      → 201).
- [ ] Drag-drop entre columnas del kanban cambia el status (PUT
      `/projects/{id}/tasks/{id}` → 200).
- [ ] Comentar en un plan funciona (POST `/plans/{id}/comments` → 201).

**Pitfalls conocidos**:

- `tenant_user` **NO** puede borrar tareas (DELETE
  `/projects/{id}/tasks/{id}` → 403 admin role required). Eso es
  por diseño — borrar tareas escaladas es operación de admin.
- Si el drag-drop falla con 403, comprueba que la tarea esté en el
  tenant donde el user tiene membership (no en otro tenant que
  el picker te haya dejado).

## Troubleshooting

| Síntoma                                              | Causa probable                                                            | Fix                                                                |
| ---------------------------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| `setup_demo_06_8.py` falla con "No existe el tenant" | El slug por defecto `tenant-a` no existe en tu BD                         | `DEMO_TENANT=<slug> python scripts/setup_demo_06_8.py`             |
| Login con las credenciales del seed falla            | El user-06-8 fue creado con un hash incompatible (versión antigua argon2) | Re-corre el seed; sobrescribe el `is_system_admin` pero NO la pass |
| El badge no aparece en el header                     | El `useCurrentUser` hook devolvió error (revisa la consola)               | F5; si persiste, mira que `/me` responda 200 con el JWT activo     |
| `curl POST /projects` da 401 en vez de 403           | Token expirado o sesión invalidada                                        | Re-login y vuelve a copiar el token                                |
| El picker de tenant no aparece para system_admin     | `is_system_admin` en BD no se reflejó en el JWT                           | Logout + login para refrescar el `sys` claim                       |

Errores transversales viven en `docs/03-guides/gotchas/`.
