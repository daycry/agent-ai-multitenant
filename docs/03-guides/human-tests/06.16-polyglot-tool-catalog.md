# Plan 06.16 — tests humanos

Esta guía cubre el **test humano** del Plan 06.16 (catálogo de tools
políglota — `shell_exec` asignable + runtime por stack). Valida lo que
los e2e Playwright escritos pero no ejecutados no cubren: que un
operador configura un proyecto PHP desde la UI (allowlist de comandos
como chips + preset PHP + `default_runtime_template`), que un agente con
`shell_exec` **ejecuta comandos PHP dentro del runtime correcto**, que
un comando **fuera de la allowlist es rechazado** (deny-by-default) y que
`run_tests` usa `php-phpunit` en vez de `python-pytest`.

> **Estado del plan**: `pending_human_validation`. Las 5 tareas
> (`task_06_16_01`..`task_06_16_05`) están en verde (migración reversible
> 0072 con `projects.allowed_commands` + `projects.default_runtime_template`,
> `shell_exec` en el seed `builtin_tools` cableado a `ProjectShellExec`
> con la allowlist del proyecto, `run_*` resueltos por
> `default_runtime_template`, sección "Comandos & runtime" en el proyecto
> con chips + presets, ADR + guía + changelog). El e2e
> `project-commands.spec.ts` está escrito pero NO ejecutado — este test
> humano es el último paso antes de pasar a `completed`.

## TL;DR

No hay `setup_demo_06_16.py` ni launcher dedicado para este plan. El
test reutiliza un proyecto + un agente que ya tengas (o el seed de
WebScorpo, que nace con `allowed_commands` PHP + `php-phpunit`). El setup
es manual:

```powershell
.\scripts\dev\up.ps1                                     # api-server :8001 + admin-panel :3000 + postgres + redis
.\.venv\Scripts\python.exe -m api_server.seeds           # built-in tools (incl. shell_exec) + agentes built-in
.\.venv\Scripts\python.exe scripts\setup_webscorpo.py    # (opcional) proyecto PHP ya configurado con allowlist + php-phpunit
```

La pantalla nueva (sección dentro del editor de proyecto) donde se
configura la allowlist + el runtime, y la sección de tools del agente
(Plan 06.15) donde se asigna `shell_exec`:

```
http://localhost:3000/admin/projects/<project_id>     # sección "Comandos & runtime": chips + presets + default_runtime_template
http://localhost:3000/admin/agents/<agent_id>          # sección "Tools del agente": shell_exec aparece en Básicas (badge Privilegiada)
```

`shell_exec` es **deny-by-default**: solo ejecuta los basenames de
`projects.allowed_commands`; lista vacía ⇒ no ejecuta nada. La edición de
la config es `tenant_admin`.

## `human_06_16_01` — Un agente lanza comandos PHP en un proyecto

**Qué prueba**: en `/admin/projects/[id]` → "Comandos & runtime", el
preset PHP rellena los chips (`php`/`composer`/`vendor/bin/phpunit`/
`pest`), se elige `default_runtime_template = php-phpunit` y se guarda;
se asigna `shell_exec` al agente (aparece en Básicas con badge
Privilegiada); el agente ejecuta `composer install` + `vendor/bin/phpunit`
**dentro del runtime**; un binario no autorizado (`rm -rf /`) es
**rechazado** (no está en la allowlist); y `run_tests` usa `php-phpunit`,
no `python-pytest`.

**Precondiciones**:

- Login como `tenant_admin`.
- Un proyecto del tenant con stack PHP (o reusa el proyecto `webscorpo`
  del seed).
- Un agente project-scoped al que asignar `shell_exec`.

**Pasos**:

1. Como `tenant_admin`, ve a `/admin/projects/<project_id>` y abre la
   sección **"Comandos & runtime"**.
2. Pulsa el **preset PHP**: los chips de `allowed_commands` se rellenan
   con `php`, `composer`, `vendor/bin/phpunit`, `pest` (puedes
   añadir/quitar chips a mano). Verifica que puedes quitar un chip y
   volver a añadirlo.
3. En el selector de **`default_runtime_template`** elige **`php-phpunit`**
   y **Guarda**. Recarga (F5): la allowlist + el runtime **persisten**.
4. Ve a `/admin/agents/<agent_id>` → sección "Tools del agente" (Plan
   06.15) → pestaña **Básicas**: `shell_exec` ("Ejecutar comando")
   aparece con badge **Privilegiada** (`security_level=privileged`).
   Asígnala al agente y guarda.
5. **Ejecuta una tarea** con ese agente que invoque `composer install` y
   `vendor/bin/phpunit`: ambos comandos se ejecutan **OK dentro del
   runtime** del proyecto (están en la allowlist).
6. Haz que el agente intente un comando **no autorizado** (p. ej.
   `rm -rf /` o cualquier binario no listado): `shell_exec` lo
   **rechaza** indicando que no está en la lista de permitidos (no se
   ejecuta nada).
7. Lanza `run_tests` del agente: debe resolver el runtime
   **`php-phpunit`** (de `default_runtime_template`), **no**
   `python-pytest`. Verifícalo en la traza/logs del agent-runtime.

**Resultado esperado**: la config se guarda y persiste; `shell_exec`
aparece en Básicas (Privilegiada) y se asigna; los comandos de la
allowlist corren en `php-phpunit`; un binario no autorizado se rechaza;
`run_tests` usa `php-phpunit`.

**Checklist**:

- [ ] En `/admin/projects/[id]` → Comandos & runtime: pulsar preset PHP
      → chips `php`/`composer`/`vendor/bin/phpunit`/`pest`.
- [ ] Elegir `default_runtime_template = php-phpunit` y guardar (persiste
      tras F5).
- [ ] Asignar `shell_exec` al agente (Plan 06.15) — aparece en Básicas
      con badge Privilegiada.
- [ ] El agente ejecuta `composer install` y `vendor/bin/phpunit` → OK
      dentro del runtime.
- [ ] El agente intenta `rm -rf /` o un binario no autorizado →
      rechazado (no está en la allowlist).
- [ ] `run_tests` del agente usa el runtime `php-phpunit`, no
      `python-pytest`.

**Pitfalls conocidos**:

- **Deny-by-default**: si la allowlist está vacía, `shell_exec` NO
  ejecuta NADA — eso es lo correcto. Si esperas que corra `composer` y
  da denegado, comprueba que el chip `composer` está en la allowlist
  guardada (no solo en el editor sin guardar).
- `shell_exec` es **básica** (`is_builtin=true`) pese a ser
  `privileged` — seguridad y básico/avanzado son ejes ortogonales (ADR
  del plan). Por eso aparece en la pestaña Básicas, no en Avanzadas.
- La allowlist compara por **basename** (`vendor/bin/phpunit`,
  `composer`…) con argv (`shlex`) + timeout; rutas absolutas o
  inyecciones de shell no la saltan.
- `run_*` resuelve el runtime desde `project.default_runtime_template`
  con **fallback** al `implementation_ref` por defecto (`python-pytest`).
  Si `run_tests` sigue usando python, comprueba que guardaste
  `php-phpunit` en el proyecto (y que el runtime existe en el catálogo).
- Si el runtime `php-phpunit` no está construido en tu entorno, la
  ejecución real puede fallar por "runtime no disponible"; la
  resolución del template (que apunta a `php-phpunit`) sigue siendo
  verificable en los logs.

| La ejecución del comando falla con "runtime no disponible" | La imagen del runtime `php-phpunit` no está construida       | Construye/pull del runtime template; el rechazo de allowlist sigue válido   |
