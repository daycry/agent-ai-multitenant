# Plan 06.10 — tests humanos

Esta guía cubre los **4 tests humanos** del Plan 06.10 (Categorías de
Knowledge Bases: built-in + custom per-tenant). Validan que las
categorías built-in aparecen, las KBs canónicas vienen categorizadas,
el CRUD de categorías custom funciona (con confirm-by-name), el alta
inline desde el dialog Crear KB, y que `tenant_user` no puede
gestionar categorías.

> **Estado del plan**: `completed` (mergeado a `master`,
> `completed_at: 2026-05-31`). Esta guía es el **registro histórico**
> de los tests humanos con los que se cerró el plan; queda para
> regresión cuando se toquen las páginas de categorías o el dialog
> Crear KB.

## TL;DR

El Plan 06.10 **no tiene** `scripts/setup_demo_06_10.py` ni launcher
dedicado: las 5 categorías built-in y las KBs canónicas se cargan con
el seed del stack. Setup manual:

```powershell
.\scripts\dev\up.ps1                 # api-server :8001 + admin-panel :3000 + postgres + redis
# luego: abre http://localhost:3000/admin/knowledge-bases/categories
```

> Para `human_06_10_04` necesitas un usuario `tenant_user` además del
> `tenant_admin`/`system_admin`. Si arrancas de cero, el primer
> registro se promueve a `system_admin`; crea un `tenant_user`
> adicional desde `/admin/users` (o reutiliza el seed RBAC de
> `scripts/setup_demo_06_8.py`, que crea `user-06-8@example.com` con
> rol `tenant_user`).

## Pre-requisitos

| Requisito                     | Por qué                                                |
| ----------------------------- | ------------------------------------------------------ |

## `human_06_10_01` — built-ins aparecen + las KBs canónicas están categorizadas

**Qué prueba**: las 5 categorías built-in se listan con badge
`platform`, el dropdown de Crear KB las ofrece, las 6 KBs canónicas
vienen categorizadas y el listing agrupa por categoría.

**Precondiciones**: stack arriba con el seed cargado, sesión
`tenant_admin`.

**Pasos**:

1. Abre `/admin/knowledge-bases/categories`.
2. Verifica que se listan las **5 built-ins** con badge `platform`.
3. Abre el modal **Crear KB** y despliega el dropdown de categoría.
4. Vuelve a `/admin/knowledge-bases` y revisa el listing.

**Resultado esperado**:

- `/admin/knowledge-bases/categories` lista las 5 built-ins con badge
  `platform`.
- El dropdown de categoría del modal Crear KB muestra las 5 + las
  custom del tenant.
- Las 6 KBs canónicas del seed aparecen categorizadas (5 en `stack`,
  1 en `role`).
- El listing `/admin/knowledge-bases` agrupa por categoría con
  secciones colapsables.

**Checklist**:

- [ ] `/admin/knowledge-bases/categories` lista las 5 built-ins con
      badge `platform`.
- [ ] Modal Crear KB: dropdown de categoría muestra las 5 + las custom
      del tenant.
- [ ] Las 6 KBs canónicas del seed aparecen ya categorizadas (5 en
      `stack`, 1 en `role`).
- [ ] Listing `/admin/knowledge-bases` agrupa por categoría con
      secciones colapsables.

**Pitfalls conocidos**:

- Si las KBs canónicas no aparecen, el seed no se cargó: revisa el log
  de arranque del api-server.

## `human_06_10_02` — crear / editar / borrar categoría custom

**Qué prueba**: el CRUD completo de categorías custom como
`tenant_admin`, con confirm-by-name al borrar y built-ins protegidas.

**Precondiciones**: stack arriba, sesión `tenant_admin`.

**Pasos**:

1. En `/admin/knowledge-bases/categories`, click **"Nueva categoría"**.
2. Crea **"Cliente Acme"** con color azul → debe aparecer en el listado.
3. Edita su nombre y guarda → F5 para confirmar que persiste.
4. Borra la categoría (confirm-by-name) → desaparece; las KBs que la
   tenían quedan sin categoría.
5. Intenta editar/borrar una **built-in**.

**Resultado esperado**:

- "Nueva categoría" abre el dialog.
- "Cliente Acme" (azul) aparece en el listado.
- La edición del nombre persiste tras F5.
- El borrado confirm-by-name elimina la categoría; las KBs quedan sin
  categoría.
- Editar/borrar una built-in: botones no visibles (o 403 desde el
  backend).

**Checklist**:

- [ ] Click "Nueva categoría" abre dialog.
- [ ] Crear "Cliente Acme" con color azul → aparece en el listado.
- [ ] Editar el nombre → persiste tras F5.
- [ ] Borrar (confirm-by-name) → categoría desaparece; KBs que la
      tenían quedan sin categoría.
- [ ] Intentar editar / borrar una built-in → botones no visibles (o
      devuelven 403).

**Pitfalls conocidos**:

- El confirm-by-name exige teclear el nombre exacto de la categoría:
  un nombre mal escrito no habilita el botón de borrado.

## `human_06_10_03` — inline "Nueva categoría" desde el dialog Crear KB

**Qué prueba**: se puede crear una categoría sin salir del flujo de
creación de KB, y queda pre-seleccionada.

**Precondiciones**: stack arriba, sesión `tenant_admin`.

**Pasos**:

1. Abre el modal **Crear KB**.
2. En el selector de categoría, click **"+ Nueva categoría"** → abre un
   mini-dialog inline.
3. Crea **"Compliance interno"** → el mini-dialog se cierra y queda
   pre-seleccionada.
4. Completa y guarda la KB.
5. Vuelve al listado y verifica que la KB aparece bajo "Compliance
   interno".

**Resultado esperado**:

- "+ Nueva categoría" abre un mini-dialog inline.
- "Compliance interno" queda pre-seleccionada al cerrarse.
- La KB guardada aparece bajo "Compliance interno".

**Checklist**:

- [ ] Modal Crear KB → click "+ Nueva categoría" abre mini-dialog
      inline.
- [ ] Crear "Compliance interno" → mini-dialog se cierra y queda
      pre-seleccionada.
- [ ] Guardar la KB → aparece bajo "Compliance interno" en el listado.

**Pitfalls conocidos**:

- Si la categoría recién creada no queda pre-seleccionada, refresca el
  dropdown: el mini-dialog debe invalidar la query de categorías al
  cerrar.

## `human_06_10_04` — tenant_user no puede gestionar categorías

**Qué prueba**: el rol `tenant_user` ve las categorías en read-only
pero no tiene botones de gestión, y el backend rechaza la mutación con 403.

**Precondiciones**: un usuario `tenant_user` (ver TL;DR). Su JWT a mano
para el curl.

**Pasos**:

1. Logout. Login como `tenant_user`.
2. Abre `/admin/knowledge-bases/categories`: el botón **"Nueva
   categoría"** debe estar **ausente**.
3. Verifica que las built-ins se ven (read-only) y que las custom del
   tenant no tienen botones edit/delete.
4. Verifica el rechazo del backend:
   ```bash
   curl -s -X POST http://localhost:8001/kb-categories \
     -H "Authorization: Bearer $TOKEN_USER" \
     -H "Content-Type: application/json" \
     -d '{"name":"hack"}'
   # → 403 tenant_admin role required
   ```

**Resultado esperado**:

- Botón "Nueva categoría" **ausente** para `tenant_user`.
- Built-ins visibles (read-only); custom del tenant sin botones
  edit/delete.
- `curl POST /kb-categories` con su token → **403 tenant_admin role
  required**.

**Checklist**:

- [ ] Sidebar de `/admin/knowledge-bases/categories`: botón "Nueva
      categoría" ausente.
- [ ] Built-ins se ven (read-only para todos) pero las custom del
      tenant no tienen botones edit/delete.
- [ ] `curl POST /kb-categories` con su token → 403 tenant_admin role
      required.

**Pitfalls conocidos**:

- Si ves el botón "Nueva categoría" como `tenant_user`, fuerza F5 para
  invalidar el `useCurrentUser` tras el cambio de cuenta.
- Si el curl da 401 en vez de 403, el token expiró: re-loguéate y
  vuelve a copiarlo.
