# Plan 06.11 — tests humanos

Esta guía cubre los **3 tests humanos** del Plan 06.11 (ingestión + fixes
del subsistema KB): subir un documento y verlo indexarse de punta a
punta, re-indexar un fallido, y que una KB borrada deje de alimentar el
RAG.

> **Estado del plan**: tareas y tests automáticos (43) en verde. Estos 3
> humanos son el último paso antes de `completed`.
>
> El antiguo `human_06_11_03` (KB built-in visible/usable) se movió al
> Plan 06.12, que es donde se implementó la alcanzabilidad de built-ins.

## Pre-requisitos

| Requisito                                                                                                     | Por qué                                                                     |
| ------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| **Stack COMPLETO arriba**: api-server, admin-panel, postgres, redis, **minio, docling-serve, clamav, ollama** | El test 01 ejerce el pipeline real de ingesta de extremo a extremo.         |
| **Worker de ingesta corriendo**: `celery -A workers.celery_app worker -Q ingestion`                           | Consume `workers.ingest_document`. Sin él, los docs se quedan en `pending`. |
| **Celery beat** (opcional): `celery -A workers.celery_app beat`                                               | Activa el barrido de respaldo `sweep_pending_documents`.                    |
| Migraciones hasta `0028` aplicadas + `python -m api_server.seeds`                                             | Esquema KB + catálogo.                                                      |
| Login como `tenant_admin` con un proyecto que tenga ≥1 KB granteada                                           | Para el test 01 (retrieval en un chat del proyecto).                        |

> ⚠️ Si `docling-serve` está `unhealthy` (lo estaba en la última
> comprobación), el test 01 dejará el documento en `failed` —
> precisamente el caso del test 02 (re-index). Levanta docling-serve
> antes del test 01.

## `human_06_11_01` — Subir un documento e indexarlo end-to-end

**Qué prueba**: el fix #1 — un documento subido ahora se **encola, se
procesa y se indexa** (antes se quedaba en `pending` para siempre).

**Cómo ejecutarlo**:

1. Login como `tenant_admin`.
2. Sidebar → **Knowledge Bases** (`/admin/knowledge-bases`).
3. Despliega una KB (click en su fila) → aparece el panel de documentos.
4. Click **"Subir documento"** → elige un `.md` o `.pdf` pequeño → **Subir**.
5. **Verifica**: el documento aparece con badge **Pendiente**, luego
   **Procesando**, y finalmente **Indexado** (refresca o abre el enlace
   **Progreso** → página de ingestión por WebSocket).
6. Ve a un proyecto que tenga esa KB granteada → **Chat** → pregunta algo
   cuya respuesta esté en el documento.
7. **Verifica**: la respuesta cita/recupera chunks de ese documento.

**✅ Pasa si**: el documento llega a **Indexado** y su contenido es
recuperable en el chat. **❌ Falla si**: se queda en `pending` para
siempre (worker o broker caído) — revisa que el worker `ingestion` esté
corriendo.

## `human_06_11_02` — Re-indexar un documento fallido

**Qué prueba**: el endpoint de re-index + el botón "Reintegrar"
(RefreshCw) permiten recuperarse de un `failed`.

**Cómo ejecutarlo**:

1. Provoca un `failed`: sube un fichero con docling-serve caído, **o**
   usa un documento que ya esté en `failed`.
2. En el panel de documentos de la KB, la fila `failed` muestra el botón
   **↻** (reindex).
3. Levanta docling-serve (si estaba caído) → click **↻**.
4. **Verifica**: el documento vuelve a **Pendiente** y se reprocesa hasta
   **Indexado** (sus chunks viejos se borran primero, no se duplican).

**✅ Pasa si**: tras reintegrar, el documento se reprocesa y termina
indexado sin chunks duplicados.

## `human_06_11_03` — Una KB borrada no contamina el RAG

**Qué prueba**: el fix del drift de soft-delete — los chunks de una KB
borrada dejan de ser recuperables (antes seguían apareciendo).

**Cómo ejecutarlo**:

1. Parte de una KB con al menos un documento **Indexado** y granteada a
   un proyecto (la del test 01 sirve).
2. En el chat del proyecto, confirma que una pregunta recupera chunks de
   esa KB.
3. Ve a **Knowledge Bases** → borra esa KB (papelera → confirmar por
   nombre).
4. Vuelve al chat → repite la misma pregunta.
5. **Verifica**: ya **no** se recuperan chunks de la KB borrada.

**✅ Pasa si**: tras el borrado, los chunks de esa KB desaparecen de los
resultados de búsqueda.
