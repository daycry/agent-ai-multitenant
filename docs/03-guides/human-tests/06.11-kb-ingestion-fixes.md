# Plan 06.11 — tests humanos

Esta guía cubre los **4 tests humanos** del Plan 06.11 (KB ingestion
wiring + arreglos críticos del subsistema de Knowledge Bases). Validan
la ingesta end-to-end de un documento, el re-indexado de un fallo, las
KB built-in concedibles y que una KB borrada no contamine el RAG.

> **Estado del plan**: `completed` (mergeado a `master`,
> `completed_at: 2026-05-31`). Esta guía es el **registro histórico**
> de los tests humanos con los que se cerró el plan; queda para
> regresión cuando se toque la pipeline de ingesta de documentos o el
> RAG.

## TL;DR

El Plan 06.11 **no tiene** `scripts/setup_demo_06_11.py` ni launcher
dedicado: requiere el **stack completo de ingesta** arriba (docling-serve,
clamav, ollama, minio) y subir un documento real desde la UI. Setup
manual:

```powershell
.\scripts\dev\up.ps1                 # api-server + admin-panel + postgres + redis + workers
# además, asegúrate de tener arriba: docling-serve, clamav, ollama, minio
# luego: abre http://localhost:3000/admin/knowledge-bases
```

> A diferencia de los demás tests de KB, estos **sí requieren los
> servicios de ingesta**: docling-serve convierte el documento, clamav
> lo escanea, ollama genera los embeddings y minio guarda el binario.
> Si alguno está caído, la ingesta queda en `failed`. Puedes apoyarte
> en `scripts/setup_demo_project.py` para tener un proyecto + agente
> con grant a la KB.

## Pre-requisitos

| Requisito                            | Por qué                                                |
| ------------------------------------ | ------------------------------------------------------ |
| Stack dev arriba (`up.ps1`)          | api-server + admin-panel + postgres + redis + workers  |
| docling-serve arriba                 | Conversión de documentos (.pdf / .md) a texto + chunks |
| clamav arriba                        | Escaneo antivirus del documento subido                 |
| ollama arriba                        | Generación de embeddings de los chunks                 |
| minio arriba                         | Almacenamiento del binario subido                      |
| Un proyecto/agente con grant a la KB | Para verificar que el RAG recupera los chunks          |

## `human_06_11_01` — subir un documento e indexarlo end-to-end

**Qué prueba**: subir un documento desde la UI lo lleva de `pending` a
`indexed` y el RAG recupera sus chunks en un chat.

**Precondiciones**: stack de ingesta completo arriba; una KB existente;
un proyecto/agente con grant a esa KB.

**Pasos**:

1. Abre `/admin/knowledge-bases` y selecciona una KB.
2. Click **"Subir documento"** y sube un `.md` o `.pdf`.
3. Observa el badge / la página de progreso: debe pasar de `pending` a
   `indexed`.
4. Abre un chat del proyecto/agente con grant a esa KB y haz una
   pregunta cuyo contenido esté en el documento.

**Resultado esperado**:

- El documento se sube sin error desde "Subir documento".
- Pasa de `pending` a `indexed` (badge + página de progreso).
- El RAG recupera chunks de ese documento en el chat.

**Checklist**:

- [ ] Subir un `.md`/`.pdf` desde `/admin/knowledge-bases` (botón
      "Subir documento").
- [ ] El documento pasa de `pending` a `indexed` (badge + página de
      progreso).
- [ ] El RAG recupera chunks de ese documento en un chat del
      proyecto/agente con grant.

**Pitfalls conocidos**:

- Si el documento queda en `failed`, mira qué servicio de ingesta está
  caído (docling-serve / clamav / ollama / minio) en
  `docker compose ps`.
- Si el RAG no recupera nada, comprueba el grant: el agente debe tener
  acceso explícito a esa KB.

## `human_06_11_02` — re-indexar un documento fallido

**Qué prueba**: un documento en `failed` ofrece "Reintentar" y al
hacerlo vuelve a `pending` para reprocesarse.

**Precondiciones**: un documento en estado `failed` (puedes forzarlo
parando momentáneamente docling-serve durante una subida y volviendo a
levantarlo).

**Pasos**:

1. Localiza un documento en estado `failed` en la KB.
2. Verifica que muestra el botón **"Reintentar"**.
3. Pulsa "Reintentar" y observa que vuelve a `pending`.

**Resultado esperado**:

- El documento `failed` muestra "Reintentar".
- Tras reintentar vuelve a `pending` y se reprocesa.

**Checklist**:

- [ ] Un documento en `failed` muestra botón "Reintentar".
- [ ] Tras reintentar vuelve a `pending` y se reprocesa.

**Pitfalls conocidos**:

- Si tras reintentar vuelve a `failed`, la causa raíz del fallo sigue
  ahí (servicio caído, formato no soportado): arréglala antes de
  reintentar.

## `human_06_11_03` — KB built-in visible y usable

**Qué prueba**: las KB built-in del catálogo aparecen, se pueden
conceder a un proyecto/agente y el agente con grant recupera sus
chunks.

**Precondiciones**: catálogo built-in cargado; un proyecto/agente al
que conceder la KB.

**Pasos**:

1. Abre `/admin/knowledge-bases` y localiza las KB built-in del
   catálogo.
2. Concede una built-in a un proyecto/agente.
3. En un chat de ese agente, pregunta algo cubierto por la built-in.

**Resultado esperado**:

- Las KB built-in del catálogo aparecen.
- Se pueden conceder a un proyecto/agente.
- El agente con grant recupera sus chunks.

**Checklist**:

- [ ] Las KB built-in del catálogo aparecen y se pueden conceder a un
      proyecto/agente.
- [ ] Un agente con grant a una built-in recupera sus chunks.

**Pitfalls conocidos**:

- Las built-in son read-only: no se editan ni borran desde la UI del
  tenant (esto se valida también en Plan 06.10).

## `human_06_11_04` — KB borrada no contamina el RAG

**Qué prueba**: tras el soft-delete de una KB, sus chunks dejan de
aparecer en los resultados de búsqueda.

**Precondiciones**: una KB con documentos indexados cuyos chunks ya se
recuperaban en un chat.

**Pasos**:

1. Confirma primero (en un chat) que el RAG recupera chunks de la KB.
2. Borra la KB (soft-delete).
3. Repite la misma consulta en el chat.

**Resultado esperado**:

- Tras el soft-delete, los chunks de esa KB **dejan de aparecer** en
  los resultados de búsqueda.

**Checklist**:

- [ ] Tras borrar (soft-delete) una KB, sus chunks dejan de aparecer en
      resultados de búsqueda.

**Pitfalls conocidos**:

- Si los chunks siguen apareciendo, revisa que la búsqueda filtre por
  `deleted_at IS NULL` (la fuga de chunks de KBs borradas fue
  precisamente uno de los bugs que arregla este plan).
