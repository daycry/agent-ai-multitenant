# Plan 06.12 — tests humanos

Esta guía cubre los **3 tests humanos** del Plan 06.12 (consistencia del
catálogo global, ADR 0029): que las KB built-in sean visibles y
grantables, read-only desde la API, y que el aislamiento cross-tenant
siga intacto tras migrar `kb_categories` al patrón (A).

> **Estado del plan**: tareas y tests automáticos (60) en verde. Estos 3
> humanos son el último paso antes de `completed`.

## Pre-requisitos

| Requisito                                        | Por qué                                                                                 |
| ------------------------------------------------ | --------------------------------------------------------------------------------------- |
| Stack dev arriba (`.\scripts\dev\up.ps1`)        | api-server + admin-panel + postgres + redis.                                            |
| Migraciones hasta `0030` aplicadas               | `cd apps\api-server; ..\..\.venv\Scripts\python.exe -m alembic upgrade head`            |
| `.\.venv\Scripts\python.exe -m api_server.seeds` | Siembra las 6 KB built-in + 5 categorías bajo el platform tenant con `is_builtin=true`. |
| Login como `tenant_admin`                        | p.ej. `admin-06-8@example.com` / `demo-06-8-admin` (seed de 06.8).                      |
| Un segundo tenant + user (para el test 03)       | Reusa el seed de 06.8 si tiene tenant-b, o crea uno por API.                            |

> El catálogo built-in **no tiene contenido (chunks) todavía** — eso es
> el Plan 06.13. Estos tests validan **visibilidad/permisos**, no
> retrieval. El retrieval de built-ins se valida en 06.13.

## `human_06_12_01` — KB built-in visible y grantable

**Qué prueba**: el catálogo built-in aparece en el panel del tenant con
badge, sin botones de editar/borrar, y se puede conceder a un proyecto.

**Cómo ejecutarlo**:

1. Login como `tenant_admin`.
2. Sidebar → **Knowledge Bases** (`/admin/knowledge-bases`).
3. **Verifica**: aparecen las 6 KB del catálogo (Python + FastAPI
   conventions, Node + Express, PHP + Symfony, PostgreSQL best
   practices, React + Next.js, API REST design guidelines) **agrupadas
   por categoría** y con un **badge "Built-in"**.
4. **Verifica**: en cada KB built-in hay botones **Grant** y
   **Asignaciones**, pero **NO** los de editar (lápiz) ni borrar
   (papelera).
5. Click **Grant** en "Python + FastAPI conventions" → elige un proyecto
   → "Otorgar acceso".
6. Entra en ese proyecto → sub-sección **Knowledge Bases** → **verifica**
   que la KB built-in aparece ahí.

**✅ Pasa si**: las 6 built-in se ven con badge, sin editar/borrar, y el
grant a proyecto funciona.

## `human_06_12_02` — Built-in es read-only desde la API

**Qué prueba**: la RLS impide que un tenant mute el catálogo, no solo la
UI.

**Cómo ejecutarlo** (PowerShell, con el JWT de tu sesión `tenant_admin`):

```powershell
$token = "<pega-tu-JWT>"   # de localStorage 'agentic.token' en el navegador
$kbId  = "<id-de-una-KB-built-in>"  # cópialo de la respuesta de GET /knowledge-bases
$h = @{ Authorization = "Bearer $token" }

# PUT debe fallar (la policy de aislamiento bloquea filas del platform tenant)
try { Invoke-RestMethod -Method Put -Uri "http://localhost:8001/knowledge-bases/$kbId" `
  -Headers $h -ContentType application/json -Body '{"name":"hack"}' } catch { $_.Exception.Response.StatusCode }

# DELETE debe fallar igual
try { Invoke-RestMethod -Method Delete -Uri "http://localhost:8001/knowledge-bases/$kbId" `
  -Headers $h } catch { $_.Exception.Response.StatusCode }
```

**✅ Pasa si**: ambos devuelven error (404/403) y la KB built-in sigue
intacta en `GET /knowledge-bases`.

## `human_06_12_03` — Aislamiento cross-tenant intacto

**Qué prueba**: migrar `kb_categories` y exponer el catálogo no filtró
datos entre tenants.

**Cómo ejecutarlo**:

1. Como **tenant A**, crea una KB propia (botón "Crear KB", p.ej.
   "Privada de A").
2. Logout → login como un user de **tenant B**.
3. Sidebar → **Knowledge Bases**.
4. **Verifica**:
   - "Privada de A" **NO** aparece para B.
   - Las 6 KB built-in **SÍ** aparecen para B (catálogo común).
   - En `/admin/knowledge-bases/categories`, las 5 categorías built-in
     (Stack, Rol, Compliance, Arquitectura, Proceso) aparecen para B con
     badge "Built-in".

**✅ Pasa si**: la KB de A es invisible para B, pero el catálogo built-in
(KBs + categorías) es visible para ambos.
