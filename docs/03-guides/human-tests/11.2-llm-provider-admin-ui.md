# Plan 11.2 — tests humanos

Esta guía cubre los **3 tests humanos** del Plan 11.2 (UI de
administración de proveedores LLM — ADR 0028). Validan lo que los e2e
Playwright escritos pero no ejecutados no pueden cubrir: que un
**System Admin configura un proveedor desde la UI y prueba la conexión**
(con el secreto solo en Vault, nunca devuelto), que el **Device Flow de
Copilot** completa y deja el token en Vault, y que el **runtime usa la
config de BD** con fallback limpio al env cuando se desactiva la fila.

> **Estado del plan**: `pending_human_validation`. Las 7 tareas
> (`task_11_2_01`..`task_11_2_07`) están en verde (tabla `llm_providers`
> platform-global + migración reversible, backend CRUD `system_admin` +
> Vault + test-connection, Device Flow de Copilot que acuña token a
> Vault, cableado del factory de runtime DB+Vault con fallback env,
> página `/admin/llm-providers`, asociación modelo→proveedor en
> `model_prices`, docs/ADR 0028). Los e2e Playwright
> (`llm-providers.spec.ts`) están escritos pero NO ejecutados — estos 3
> tests humanos son el último paso antes de pasar a `completed`.

## TL;DR

No hay `setup_demo_11_2.py` ni launcher dedicado para este plan: los
tests necesitan Vault vivo, un endpoint Ollama (o un endpoint inventado
para el caso de error) y, para Copilot, una cuenta de GitHub real. El
setup es manual:

```powershell
.\scripts\dev\up.ps1     # api-server :8001 + admin-panel :3000 + postgres + redis + vault
```

La pantalla nueva (RoleGuard `system_admin`, en el menú lateral) y la
pantalla de catálogo donde se ve la asociación modelo→proveedor:

```
http://localhost:3000/admin/llm-providers     # lista + crear/editar por kind + probar conexión + Device Flow Copilot
http://localhost:3000/admin/model-prices        # catálogo con el proveedor asociado a cada modelo (lectura)
```

Las credenciales viven en Vault bajo `secret/platform/llm/<provider_id>`
— la API **nunca** las devuelve (write-only).

## `human_11_2_01` — Configurar un proveedor desde la UI y probar conexión

**Qué prueba**: como System Admin se crea un proveedor Ollama con su
endpoint y se guarda, 'probar conexión' responde OK (o error claro si el
endpoint no existe), un Tenant Admin NO ve la página, y el secreto queda
en Vault sin que la API lo devuelva nunca.

**Precondiciones**:

- Login como `system_admin`.
- Un endpoint Ollama alcanzable (para el caso OK) — o uno inexistente a
  propósito (para el caso de error).
- Acceso de lectura a Vault para verificar el secreto.

**Pasos**:

1. Como `system_admin`, ve a `/admin/llm-providers`.
2. **Crea un proveedor** de `kind` **Ollama**: rellena `display_name` +
   `base_url` (su endpoint) + la credencial si aplica. Guarda.
3. Pulsa **'probar conexión'** (`POST .../{id}/test`):
   - Con un endpoint válido → responde **OK**.
   - Con un endpoint inexistente → responde **error clasificado y claro**
     (no un stack trace).
4. Cierra sesión y entra como **`tenant_admin`**: la página
   `/admin/llm-providers` debe estar **oculta en el menú** y, si navegas
   a la URL directamente, dar **403** (RoleGuard `system_admin`).
5. En **Vault**, comprueba `secret/platform/llm/<provider_id>`: el
   secreto está ahí. En la **respuesta de la API** (GET del proveedor) la
   credencial **nunca** aparece (solo `secret_vault_path`).

**Resultado esperado**: el proveedor se crea, 'probar conexión' da OK o
error claro, el tenant_admin no accede, y el secreto vive solo en Vault
sin eco en la API.

**Checklist**:

- [ ] Como system_admin, crear un proveedor Ollama con su endpoint y
      guardar funciona.
- [ ] 'Probar conexión' responde OK (o error claro si el endpoint no
      existe).
- [ ] Como tenant_admin, NO ve la página (403/oculta).
- [ ] En Vault (`secret/platform/llm/<id>`) el secreto está; la API nunca
      lo devuelve.

**Pitfalls conocidos**:

- El secreto es **write-only**: el formulario lo manda como `SecretStr`,
  se escribe en Vault y en BD solo queda `secret_vault_path`. Si la
  respuesta de la API devuelve la credencial, es un fallo de seguridad a
  reportar.
- Si 'probar conexión' falla con un proveedor que crees válido, comprueba
  que **Vault está unsealed** — el `/test` lee el secreto de Vault para
  hacer la llamada mínima; sin Vault no hay credencial.
- La escritura va por el **engine BYPASSRLS** de los endpoints
  `system_admin` (la tabla es platform-global, sin RLS): un 403 al
  tenant_admin es el comportamiento correcto, no un bug.

## `human_11_2_02` — Device Flow de Copilot

**Qué prueba**: iniciar el device flow de GitHub Copilot desde la UI
muestra el `user_code` + `verification_uri`, y tras autorizar en GitHub el
polling completa y el token queda en Vault.

**Precondiciones**:

- Login como `system_admin`.
- Una cuenta de GitHub con acceso a Copilot para autorizar el device
  flow.
- Acceso de lectura a Vault.

**Pasos**:

1. En `/admin/llm-providers`, inicia el **Device Flow de Copilot**
   (`POST /admin/llm/copilot/device-flow/start`): la UI muestra un
   **`user_code`** y una **`verification_uri`**.
2. Abre la `verification_uri` en GitHub, introduce el `user_code` y
   **autoriza** la app.
3. La UI hace **polling** (`…/poll`) hasta que GitHub confirma: cuando
   autorizas, el polling **completa**.
4. El backend **acuña el token** de Copilot y lo guarda en **Vault** del
   proveedor. Verifícalo en Vault (`secret/platform/llm/<provider_id>`).

**Resultado esperado**: la UI muestra user_code + verification_uri, el
polling completa tras autorizar, y el token queda en Vault.

**Checklist**:

- [ ] Iniciar device flow desde la UI muestra user_code +
      verification_uri.
- [ ] Tras autorizar en GitHub, el polling completa y el token queda en
      Vault.

**Pitfalls conocidos**:

- El polling respeta el **intervalo** que devuelve GitHub: si haces poll
  más rápido, GitHub responde `slow_down`. La UI debería gestionarlo; no
  refresques a mano más rápido que el intervalo.
- El device flow reusa la lógica de
  `shared-llm/providers/copilot.py`: si falla la acuñación, mira el log
  del api-server por el paso `mint token`.
- El `user_code` **caduca** (ventana corta): si tardas en autorizar,
  reinicia el flujo desde la UI.

## `human_11_2_03` — El runtime usa la config de BD

**Qué prueba**: con un proveedor activo en BD, un agente que lo use toma
`base_url` + credencial de BD/Vault (no del env); si se desactiva la
fila, el runtime vuelve al fallback de env sin romper.

**Precondiciones**:

- Un proveedor creado y **activo** (`is_active = true`) en
  `/admin/llm-providers`, con su secreto en Vault.
- Un agente configurado para usar ese `kind` de proveedor.
- Conocer la config de env/installer actual (el fallback) para
  contrastar.

**Pasos**:

1. Con el proveedor **activo** en BD, lanza un agente que lo use.
   Comprueba (log del runtime / agent-runtime) que el `model_from_spec`
   toma el **`base_url` + credencial de `llm_providers` + Vault**, no del
   entorno.
2. **Desactiva** la fila (`is_active = false`) desde
   `/admin/llm-providers`.
3. Vuelve a lanzar un agente del mismo `kind`: el runtime debe **volver
   al fallback de env/installer** sin romper (la fila activa gana; sin
   fila activa, manda el env).
4. Confirma el **orden de precedencia** documentado: fila activa en BD >
   env/installer.

**Resultado esperado**: con fila activa, el runtime usa BD+Vault; al
desactivarla, cae al fallback env sin errores.

**Checklist**:

- [ ] Con un proveedor activo en BD, un agente que lo use toma
      base_url+credencial de BD/Vault (no del env).
- [ ] Si se desactiva la fila, vuelve al fallback de env sin romper.

**Pitfalls conocidos**:

- La migración es **aditiva** y el factory mantiene el **fallback a
  env/installer**: si no hay fila (o está inactiva), el arranque actual
  no se rompe — ese es justamente el comportamiento que valida el step 3.
- Si el agente sigue usando el env con la fila activa, comprueba que la
  fila está **`is_active = true`** y que su `secret_vault_path` resuelve
  en Vault (un secreto ausente puede degradar al fallback).
- El `tenant_admin` sigue eligiendo `agents.llm_provider` +
  `agents.llm_model` (Plan 06.8), pero **no toca proveedores**: el `kind`
  del agente debe casar con un proveedor configurado por el System Admin.

## Troubleshooting

| Síntoma                                         | Causa probable                                          | Fix                                                                    |
| ----------------------------------------------- | ------------------------------------------------------- | ---------------------------------------------------------------------- |
| 'Probar conexión' falla con un proveedor válido | Vault sealed o `secret_vault_path` no resuelve          | Unseal Vault (`init-vault.ps1`); recrea el proveedor para reescribir   |
| La API devuelve la credencial                   | (No debería) bug de write-only — repórtalo              | El GET solo debe exponer `secret_vault_path`, nunca el secreto         |
| El tenant_admin ve `/admin/llm-providers`       | RoleGuard mal aplicado — repórtalo                      | Debe ser 403/oculta; la escritura va por engine BYPASSRLS system_admin |
| El device flow nunca completa                   | `user_code` caducado o poll más rápido que el intervalo | Reinicia el flujo; respeta el `interval` de GitHub                     |
| El runtime ignora la fila activa de BD          | Fila `is_active=false` o secreto ausente en Vault       | Activa la fila; verifica el secreto en `secret/platform/llm/<id>`      |
| Desactivar la fila rompe el agente              | (No debería) el fallback env no se aplicó               | Confirma el orden de precedencia: fila activa > env; revisa el factory |

Errores transversales viven en `docs/03-guides/gotchas/`.
