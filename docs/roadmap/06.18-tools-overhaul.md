# Plan 06.18 — Tools: UI clara, sin duplicados y cableado real del runtime

> **Origen:** auditoría intensa y verificada del subsistema de tools (UI/affordances, duplicados,
> modelo de catálogo, flujo asignación→runtime, comandos/runtime/MCP) sobre el código ya
> implementado. El operador reporta dos cosas concretas: la UI de tools **"no se ve bien, no se
> sabe si algo es clickable"** y hay **"tools duplicadas"**. La auditoría confirma que ambas son
> síntomas de una causa de fondo más grave: **el catálogo del que se asigna no corresponde con lo
> que el runtime ejecuta** (tres espacios de nombres divergentes), de modo que cualquier tool
> distinta de `shell_exec` termina en un `unknown tool` silencioso.

## Resumen

El subsistema de tools está **roto de extremo a extremo entre tres capas que no comparten una
fuente única de nombres**: el **catálogo** (`seeds/builtin_tools.py`: `read_file`/`write_file`/
`http_get`…), los **chat-modes** (`chat/modes.py`: `file_read`/`file_write`/`http_request`…) y el
**runtime ejecutable** (`agent_runtime/file_tools.py`: `file_read`/`file_write`…). El boot real del
agente (`agent_runtime/__main__.run_task`) solo monta `default_registry()` = `echo`+`noop` +
`shell_exec` condicional; toda la infra del Plan 06.16 (`tool_wiring.WiringContext`,
`register_tool_specs`, `resolve_run_runtime_image`) **existe y está testeada en aislado pero está
muerta en producción** (el orquestador ni siquiera serializa los `ToolSpec` ejecutables: solo emite
`allowed_tools` como lista de **nombres**). Consecuencia: **el operador asigna `read_file`/
`run_pytest`/`git_commit`/`http_get` desde una UI cuidada y el motor solo ejecuta `echo`/`noop`/
`shell_exec`**; cualquier otra tool cae en `ToolResult(ok=False, 'unknown tool')` absorbido como
paso normal. La única cadena que funciona hoy es `shell_exec` + `allowed_commands`.

Sobre esa base falsa, la UI hereda problemas de **affordance** verificables (área de hover ≠ área de
click, `cursor-pointer` incondicional incluso en solo-lectura, estado seleccionado invisible, badges
informativos que parecen botones, control "Seleccionar todas" disfrazado de enlace, dos pantallas con
badges divergentes que renderizan enums crudos, rutas muertas a `/tools`) y de **vocabulario** (KBs
usa "Grant KB", tools usa "Guardar", sin verbo único). Las **"tools duplicadas"** que ve el operador
son el mismo nombre lógico **triplicado** en los tres namespaces, más la ausencia de
`UNIQUE (tenant_id, name)` que permite homónimos built-in↔custom.

Este plan endurece el subsistema de tools **de raíz y en este orden**: primero la **verdad backend**
(fuente única de nombres + cableado real del runtime + deduplicación), luego la **verdad visible**
(endpoint de "set efectivo" + catálogo navegable), y encima la **UI clara** (affordances + taxonomía
visual consistente). Expone el contrato `effective-tools` que **06.17** consumirá en el Hub de
Capacidad, sin duplicar trabajo. Prioridad explícita del operador: la categorización/asignación de
tools debe ser **UI-amigable e intuitiva**.

## Alcance

**Entra**:

- **Fuente única de nombres de tool** (`packages/shared-domain`) importada por catálogo, chat-modes,
  `approval` y los `register_*` del runtime, con capa de alias retrocompatible (no rename duro) y
  validación que impida intersecciones vacías silenciosas (ADR 0048).
- **Deduplicación de datos**: `UNIQUE (tenant_id, name) WHERE deleted_at IS NULL` en `tools`
  (migración reversible), `CHECK`/enum para `category`/`security_level`/`implementation_type`, y
  `409`/`422` en `create_tool`/`PUT` ante colisión o nombre no ejecutable.
- **Cableado real del runtime** (`agent_runtime/__main__.run_task`): el framework de wiring
  (`tool_wiring`) + registro de **todas** las familias de tools (file/git/runtime/red/notificación/
  orquestación/conocimiento/memoria/MCP) con nombres canónicos; el orquestador serializa los
  `ToolSpec` ejecutables (no solo nombres); `approval.DEFAULT_TOOL_CATEGORIES` alineado a los nombres
  canónicos (cierra el bypass latente de aprobación); punto **único** de intersección agente∩modo.
- **Endpoint de "set efectivo"** `GET /agents/{id}/effective-tools` (asignadas ∩ modo + `shell_exec`
  si `allowed_commands` no vacío + flag `executable_in_runtime`) y reescritura del diagnóstico para
  consumirlo (corrigiendo el texto que hoy miente sobre disponibilidad). **Contrato de frontera con
  06.17.**
- **Endpoint `GET /runtime-templates`** que proyecta `shared_test_runtimes.CATALOG` (label ES+EN),
  eliminando el triple-hardcodeo divergente (12 vs 14) del frontend; `field_validator` de
  `default_runtime_template`.
- **UI de tools clara** (la prioridad del operador): la fila de tool como **un solo control**
  (hover == click), `cursor-pointer` solo cuando `canEdit`, estado seleccionado legible de un
  vistazo, **badges planos no-ambiguos con Tooltip accesible** (primitivo a crear), control bulk
  como checkbox tri-state, feedback de guardado consistente; **taxonomía visual de tres facetas**
  (Función · Seguridad · Origen) en un módulo compartido importado por asignación y diagnóstico.
- **Catálogo navegable** `/admin/tools` (faceted browse + CRUD de custom, built-in read-only) con
  entrada "Catálogo" en el sidebar; cierre de la ruta muerta `/tools`.
- **MCP**: importación `discovery → catálogo` (upsert de filas `Tool` `mcp_tool` con nombre
  namespaced `<server>.<tool>`) y threading de `project.mcp_servers` al runtime (ADR 0052).
- **Skills**: implementación end-to-end o deprecación, según ADR 0050.
- **Tests de contrato** que crucen `builtin_tools.py` ↔ `chat/modes.py` ↔ `approval.py` ↔ conjunto
  registrable del runtime + e2e que asigne una tool real y verifique su ejecución; actualización de
  ADR 0044/0045/0025 y docs de tools.

**Queda fuera**:

- El **Hub de Capacidad** y el modelo conceptual `SABER/RECORDAR/SER/HACER` → **Plan 06.17** (06.18
  expone `effective-tools`; 06.17 lo presenta en el Hub).
- El **cableado de RAG/memoria a nivel de api-server/worker** (query-embedder en `rag-search`/
  `memory-recall`, back-fill de embeddings) → **06.17**. 06.18 solo **registra** las familias
  `rag`/`docling`/`memory` en el boot del runtime para que existan como tools ejecutables.
- **Motor de guardrails** (pre/post LLM/tool) → Plan 11. 06.18 solo garantiza que la unificación de
  nombres **no debilite** el gate de aprobación existente (`approval.py`).
- **Auto-detección de stack** del repo (ADR 0045) → diferida; 06.18 solo expone el endpoint de
  runtime-templates.
- **Re-embedding masivo** de KBs (Plan 12) y migración de `model_config` a esquema relacional.

## Decisiones clave

- **Verdad antes que pintura**: la UI no se arregla puliendo pantallas si el motor no ejecuta lo
  asignado. Por eso el orden es **nombres únicos → cableado del runtime → set efectivo → UI**.
- **Una sola fuente de nombres** en `shared-domain` con **alias retrocompatible** (no rename duro):
  no rompe agentes existentes y elimina las intersecciones vacías silenciosas (ADR 0048).
- **El runtime es el dueño del boot**: 06.18 posee `__main__.run_task` (registra todas las familias,
  incluidas rag/docling/memory). 06.17 **no toca** ese fichero → cero conflicto entre planes.
- **Disponibilidad honesta**: el catálogo no ofrece como asignable lo que terminará en `unknown
tool`; las categorías sin motor (p. ej. `git`) se marcan "No disponible aún" o se retiran (ADR 0049).
- **Taxonomía de tres facetas ortogonales** (Función / Seguridad / Origen), con Origen separado del
  mecanismo de ejecución (hoy `implementation_type==mcp_tool` hace doble función) (ADR 0049).
- **Verbo único "Asignar/Quitar"** y una sola mecánica de interacción (tarjeta-fila) en todas las
  superficies de capacidad; etiquetas ES+EN servidas desde el backend.
- **Sin hardcode**: el catálogo de runtime templates y las etiquetas de taxonomía se sirven por
  endpoint; tunables (p. ej. multiselección de import MCP) configurables por operador. Migraciones
  reversibles. Tests `cross_tenant` por endpoint nuevo. Sin auto-retry.

## Notas de proceso y frontera

- **Frontera con 06.17** (no duplicar): 06.18 **produce** la verdad sobre tools (UI, datos, ejecución)
  y expone `GET /agents/{id}/effective-tools` y `GET /runtime-templates`. **06.17 los consume** en el
  Hub de Capacidad (sección HACER) y no recalcula la intersección ni toca el boot del runtime. Regla:
  si toca mecánica/datos/ejecución/UI **de tools** → 06.18; si toca cómo el Hub **narra** capacidades
  ya resueltas → 06.17.
- **Orden recomendado**: 06.18 (al menos Fases 0-B) **antes** de la parte HACER/Hub de 06.17, porque
  06.17 depende del contrato `effective-tools` y de que el runtime ejecute lo asignado.
- **Solo 06.18 toca `__main__.run_task`**: evita conflictos de fichero con 06.17 (que no toca el boot
  del runtime). 06.18 registra ahí también las familias rag/docling/memory para que existan como
  tools; 06.17 provee el endpoint con embedder y el back-fill.
- **Riesgos**: (1) cablear `register_*` puede activar comportamientos latentes (timeouts/egress) →
  feature-flag por familia con default backward-compat de 06.15; (2) unificar nombres podría romper
  agentes existentes → alias retrocompatible (no rename duro); (3) alinear `approval` a nombres
  canónicos es **prerequisito** de cablear `write_file`/`http_*` para no abrir el bypass de aprobación.
- **Gobernanza**: al activar el plan, verificar que ninguna otra fase esté `in_progress`. Los números
  de ADR (0048-0052) son sugeridos; se confirman en Fase 0 según el orden real de ejecución respecto a
  06.17 (cuyos ADRs van como 0053-0055).
