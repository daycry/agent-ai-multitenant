## Resumen

El modelo de roles existe en BD pero no se aplica en la mayoría de
endpoints. Hoy `tenant_user` y `tenant_admin` son funcionalmente
equivalentes: cualquier usuario autenticado del tenant puede crear/
editar/borrar proyectos, agentes, teams, MCP servers, KBs y tareas.
Solo `tenant-settings` y `memorias (scope=global)` chequean el rol.

Este plan **cierra ese gap**:

1. Audita todos los endpoints actuales contra la matriz de roles.
2. Aplica gates (`require_tenant_admin`, `require_tenant_member`,
   `require_tenant_role(role)`) consistentemente.
3. Expone `GET /me` con `{user_id, email, is_system_admin,
memberships: [{tenant_id, role, is_active}]}` para que la UI
   sepa qué puede mostrar.
4. La UI consume `/me` al cargar y oculta/deshabilita botones según
   el rol del usuario en el tenant activo.
5. Documenta la matriz de roles en `docs/04-reference/rbac.md` y la
   guía de usuario en `docs/03-guides/roles-y-permisos.md`.

Es bloqueante para:

- **Self-service de credenciales MCP** (Plan 06.6 follow-up): añadir
  `POST /credentials` sin RBAC dejaría que cualquier `tenant_user`
  escriba en Vault, lo opuesto al diseño.
- **Plan 09 (marketplace)**: install/uninstall de paquetes del
  marketplace debe ser `tenant_admin`.
- **Plan 15 (instalador prod)**: la primera cuenta tras bootstrap
  debe ser claramente `tenant_admin` y todo lo que añada
  `tenant_user` por defecto.

## Alcance

**Entra**:

### Backend — auditoría y gates

- **Matriz de roles → endpoints** en
  `docs/04-reference/rbac.md` con una tabla por router:
  ```
  | Endpoint                       | Acción | Mínimo rol     |
  |--------------------------------|--------|----------------|
  | POST /projects                 | crear  | tenant_admin   |
  | PUT  /projects/{id}            | editar | tenant_admin   |
  | DELETE /projects/{id}          | borrar | tenant_admin   |
  | GET  /projects                 | listar | tenant_member  |
  | POST /projects/{id}/mcp-servers| editar | tenant_admin   |
  | POST /projects/{id}/tasks      | crear  | tenant_member  |
  | PUT  /tasks/{id}/status        | mover  | tenant_member  |
  | ...                            |        |                |
  ```
  Sirve como contrato — los tests integration la pinean.
- **Helpers `auth/deps.py`**:
  - `require_tenant_member()` — basta con membership activa.
  - `require_tenant_admin()` — solo TENANT_ADMIN o system_admin.
    Mover el helper actual de `tenant_settings.py` aquí.
  - `require_tenant_role(role: UserRole)` — parametrizable.
- **Aplicar gates** en todos los `POST/PUT/DELETE` de recursos del
  tenant. Conservar lectura (`GET`) accesible a `tenant_member`.
- **Tests integration cross-rol** — uno por endpoint que verifica:
  `tenant_user` → 403, `tenant_admin` → 2xx, `system_admin` → 2xx.

### Backend — endpoint `/me`

- `GET /me` devuelve:
  ```json
  {
    "user_id": "uuid",
    "email": "user@example.com",
    "full_name": "string | null",
    "is_system_admin": false,
    "memberships": [
      {
        "tenant_id": "uuid",
        "tenant_name": "Acme Corp",
        "role": "tenant_admin",
        "is_active": true
      }
    ],
    "active_tenant_id": "uuid | null"
  }
  ```
- Cache headers `Cache-Control: private, max-age=60` — la UI invalida
  al cambiar de tenant.

### Frontend — UI guards

- **Hook `useCurrentUser()`** que consume `/me` (TanStack Query con
  staleTime 5 min). Expone helpers:
  - `isSystemAdmin: boolean`
  - `isTenantAdmin: boolean` (en el tenant activo)
  - `isTenantMember: boolean`
  - `roleInActiveTenant: UserRole | null`
- **Componente `<RoleGuard>`**:
  ```tsx
  <RoleGuard min="tenant_admin" fallback={<DisabledButton tooltip="…" />}>
    <Button>Crear proyecto</Button>
  </RoleGuard>
  ```
  Para casos simples; para casos complejos el hook directo.
- **Aplicar en componentes de admin-panel** existentes:
  - Crear/Editar/Borrar proyecto → `tenant_admin`
  - Crear/Editar/Borrar agente → `tenant_admin`
  - Crear/Editar/Borrar team → `tenant_admin`
  - Editar MCP servers → `tenant_admin`
  - Crear KB → `tenant_admin`
  - Borrar memoria global → `tenant_admin`
  - Crear/Mover task → `tenant_member` (todos pueden)
  - Comentar en plan → `tenant_member`
- **Sidebar**: items "Settings", "Tasks escaladas", "Roles" solo
  visibles a `tenant_admin`.
- **Indicador de rol** en la cabecera del admin-panel: badge "admin"
  / "user" al lado del email para que el usuario sepa qué puede hacer.

### Documentación

- `docs/04-reference/rbac.md` — matriz por endpoint (la doc de
  referencia técnica).
- `docs/03-guides/roles-y-permisos.md` — guía de usuario en lenguaje
  natural: "qué puede hacer un user", "qué puede hacer un admin",
  "cómo le doy admin a alguien" (con screenshots cuando exista la
  UI para gestionar memberships, plan 06.8.b o follow-up).
- Actualizar `docs/03-guides/configurar-mcp-server.md` con la nota
  "esta operación requiere rol tenant_admin".

**Queda fuera**:

- UI para **gestionar memberships** (asignar/revocar admin a otros
  usuarios). Hoy se hace vía SQL/API directa, y la UI tocaría
  `/admin/users` que es tarea de plan 06.9 o follow-up.
- **Refresh automático** del JWT cuando cambia el rol — el usuario
  hace logout/login para refrescar memberships. Mejora futura.
- Soporte para roles **custom** por tenant (e.g., "qa_lead") — el
  enum sigue siendo fijo (admin/user/system_operator).
- **Audit log** de operaciones gateadas — ya existe `audit_log`;
  este plan no añade entries nuevos, solo aplica gates a los
  endpoints existentes.

## Decisiones clave

- **Enum cerrado**, no roles dinámicos. Tres valores: `tenant_admin`,
  `tenant_user`, `system_operator`. `is_system_admin` es boolean en
  `users`, separado de las memberships. Añadir un cuarto rol requiere
  ADR y migration.
- **`tenant_member` no es un rol** — es el predicado "tiene membership
  activa, sea cual sea el rol". Lo usamos en `require_tenant_member()`
  como criterio mínimo.
- **GET es público para members**, mutaciones requieren `tenant_admin`.
  Hay excepciones: crear/mover tasks lo hace cualquier member
  (porque ese es el trabajo del día a día); editar la configuración
  del proyecto es del admin.
- **system_admin pasa todo siempre**. No vamos a inventar un rol
  "system_operator más fino" — lo dejamos como flag global y punto.
- **Frontend no es fuente de verdad**. Aunque la UI oculte botones, el
  backend valida igual con su `require_*` helper. Auth en cliente es
  UX, no seguridad.
- **El rol se computa al hacer login y va en el JWT** — no se mira la
  BD en cada request, eso ya lo hace el server-side session check.
  Cambiar rol = re-login del usuario.
