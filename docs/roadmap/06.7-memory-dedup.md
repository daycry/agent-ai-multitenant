## Resumen

Dos cosas relacionadas:

1. **Detector de memorias similares (Nivel 1)**: endpoint pgvector
   que devuelve top-K candidatos por coseno, con UI accionable
   (fusionar / descartar) en `/admin/memories`. Sin LLM en el path
   — el % es coseno directo, la decisión es del humano.

2. **Sistema de tenant-settings genéricos categorizados**: tabla
   `tenant_settings(tenant_id, category, key, value)` + endpoint
   genérico `GET/PUT /tenant-settings/{category}/{key}` + página
   `/admin/settings` con cards por categoría (cada una con su
   icono lucide-react). Necesaria porque el threshold + limit del
   detector deben ser configurables y el sistema actual de settings
   (una columna en `organizations` por feature) no escala.

`hourly_rate` se queda donde está — no migramos lo que funciona. La
página `/admin/settings/hourly-rate` existente sigue activa; el nuevo
`/admin/settings` la enlaza desde la card de la categoría "Costes".

## Alcance

**Entra**:

### Settings genéricos

- **Tabla Alembic** `tenant_settings(tenant_id, category, key, value
JSONB, updated_at, updated_by_user_id, PK(tenant_id, category, key))`.
- **Registry de settings conocidos** en código
  (`api_server/settings_registry.py`) que mapea cada `(category,
key)` a `{type, default, description_es, validator, icon, label}`.
  La UI lo lee vía endpoint y genera formularios sin hardcodear.
- **Endpoints**:
  - `GET /tenant-settings/_registry` → todo el registry serializado
    (lo lee la UI para pintar cards + formularios).
  - `GET /tenant-settings/{category}` → todas las keys de esa
    categoría dentro del tenant (los valores set por el usuario).
  - `GET /tenant-settings/{category}/{key}` → valor único; 404 si no
    está → caller usa el default code-side.
  - `PUT /tenant-settings/{category}/{key}` body `{ value }` →
    upsert con validación contra el registry. Sólo `tenant_admin`.
- **Helper Python** `get_setting(session, tenant_id, category, key)`
  que abstrae lectura + default.

### Iconos por categoría

Cada categoría tiene un icono lucide-react declarado en el registry.
El nombre se serializa como string ("Brain", "Coins", …) y la UI
mapea string → componente. La UI usa ese icono en:

- La card de la categoría en `/admin/settings` (index).
- El `PageHeader` de la página de cada categoría.

Categorías iniciales:

```
memories  → "Brain"   (lucide-react)
costs     → "Coins"   (link a la página dedicada de hourly-rate)
```

### Detector de memorias

- `GET /memories/{id}/similar` — lee `memories.similarity.threshold`
  - `memories.similarity.limit` del tenant settings (defaults 0.85 y
    5 del registry), corre pgvector cosine query restringida al
    scope+tenant del row origen, devuelve `[{memory, similarity}]`.
- `POST /memories/{id}/merge-into` body `{ target_id }` — funde
  content + tags en target, soft-deletes el origen, anota
  `metadata.merged_from` en target.

### UI

- `/admin/settings/page.tsx` — index categorizado con cards por
  categoría conocida (consume `GET /tenant-settings/_registry`).
- `/admin/settings/memories/page.tsx` — formulario para
  `similarity.threshold` (slider 0.5-0.99) + `similarity.limit`
  (number 1-20).
- `/admin/memories/page.tsx` — añadir botón "Ver similares" por
  row + modal con candidatos + botones Fusionar/Descartar.
- Sidebar: el item "Settings" pasa a apuntar a `/admin/settings`
  (no a `/admin/settings/hourly-rate`).

**Queda fuera**:

- Detección automática al insertar (sería un cambio del Memorizer
  pipeline; queda para Plan 06.5 o follow-up).
- Nivel 2 (LLM en la zona gris) — explícitamente fuera.
- Re-embed post-fusión (la memoria target conserva su embedding
  antiguo; el Memorizer re-embeb la próxima vez que se actualice).
- Migración de `hourly_rate` al sistema genérico.

## Decisiones clave

- **Registry de settings conocidos en código, no en BD**. El PUT
  rechaza keys no listadas. Esto da:
  - Type safety en backend (`get_setting` devuelve el tipo correcto).
  - UI generable automáticamente.
  - No hay key/value libre que termine siendo basura.
  - Migrar a key nueva = añadir al registry, no Alembic.
- **value JSONB**, no string. Soporta float, int, string, dict.
- **Defaults code-side, no DB-side**. Si el row no existe,
  `get_setting` devuelve el default del registry. El tenant no
  necesita haber tocado el setting para que el sistema funcione.
- **Iconos como strings**, no objetos importados. El registry vive
  en backend y se serializa por JSON — declarar el componente
  lucide-react en backend no tiene sentido. La UI tiene un mapping
  `string → component` con los iconos disponibles.
- **PUT requiere tenant_admin**. Mismo patrón que hourly-rate.
- **Fusión asimétrica de memorias**: A se funde EN B (humano elige
  B como ganador). Content = `B.content + "\n\n---\n" + A.content`;
  tags = unión; A.deleted_at = now.
