## Resumen

El operador necesita que los agentes **lancen comandos del stack del proyecto** (`php`, `composer`,
`vendor/bin/phpunit`, `pest`, `npm`, `dotnet`…), no solo Python. La verificación confirma que el motor YA es
políglota (runtime templates `php-phpunit`/`php-pest`/`dotnet-test`/`node-*`/… + `shell_exec` con allowlist por
proyecto + timeout en `agent_runtime/shell_exec.py`), pero **falta cablearlo y exponerlo**: (1) `shell_exec`
NO está en el catálogo `tools` (no asignable) y `ProjectShellExec` no se instancia con la allowlist de un
proyecto; (2) el proyecto **no tiene campos** de `allowed_commands` ni de stack/runtime; (3) los `run_*`
(`docker_command`) tienen el runtime `python-pytest` **fijo**. Este plan cierra el círculo: config de proyecto
(allowlist + runtime por defecto), `shell_exec` asignable y cableado, `run_*` resueltos por stack, y una UI
**amigable** (chips + presets por stack) para configurarlo.

## Alcance

**Entra**:

- **Config de proyecto** (migración reversible 0072): `projects.allowed_commands` (array de basenames, default
  `[]`) + `projects.default_runtime_template` (string nullable, p. ej. `php-phpunit`). ORM + schemas + create/update.
- **`shell_exec` asignable + cableado**: añadir `shell_exec` ("Ejecutar comando") al seed `builtin_tools`
  (category `command`, `security_level=privileged`, `is_builtin=true`). Cablear el runtime para instanciar
  `ProjectShellExec(allowed_commands=project.allowed_commands)` y registrarlo en el `ToolRegistry` (threading
  de `project.allowed_commands` por el spec de la tarea). Sin allowlist ⇒ shell_exec no ejecuta nada (deny-all).
- **`run_*` por stack**: `run_pytest`/`run_lint`/`run_typecheck`/`run_build` resuelven su runtime template desde
  `project.default_runtime_template` (con fallback al `implementation_ref` actual). Resolución vía
  `shared_test_runtimes.catalog.get(...)`.
- **UI amigable** (prioridad UX del operador) en `/admin/projects/[id]`: sección "Comandos & runtime" con la
  allowlist como **chips** + **presets por stack** (PHP → `php`/`composer`/`vendor/bin/phpunit`/`pest`; Node →
  `npm`/`npx`/`node`; .NET → `dotnet`; Python → `python`/`pytest`) y un selector de `default_runtime_template`.
- Tests + ADR + guía + changelog.

**Queda fuera**:

- Browser/Playwright como builtin (queda el runtime `node-playwright` + el listing de marketplace; fuera de aquí).
- Reescribir el sandbox de ejecución o los runtime templates (ya existen).
- Auto-detección del stack del proyecto (se elige manualmente; auto-detección = mejora futura).

## Decisiones clave

- **Deny-by-default**: `shell_exec` solo ejecuta binarios en `project.allowed_commands`; lista vacía ⇒ nada.
  El operador autoriza explícitamente `php`/`composer`/etc. por proyecto. Sigue siendo argv (`shlex`) + timeout.
- **`shell_exec` es básica** (`is_builtin=true`) pese a ser `privileged` — la seguridad es un eje ortogonal
  (coherente con ADR 0044). En la UI de asignación de tools (Plan 06.15) aparece en "Básicas" con badge
  `Privilegiada`.
- **Runtime por proyecto, no por tool**: el stack lo fija `project.default_runtime_template`; los `run_*` lo
  respetan con fallback. Evita duplicar tools por lenguaje.
- **UI amigable obligatoria** (memoria de feedback del operador): chips + presets, no teclear listas crudas.

## Tareas

### Fase A — Config de proyecto

#### `task_06_16_01` — Campos `allowed_commands` + `default_runtime_template` en projects

- [x] **Título**: Migración reversible (0072) que añade `projects.allowed_commands` (JSONB/array text, default `[]`)
      y `projects.default_runtime_template` (text nullable). ORM + schemas (ProjectCreate/Update) + endpoints que
      los aceptan/devuelven. Tenant-scoped (RLS de projects ya existe).
- **Tests**: `pytest tests/integration/test_project_command_config.py -v` (create/update persisten; default `[]`; reversible)

### Fase B — shell_exec asignable + cableado

#### `task_06_16_02` — `shell_exec` en el catálogo + instanciación por proyecto

- [x] **Título**: Añadir `shell_exec` al seed `builtin_tools` (category `command`, `privileged`, builtin, con su
      input_schema `{command}`). Cablear el runtime: construir `ProjectShellExec(allowed_commands=...)` desde
      `project.allowed_commands` (threading por el spec, como el allowlist de chat-mode de 06.15/06.14) y
      registrarlo en el `ToolRegistry`. Deny-all si la lista está vacía.
- **Tests**: `pytest tests/integration/test_shell_exec_allowlist.py -v` (comando en allowlist se ejecuta; uno fuera
  → rechazado con la lista de permitidos; lista vacía → deny-all; seed expone shell_exec asignable)

### Fase C — run\_\* por stack

#### `task_06_16_03` — `run_*` resuelven runtime desde `default_runtime_template`

- [ ] **Título**: `run_pytest`/`run_lint`/`run_typecheck`/`run_build` resuelven su runtime template desde
      `project.default_runtime_template` (fallback al `implementation_ref` por defecto). Un proyecto PHP con
      `php-phpunit` ejecuta sus tests en ese runtime, no en `python-pytest`.
- **Tests**: `pytest tests/integration/test_run_tools_by_stack.py -v` (proyecto php-phpunit → runtime php-phpunit;
  sin campo → fallback python-pytest; runtime desconocido → error claro)

### Fase D — UI amigable

#### `task_06_16_04` — Sección "Comandos & runtime" en el proyecto (chips + presets)

- [ ] **Título**: En `/admin/projects/[id]`, sección "Comandos & runtime": `allowed_commands` como **chips**
      (añadir/quitar) + botones **preset por stack** (PHP/Node/.NET/Python) que rellenan los chips; selector de
      `default_runtime_template` (lista de templates disponibles). Amigable, intuitiva, accesible; estados claros.
      `tenant_admin` para editar. _(typecheck/lint/build verde; e2e escrito NO ejecutado)._
- **Tests**: `npm run typecheck && lint && build` (admin-panel) + e2e `project-commands.spec.ts` (escrito, no ejecutado)
