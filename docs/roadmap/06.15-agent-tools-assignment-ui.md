## Resumen

Hoy **no existe ninguna pantalla para asignar tools a un agente** (qué tools puede usar cada uno). El
backend tiene casi todo: catálogo de tools (`/tools` CRUD), la tabla de unión `agent_tools` (agent_id,
tool_id, config_override) y un panel de diagnóstico **solo-lectura** (`/admin/projects/[id]/agent-tools-
diagnostic`), pero `agent_tools` solo se rellena por seeds/SQL — no hay endpoint para asignar, ni sección
en el editor de agente, ni distinción **básicas vs avanzadas** en la UI. Además, el runtime hoy no filtra
el toolset por `agent_tools` (la restricción real solo existe a nivel chat-mode). Este plan cierra el hueco:
**endpoints de asignación por agente + enforcement en runtime + sección "Tools del agente" en el editor**,
con la taxonomía **básicas (builtin) vs avanzadas (custom + MCP + ejecutores)** derivada de los campos que ya
existen (`is_builtin`, `implementation_type`), sin cambio de esquema.

## Alcance

**Entra**:

- Backend `GET/PUT /agents/{id}/tools` sobre la junction `agent_tools` (escritura `tenant_admin`, lectura
  `tenant_user`). Validación de scope: las **builtin** (is_builtin, PLATFORM_TENANT_ID) son asignables a
  cualquier agente; las **custom** solo del propio tenant; las **MCP** dependen de los MCP servers del
  proyecto. `config_override` opcional por asignación.
- **Enforcement en runtime**: el toolset resuelto de un agente se filtra por su `agent_tools` cuando tiene
  asignaciones (intersectado con el allowlist del chat-mode donde aplique). **Backward-compatible**: si un
  agente no tiene filas en `agent_tools`, se mantiene el comportamiento actual (sin restricción por agente)
  para no romper agentes existentes. Punto de cableado: `agent-runtime/tool_wiring.py` + el builder del spec.
- **UI**: sección "Tools del agente" en `/admin/agents/[id]` siguiendo EXACTAMENTE el patrón de
  `AgentKbsSection` (asignación de Knowledge Bases de Plan 06.9). Pestañas **Básicas** (builtin: file/git/
  runtime/network) vs **Avanzadas** (custom + MCP + ejecutores http/python/docker), con badges de
  `security_level` (safe/sandboxed/privileged) y `implementation_type`. Estados vacío/cargando/error claros.
- Taxonomía básicas/avanzadas **derivada** de `is_builtin`/`implementation_type` (sin nuevo campo) +
  documentada en un ADR.
- Tests automáticos por tarea + docs (ADR, guía, changelog).

**Queda fuera**:

- Gestión de **custom chat modes** + su `allowed_tools` por UI (otro hueco; queda anotado).
- Reescribir el catálogo de tools `/tools` o el descubrimiento MCP (ya existen).
- Convertir `básico/avanzado` en un campo de primera clase en `Tool` (se deriva; el ADR justifica).
- `assignment_mode` u otras features de Plan 16.

## Decisiones clave

- **Scope tenant, no plataforma**: la asignación de tools a agentes es `tenant_admin` (lectura `tenant_user`),
  por proyecto/tenant. NO se mezcla con el catálogo de proveedores LLM (Plan 11.2, scope plataforma).
- **Básico/avanzado derivado, no nuevo campo**: `básico = is_builtin=true` (con CUALQUIER
  `implementation_type`); `avanzado = is_builtin=false` (custom del tenant + MCP). El `implementation_type`
  es ortogonal (un builtin `run_pytest` es `docker_command` y sigue siendo básico). Evita una migración y
  mantiene una sola fuente de verdad. Un ADR fija esta derivación.
- **Enforcement backward-compatible**: sin filas `agent_tools` ⇒ sin restricción por agente (comportamiento
  actual). Con filas ⇒ el agente solo ve/usa esas tools. Reutiliza el patrón de `AgentKbsSection` en UI y la
  ruta de `ToolRegistry` en runtime.
- **El frontend no es fuente de verdad**: la restricción real se aplica en el runtime (`ToolRegistry`); la UI
  es para configurar.

## Tareas

### Fase A — Backend: asignación por agente

#### `task_06_15_01` — Endpoints `GET/PUT /agents/{id}/tools`

- [x] **Título**: Router que lee/escribe la junction `agent_tools` para un agente: `GET /agents/{id}/tools`
      (lista de tools asignadas, `tenant_user`) y `PUT /agents/{id}/tools` (set declarativo de `tool_ids` +
      `config_override` opcional, `tenant_admin`). Validación de scope (builtin asignable siempre; custom solo
      del tenant; MCP del proyecto). Tenant-scoped por RLS vía la tabla `agents`.
- **Tests**: `pytest tests/integration/test_agent_tools_assignment.py -v` (set/replace persiste; RBAC `tenant_admin`
  para escritura; no se puede asignar custom de otro tenant; `@pytest.mark.cross_tenant`)

### Fase B — Enforcement en runtime

#### `task_06_15_02` — El toolset del agente respeta `agent_tools`

- [x] **Título**: Cablear el builder del spec + `agent-runtime/tool_wiring.py`/`tools.py` para que, cuando un
      agente tiene asignaciones `agent_tools`, su toolset resuelto se restrinja a ellas (intersectado con el
      allowlist del chat-mode donde aplique). Sin filas ⇒ comportamiento actual (no romper agentes existentes).
- **Tests**: `pytest tests/integration/test_agent_tools_enforcement.py -v` (agente con asignaciones solo ve esas
  tools; sin asignaciones ⇒ comportamiento previo; una tool no asignada se rechaza en `ToolRegistry.call`)

### Fase C — UI: sección "Tools del agente"

#### `task_06_15_03` — Sección de tools en el editor de agente
