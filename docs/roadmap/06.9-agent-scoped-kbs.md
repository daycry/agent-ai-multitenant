## Resumen

Hoy las KBs están scopeadas solo a proyecto. Eso fuerza un acople
incómodo: si quieres que `backend_dev` "sepa diseñar APIs REST", esa
KB tiene que estar granted en cada proyecto donde corre. Y si quieres
varios stacks (Python, PHP, JS) tienes la tentación errónea de
crear `backend_dev_python`, `backend_dev_php`, etc. — multiplicación
de agentes que comparten 90 % del prompt.

Este plan separa dos cosas que se han venido confundiendo:

1. **Rol del agente** (qué hace) → KBs **del agente template**.
   "API REST design principles" se attach a `backend_dev`. Se aplica
   en cualquier stack porque el conocimiento es agnóstico.
2. **Stack del proyecto** (con qué tecnología) → KBs **del proyecto**.
   "Python + FastAPI conventions" se grants al proyecto X. La graneas
   automáticamente desde la plantilla del proyecto (extensión natural
   de las 8 plantillas seedeadas que ya existen).

En tiempo de ejecución el agente consulta:

```
KBs visibles = KBs del proyecto ∪ KBs del agente template ∪ KBs globales
```

## Alcance

**Entra**:

### Backend — agent ↔ KB

- **Tabla Alembic** `agent_knowledge_bases(agent_id, kb_id, granted_by,
granted_at)` con PK compuesta + FKs ON DELETE CASCADE. RLS por
  `tenant_id` heredado del KB.
- **Endpoints** sobre `/agents/{id}`:
  - `GET /agents/{id}/knowledge-bases` → KBs que tiene atadas el agente.
  - `POST /agents/{id}/knowledge-bases` body `{kb_id}` → grant.
  - `DELETE /agents/{id}/knowledge-bases/{kb_id}` → revoke.
  - `require_tenant_admin` para los dos últimos (cambio gateado por
    Plan 06.8 cuando esté listo; mientras tanto la regla queda
    documentada y el endpoint la aplica directamente).
- **Reglas**:
  - Sólo se puede grant a un agente con scope `global_tenant_template`
    o `project_local`. Los `global_builtin` los administra el
    sistema vía seeds.
  - El `kb_id` debe ser del mismo tenant que el agente. RLS lo
    garantiza pero el endpoint devuelve 404 explícito si no.

### Backend — resolver de KBs en runtime

- **Helper `resolve_visible_kbs(project_id, agent_id) -> list[KB]`**
  que une las tres fuentes y deduplica por KB id.
- **Cambio en el flujo de retrieval**: el agent-runtime usaba
  `resolve_kbs_for_project(project_id)`. Pasa a usar el helper nuevo;
  el call site existente (`packages/agent-runtime/...`) recibe ahora
  también el `agent_id`.
- **Tests integration** que confirman:
  - Agente sin KBs propias → sólo ve las del proyecto (compat).
  - Agente con KB propia → la ve además de las del proyecto.
  - KB granteada DOS veces (al agente y al proyecto) aparece una vez.

### Backend — plantillas de proyecto declaran KBs por stack

- Extender `ProjectTemplate` (en `api_server.seeds.builtin_project_templates`)
  con un campo `default_kb_grants: list[str]` — IDs de KBs seedeadas
  por el sistema (e.g. `python-fastapi-conventions`,
  `postgresql-best-practices`).
- **Seed** `api_server.seeds.builtin_kbs.py` con un puñado de KBs
  canónicas por stack (Python+FastAPI, PHP+Symfony, Node+Express,
  …). El contenido inicial son chunks markdown del open-source
  upstream del cliente — refrescables vía nuevo seed run.
- **Wizard de creación de proyecto** (Plan 03) ya consume las
  plantillas: al crear un proyecto desde una plantilla, el backend
  hace los grants declarados en `default_kb_grants` automáticamente.

### Frontend — UI

- En el detalle del agente `/admin/agents/[id]` añadir una sub-sección
  **"Knowledge Bases"**:
  - Listado de KBs ya granted al agente.
  - Botón "Grant KB" → dialog con un `<KbCombobox>` (server-side
    search sobre `/knowledge-bases?q=`, mismo patrón que el
    `ProjectCombobox` que ya tenemos).
  - Botón "Revoke" por fila.
- En el detalle de la KB `/admin/knowledge-bases` añadir un panel
  "Asignaciones":
  - Proyectos con grant (necesita un nuevo endpoint
    `GET /knowledge-bases/{id}/projects`).
  - Agentes con grant (similar para agentes).
  - Botón "Revoke" por fila.

### Documentación

- **ADR nuevo** `docs/05-architecture-decisions/0026-agent-scoped-kbs.md`
  con la decisión "stack vive en proyecto, rol vive en agente, ambos
  tienen KBs".
- Actualizar
  [`docs/03-guides/configurar-mcp-server.md`](../03-guides/configurar-mcp-server.md)
  con un párrafo sobre cómo las KBs de stack se asignan vía plantilla.
- **Guía nueva** `docs/03-guides/knowledge-bases-rol-vs-stack.md`
  con ejemplos: cuándo crear KB de rol, cuándo crear KB de stack,
  cómo evitar duplicación, cómo refrescar contenido upstream.

**Queda fuera**:

- **KBs de team** (intermedio entre proyecto y tenant). El team ya
  tiene memorias `team_shared`, pero no KBs. Si surge la necesidad se
  añade en un follow-up — la maquinaria es idéntica.
- **Sincronización automática** de KBs canónicas con upstream
  (Python docs, FastAPI docs, etc.). Hoy son chunks indexados manualmente
  desde un fork; un cron que las refresque viene en Plan 04.5 o
  follow-up.
- **Ranking / weighting** entre las tres fuentes. En esta iteración
  se concatena y se rankea por similitud coseno como una sola lista.
  Si surge la necesidad de favorecer una fuente sobre otra, se añade
  un parámetro al retriever.
- **Versionado del catálogo de KBs canónicas**. Si la KB "Python+FastAPI"
  cambia de contenido, el agente verá la versión nueva la próxima vez
  que consulte. No hay snapshot por versión del proyecto.

## Decisiones clave

- **Rol ≠ stack**. El agente template es agnóstico de stack; la
  documentación específica del stack vive con el proyecto, no con
  el agente. Un solo `backend_dev` sirve para Python, PHP, JS, Go,
  etc. — su KB de rol ("API REST design") es la misma en todos.
- **Tres fuentes, una lista**. Al retrievar, no distinguimos de dónde
  vino cada chunk — el ranking por coseno decide. Mantener fuentes
  separadas internamente solo añade complejidad sin valor de producto.
- **Grant es una operación de admin**, no del operador del proyecto.
  Tanto agente↔KB como proyecto↔KB requieren `tenant_admin`.
- **El backend NO copia chunks** entre KBs. Si dos agentes necesitan
  la misma doc, se grants la misma KB a ambos — los chunks viven una
  sola vez en la BD.
- **Built-in agents** (los seedeados por el sistema, scope=
  `global_builtin`) NO pueden recibir grants de KBs de tenant. Si un
  tenant quiere customizar `backend_dev`, lo forkea
  (`tenant_template`) y desde ahí grants sus KBs. Mismo patrón que
  ya existe para forkear agentes.
