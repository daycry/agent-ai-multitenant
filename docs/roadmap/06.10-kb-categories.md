## Resumen

Tras Plan 06.9 las KBs pueden venir de tres fuentes (proyecto, agente,
built-in del platform). Cuando un tenant tiene 20-30 KBs (built-ins +
de stack + de rol + custom internas) el listado plano de
`/admin/knowledge-bases` se vuelve inmanejable. El usuario lo señaló
durante los tests humanos de 06.9.

Este plan añade un eje de **categoría** sobre las KBs:

- Catálogo built-in del platform con 5 categorías default (`stack`,
  `role`, `compliance`, `architecture`, `process`) seedeadas bajo
  `PLATFORM_TENANT_ID` y visibles a todos los tenants — mismo
  patrón que `approval_policy_templates_builtin_read` de Plan 01.
- Cada tenant puede **crear sus propias categorías custom** (e.g.
  "Cliente Acme", "Compliance ISO 27001"). Las custom viven en su
  tenant via RLS.
- Cada KB tiene un `category_id` FK nullable. Borrar una categoría
  no borra las KBs — `category_id` queda `NULL` (soft-detach).

En la UI, el listado de `/admin/knowledge-bases` agrupa por
categoría con secciones colapsables; el `<KbCombobox>` muestra la
categoría como descriptor secundario; y hay una nueva página
`/admin/knowledge-bases/categories` para CRUD de las custom.

## Alcance

**Entra**:

### Backend — modelo y endpoints

- **Migration Alembic** `kb_categories(id, tenant_id NULLABLE,
slug, name, color, created_by, ...)` con RLS dual:
  - Custom (`tenant_id IS NOT NULL`): policy de tenant isolation
    estándar.
  - Built-in (`tenant_id IS NULL`): policy de lectura
    incondicional para sesiones de tenant — análogo al
    `approval_policy_templates_builtin_read` de Plan 01.
- **Migration** `knowledge_bases.category_id UUID NULLABLE` con
  FK a `kb_categories(id) ON DELETE SET NULL`.
- **Endpoints**:
  - `GET    /kb-categories` — lista (built-in + del tenant). `tenant_member`.
  - `POST   /kb-categories` — crea una custom. `tenant_admin`.
  - `PUT    /kb-categories/{id}` — edita (solo custom; built-ins read-only). `tenant_admin`.
  - `DELETE /kb-categories/{id}` — soft-delete (built-ins protegidas). `tenant_admin`.
- **Extensión de `GET /knowledge-bases`** con `?category=<id|slug>`
  para filtrado server-side.
- **Extensión de `KnowledgeBaseResponse`** con `category` embebido
  (id + slug + name + color + is_builtin) — la UI lo necesita para
  agrupar sin un fetch extra.

### Backend — seed

- **`seeds/builtin_kb_categories.py`** con las 5 categorías default
  bajo `PLATFORM_TENANT_ID`. Slugs estables + UUIDs deterministas
  via `uuid5(KB_CATEGORY_NAMESPACE, slug)` — mismo patrón que el
  catálogo de KBs.
- **Actualizar `BuiltinKB`** del Plan 06.9 con un campo
  `category_slug`; el seed `seed_builtin_kbs` resuelve el slug al
  UUID al insertar.
- Categorización de las 6 KBs canónicas:
  - `python-fastapi-conventions` → `stack`
  - `node-express-conventions` → `stack`
  - `php-symfony-conventions` → `stack`
  - `postgresql-best-practices` → `stack`
  - `api-rest-guidelines` → `role`
  - `react-nextjs-conventions` → `stack`

### Frontend — UI

- **`/admin/knowledge-bases`**: render agrupado por categoría con
  secciones colapsables. KBs sin categoría caen a "Sin categoría"
  al final.
- **Modal Crear/Editar KB**: nuevo selector de categoría (dropdown
  con built-ins + custom del tenant). Opción "+ Nueva categoría"
  abre un mini-dialog inline que crea la categoría y la
  pre-selecciona.
- **Página nueva `/admin/knowledge-bases/categories`** — listado
  - create + edit + delete. Built-ins read-only con badge.
- **`<KbCombobox>`** muestra `[stack] python-fastapi-conventions`
  en el typeahead.

### Documentación

- **Update `docs/03-guides/knowledge-bases-rol-vs-stack.md`** con
  nueva sección "Cómo usar las categorías" explicando que rol/stack
  son los dos buckets más comunes pero el tenant puede añadir los
  suyos (compliance, cliente externo, etc.).
- **Update `docs/04-reference/rbac.md`** con los 4 endpoints nuevos
  - categoría en la matriz.

**Queda fuera**:

- **Sub-categorías / jerarquía**. Si una categoría custom necesita
  hijos ("Backend > APIs > REST"), se añade en un follow-up con
  `parent_id` opcional.
- **Categorías multi-KB** (una KB en varias categorías). El modelo
  es single FK; si surge la necesidad se promociona a M:N.
- **Reordenar visual de categorías** (drag-and-drop). El orden por
  ahora es alfabético + built-ins primero.

## Decisiones clave

- **Built-ins compartidas + custom per-tenant**, no per-tenant pura.
  Las built-ins evitan que cada tenant invente "stack" / "Stack" /
  "stk" para la misma idea. Mismo patrón que `BUILTIN_KBS`,
  `BUILTIN_AGENTS`, `BUILTIN_PROJECT_TEMPLATES`.
- **`category_id` NULLABLE**. Borrar una categoría no borra las KBs
  — quedan sin categoría hasta que el tenant las re-categorice. Más
  amable que ON DELETE CASCADE.
- **Single FK, no M:N**. Una KB pertenece a UNA categoría
  conceptualmente. M:N añade complejidad (tabla de junction,
  endpoints add/remove categoría) sin valor probado.
- **Soft-delete de categorías** (`deleted_at`). Si un tenant borra
  una categoría custom y luego se arrepiente, restaurarla es trivial
  (`UPDATE kb_categories SET deleted_at = NULL`). Las built-ins NO
  son soft-deletables — el sistema las re-seedea siempre.
- **Slug estable + UUID determinista** para built-ins. Re-seedear no
  rompe `kb.category_id` que apuntaba a una built-in.
