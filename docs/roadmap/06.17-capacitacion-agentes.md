# Plan 06.17 — Capacitación de agentes (SABER/RECORDAR/SER/HACER)

> **Origen:** auditoría multi-agente verificada del subsistema de "entrenamiento" de agentes/equipos/
> proyectos. El operador reporta que **hoy es difícil de ENTENDER y de USAR**. La causa raíz
> confirmada no es la UI: varias vías **parecen activas y están rotas de extremo a extremo** (el RAG
> del agente no se consulta, la memoria semántica está vacía, hay funcionalidades fantasma) y el
> conocimiento vive fragmentado en 4-6 pantallas con verbos inconsistentes y sin ningún hilo que las
> una. Este plan cierra primero las cadenas backend y luego construye un **modelo mental único** y un
> **Hub de Capacidad honesto** encima.

## Resumen

"Capacitar" en este sistema **no** es fine-tuning de pesos (los LLM son externos y de catálogo
cerrado, ADR 0021): es **dotar de CAPACIDAD** por cuatro vías —**SABER** (conocimiento/KBs+RAG),
**RECORDAR** (memoria por scopes), **SER** (persona/modelo/prompt) y **HACER** (tools/comandos)—.
Hoy esas vías viven en tablas, endpoints, pantallas y vocabularios separados sin hilo conductor, y
algunas **prometen capacidad que el motor no entrega**: el RAG del agente corre BM25-only con
`embedder=None` y la tool `rag_search` ni se cablea; el embedding de memoria nunca se rellena (recall
vectorial y "similares" vacíos); el `memory_scope` por defecto `private` hace que un agente IA **no
memorice nada en silencio**; las skills no inyectan su `prompt_fragment`. La parte de **tools/HACER**
(catálogo ≠ runtime, namespaces, UI) se aborda en su plan dedicado **06.18**; este plan la **consume**.

El plan sigue **verdad primero**: cierra las cadenas backend de SABER/RECORDAR y la **honestidad de
estado** (que nada parezca activo si no lo está), fija el **vocabulario único** como estrella polar,
y solo entonces construye el **Hub de Capacidad** por entidad, la **persona/fork** de primera clase y
la **capacidad coherente de proyecto/equipo**, cerrando con guías y un e2e del flujo completo.

## Estrella polar: Capacitar = SABER + RECORDAR + SER + HACER

> Se materializa como `docs/04-reference/training-model.md` en la Fase B y la consumen todas las
> fases de UI. Es el modelo mental único del plan.

| Categoría                | Pregunta del operador         | Mecanismo real (código)                                                                                                 | Verbo en UI            |
| ------------------------ | ----------------------------- | ----------------------------------------------------------------------------------------------------------------------- | ---------------------- |
| **SABER** (Conocimiento) | ¿Qué corpus curado consulta?  | Knowledge Bases + RAG (`agent_knowledge_bases` rol, `kb_projects` stack, catálogo global built-in)                      | **Asignar**            |
| **RECORDAR** (Memoria)   | ¿Qué recuerda entre runs?     | `MemoryEntry` por scope (private/team_shared/project_shared/global), destilada por el Memorizer                         | **Asignar/Configurar** |
| **SER** (Persona)        | ¿Quién es y cómo se comporta? | `system_prompt` + `model_config` (provider/model/temperature/prompts es+en) + skills + chat-mode                        | **Editar/Asignar**     |
| **HACER** (Acciones)     | ¿Qué puede ejecutar?          | tools (`agent_tools`) + comandos/runtime (`allowed_commands`, `default_runtime_template`) + MCP → **definido en 06.18** | **Asignar**            |

### Tabla de NIVELES (dónde se capacita qué)

| Nivel                | Etiqueta UI                                    | Qué se asigna a este nivel                                                          | Anclaje real                        |
| -------------------- | ---------------------------------------------- | ----------------------------------------------------------------------------------- | ----------------------------------- |
| **Rol / agente**     | "Conocimiento/Tools del rol del agente"        | KBs de rol, tools, skills, persona, `memory_scope`                                  | fila `agents` + junctions `agent_*` |
| **Stack / proyecto** | "Conocimiento/Comandos del stack del proyecto" | KBs de stack (`kb_projects`), `allowed_commands`, runtime, memoria `project_shared` | fila `projects` + `kb_projects`     |
| **Equipo**           | "Capacidad del equipo"                         | Composición + metadata de miembro; KB/memoria de equipo SEGÚN ADR 0053              | `teams` + `team_members`            |
| **Plataforma**       | "Catálogo global (built-in)"                   | KBs/agentes/tools built-in read-only (requieren grant o fork)                       | platform-tenant, `is_builtin`       |

### Reglas del modelo unificado

1. **Un verbo único** "Asignar/Quitar" en toda la UI ("grant" queda como término interno de datos).
2. **Un Hub por entidad** con 4 secciones (Saber/Recordar/Ser/Hacer) + estado por sección, que
   muestra el **set efectivo REAL** (la sección HACER consume `effective-tools` de 06.18; avisa si el
   agente es global y no verá conocimiento de proyecto).
3. **Nivel explícito** en cada capacidad (Rol/Stack/Equipo/Plataforma), reemplazando la jerga "rol vs stack".
4. **Honestidad de estado**: ninguna capacidad parece activa si no lo está; lo roto se marca "No
   disponible aún". **Se cierra primero (Fases 0/A/B) lo que rompe la promesa de extremo a extremo.**
5. **Fork de primera clase**: "Personalizar (crear copia)" en agente y equipo que copia KBs/tools/skills.
6. **Onboarding/checklist**: el Hub guía el orden Persona → Saber → Hacer → Recordar.

- Implementación plena de **TeamKnowledgeBase/fork de equipo** → condicionada al ADR 0053 (si mantiene
  ADR 0026, se recorta a aclaración + metadata de miembro).

## Decisiones clave

- **Verdad primero**: las cadenas backend rotas (Fase A) y la honestidad de estado (Fase B) van antes
  que cualquier UI; el Hub muestra el set efectivo y el estado **reales**, que solo existen tras A/B.
- **Fase 0 sin código**: los 3 ADRs (0053-0055) se aceptan ANTES de la tarea que dependa de cada uno.
- **06.17 no toca el boot del runtime**: depende de 06.18 para que `rag_search`/memory tools estén
  registradas; 06.17 provee el endpoint con embedder y el back-fill. Evita conflictos de fichero.
- **Tunables operator-configurable** vía `platform_settings` (default `memory_scope`, flag de reranker,
  throttle/batch del back-fill, estados elegibles de memorización, default provider/model). **Sin
  auto-retry** de runs (el back-fill es un worker dedicado idempotente). RLS + tests `cross_tenant`.
- **`model_config` legacy seguro**: validación estricta en create/update por UI; agentes existentes
  con `{}` reciben un default operator-configurable en dispatch (no fallo en arranque) + saneo por migración.

- **Frontera con 06.18** (no duplicar): 06.18 **produce** la verdad sobre tools y expone

  (sección HACER) y en la vista de capacidad del proyecto. 06.17 **no toca** el boot del runtime
  (`__main__.run_task`); depende de que 06.18 registre `rag_search`/memory tools.

  `effective-tools` y el cableado del runtime. Las Fases 0/A/B de 06.17 (ADRs + SABER/RECORDAR backend
  - honestidad + vocabulario) pueden avanzar en paralelo a 06.18.
- **SPLIT opcional**: si se prefiere granularidad, partir en `06.17.1` (Fases 0+A+B) y `06.17.2`
  (Fases C..F, `blocking_plan: [06.17.1, 06.18]`). Un solo sub-plan `in_progress` a la vez.

  (0053-0055) sugeridos; se confirman en Fase 0 (06.18 usa 0048-0052).
