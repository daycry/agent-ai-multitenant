# constraints.txt — GENERADO, no editar a mano (prod-11 task_uv_lock_09, ADR 0147).
#
# Fuente de verdad: uv.lock (workspace uv declarado en pyproject.toml). Este
# fichero es su proyección plana para `pip`, que es lo que instalan CI y el
# Dockerfile del agent-runtime:
#
#     pip install -e "apps/api-server[dev]" -c constraints.txt
#
# Los rangos de cada pyproject.toml siguen siendo la restricción de
# COMPATIBILIDAD ("con qué versiones sé funcionar"); esto es la resolución
# REPRODUCIBLE ("con cuáles se validó este commit"). Sin él, cada `pip install`
# de CI resuelve las transitivas por su cuenta y el verde de hoy no dice nada
# del árbol de mañana (hallazgo quality-5 / gap5-4).
#
# Regenerar tras tocar cualquier pyproject.toml:
#
#     uv lock
#     uv export --frozen --all-packages --all-extras --all-groups \
#               --no-hashes --no-emit-workspace --no-annotate --no-header \
#               -o constraints.txt      # y volver a pegar esta cabecera
#
# `uv lock --check` en CI pone en rojo el drift entre pyproject.toml y uv.lock.
#
# Sin hashes a propósito: un fichero de constraints con hashes obliga a que
# TODA la instalación vaya con hash, y los `pip install -e` (editables) del
# monorepo no pueden tenerlo. La integridad de la descarga la cubre el
# `--require-hashes` que NO usamos aquí y, aguas arriba, pip-audit + el pin
# exacto de versión.
